LLM and Agentic AI: Production Intelligence

Four expert labs on the application layer of large language models: the tool-calling agent loop with guardrails and evals, multi-agent planner, worker and critic systems, inference-time scaling with verifiers, and agents that improve themselves from verified experience.

4 labs25 tasksDifficulty: all ExpertWeek 15

Why this category exists

A language model predicts text. An agent uses a language model inside a loop that perceives, decides, acts through tools, and observes the results. That loop is the application layer of everything the earlier volumes built: Volume 4 built the transformer, Volume 5 the pretraining, Volume 7 the post-training that makes models follow instructions, Volume 8 the serving stack, and Volume 9 the retrieval and agent basics. This category is what turns all of that into systems that do work: book the ticket, fix the bug, run the analysis.

What fails without these skills is specific and expensive. An agent without guardrails (explicit limits on what the loop may do) takes irreversible actions: deleting data, spending money, sending messages it cannot unsend. An agent without an evaluation harness (a benchmark plus operational metrics) can only be judged by vibes, and every prompt change is a gamble. An agent without verification trusts its own outputs, and language models are fluent enough to be wrong with confidence. The four labs in week 15 attack exactly these failure modes, in order: build the loop with guardrails and evals, split it across specialized agents with a critic, spend extra inference-time compute with verifiers, and close the loop by turning verified successes into memory.

All four labs carry the Expert rating. They are simulation labs, not toy demos: you implement the policies, the guardrails, the samplers, the verifiers, and the memory distillation yourself, and you measure operational metrics (success rate, cost per task, iterations to completion), not just accuracy. That measurement habit is the interview signal this whole volume is tuned for.

  1. The top ring is the minimal agent: a prompt plus tool results come in, a policy picks an action, a tool executes, and the result is observed. Everything in this volume is machinery around this ring.

  3. The dashed box maps the four labs: Lab 1 builds the loop with guardrails and an eval harness; Lab 2 splits it across planner, worker, and critic agents; Lab 3 spends extra loop iterations per problem with verifiers; Lab 4 turns verified successes into memory.

Key takeaways

  • An agent is a loop (perceive, plan, act, observe) around a language model, not a bigger model.
  • Guardrails, evaluation harnesses, and verification are the production difference between a demo and a system.
  • All four labs are Expert: you implement the machinery and measure operational metrics, not just accuracy.
  • Volume 9 built the agent basics; this volume builds reliability, scaling, and improvement on top.

Core ideas, worked end to end

Three ideas carry the category, each with the full treatment: what it is, why it exists, how it works, concrete numbers, the misunderstanding interviewers exploit, a visual, and the interview line.

Concept 1: the agent loop with guardrails

What it is. A tool-calling agent loop is a cycle: the policy reads the prompt and the conversation, proposes one tool action, the executor checks the guardrails, the tool runs, and its typed result is appended as an observation. Guardrails are the explicit limits checked before every action: which tools are allowed, whether the arguments are valid, the iteration and token budgets, and whether a write needs human confirmation. The week 15 day 3 lab builds this loop with a tiny heuristic policy standing in for the language model, so every piece is visible.

Why it exists. A language model alone cannot act: it has no hands. Tools are the hands, and hands without rules are dangerous. The production failures are all in the loop, not the model: unbounded iteration burning money, writes to the wrong system, tool outputs trusted blindly. Guardrails turn the loop from a demo into something shippable, and the evaluation harness turns "it seems to work" into a number.

How it works, step by step. (1) Define tools with explicit input and output contracts: name, typed arguments, typed return, and a short description of when to use it. Three deterministic tools are enough to learn the pattern. (2) Write the policy: given the prompt and history, pick the next action. Start heuristic; the shape is identical when a language model fills the slot. (3) Build the executor: propose, gate, execute, observe, repeat. The guardrail gates run before every action, and the stop conditions are explicit: the policy declares done, a budget is exhausted, or a gate fires. (4) Build the evaluation harness: a small benchmark of tasks plus operational metrics (success rate, iterations per task, cost per task), summarized after every run.

Concrete numbers. In the lab harness, a typical small task completes in 3 to 6 loop iterations. Set the iteration budget at roughly 3x the p95 of your benchmark: generous enough for hard tasks, tight enough to catch a looping agent before the bill hurts. Cost per task is the metric that decides whether the agent is a product or a demo.

The misunderstanding. "The agent is the model." Interviewers at the labs that ship agents ask the opposite question: for a fixed frontier model, what matters more, the model or the harness? The strong answer is the harness: simple composable loops beat frameworks, verification beats cleverness, and the highest-leverage piece is the agent running tests and checks after each edit. The model is interchangeable; the loop is the product.

How to read this diagram

  1. The four blue boxes are the components: tools with explicit input and output contracts, a policy that maps a prompt to an action (the lab uses a tiny heuristic policy standing in for the LLM), an executor that runs the loop, and an eval harness.
  2. The red box is the guardrail layer. Before every action the executor checks: is this tool allowed, are the arguments valid, are we within the iteration and token budgets, and does this write need human confirmation. Any failure stops or escalates.
  3. The dashed box is the loop itself: propose, gate, execute, observe, repeat. The stop conditions (done, budget exhausted, gate fired) are as important as the tools.
  4. The eval harness measures operational metrics, not just correctness: success rate, iterations per task, cost per task. You cannot improve what you do not measure.

Interview relevance. Tool-calling loop design with guardrails is a reported system design question at two of the three labs. The graded parts are always the same: the stop conditions, the write-action policy, the budgets, and how you would measure reliability.

Concept 2: inference-time scaling and verifiers

What it is. Inference-time scaling means spending more compute when answering instead of when training: sample many candidate answers and pick the best one. The picker is a verifier (a checker that knows the right answer, like running unit tests) or a judge (a scorer that estimates quality, like a language model grading outputs). The week 15 day 6 lab simulates the whole tradeoff space.

Why it exists. Some problems yield to more tries plus verification: code with tests, math with checkable answers, plans with simulators. When the verifier is cheap and reliable, extra samples are the cheapest accuracy available, no retraining required. This is also the mechanism behind several post-training methods: generate many, keep what verifies.

How it works, step by step. (1) Sample N candidates from the model at some temperature. (2) Score each with the verifier or judge. (3) Return the best (best-of-N). The lab measures the coverage curve: pass@1 versus best-of-N as N grows. Then it adds the refinements: temperature trades diversity against per-sample accuracy (hotter sampling finds more varied candidates but each is weaker); exact verifiers beat noisy judges; and adaptive budgets spend more samples on hard problems and fewer on easy ones instead of a flat N.

Concrete numbers. If one sample succeeds with probability p and samples are independent, N tries succeed with probability 1 - (1-p)^N. With p = 0.3, pass@1 is 0.3 and best-of-10 reaches about 0.97, in theory. In practice the gains flatten earlier: samples are not independent, and a noisy judge picks the wrong candidate part of the time. The lab measures both effects, which is why the verifier-quality curve matters more than the sample-count curve.

The misunderstanding. "More samples always help." They help until the selector becomes the bottleneck: with a noisy judge, extra samples mostly add chances to pick confidently wrong answers. The interview follow-up is always about the verifier: what verifies the output, how good is it, and what happens when it is wrong.

How to read this diagram

  1. The x-axis is samples per problem N; the y-axis is the success rate. The leftmost point is pass@1: a single sample.
  2. The green curve is best-of-N with an exact verifier: a checker that knows the right answer (like running unit tests). Coverage climbs steeply because the math 1 - (1-p)^N compounds, then plateaus as the easy wins are exhausted.
  3. The dashed orange curve is selection by a noisy judge (an LLM scoring its own outputs). It climbs less and ceilings lower: a bad selector wastes samples by picking the wrong candidate. Verifier quality dominates sample count.
  4. The lab adds two refinements: temperature trades diversity against per-sample accuracy, and adaptive budgets spend more samples on hard problems and fewer on easy ones.

Interview relevance. Inference-time compute is a first-class topic in post-training and serving interviews: best-of-N, verifiers versus judges, and the temperature tradeoff. The 1 - (1-p)^N math is the kind of on-the-board calculation interviewers ask for cold.

Concept 3: multi-agent systems and self-improvement

What it is. A multi-agent system splits the loop across specialized roles: a planner turns the task into a tool plan, a worker executes it under guardrails, a critic verifies the outputs and escalates failures, and an orchestrator drives the cycle over shared state. Self-improvement closes a second loop: verified successful rollouts are distilled into memory that makes the next round of tasks easier. The week 15 day 4 lab builds the split; the week 15 day 7 lab builds the improvement loop.

Why it exists. One big prompt doing everything is hard to debug and harder to trust. Narrow roles have narrow contracts, and narrow contracts are checkable: the critic cannot take actions, the worker cannot rewrite the plan. Self-improvement exists because the cheapest way to get better at a repeated task is to remember what worked, but only if the memories are verified: unverified memory teaches the agent its own mistakes.

How it works, step by step. Multi-agent: (1) the orchestrator creates fresh shared state; (2) the planner converts the user task into a short sequence of tool calls; (3) the worker executes each step, enforcing allowed tools and argument validation; (4) the critic rejects outputs that contradict the plan or the evidence and escalates what it cannot verify. Self-improvement: (1) run the agent on a task set and collect rollouts; (2) keep only rollouts the verifier accepts; (3) distill the successful traces into compact memory (reusable patterns, not raw transcripts); (4) give the memory to the planner on the next round; (5) evaluate before versus after, and compare the improvement against the cheaper alternative of just sampling more.

Concrete numbers. The week 15 day 7 lab frames the decision as a contest: memory-assisted planning versus extra sampling at equal compute. Memory wins when the task distribution repeats (the same patterns recur); extra sampling wins on one-off novel tasks. The lab makes you measure which regime you are in instead of assuming.

The misunderstanding. "More agents are better." Every added agent adds coordination overhead and new failure modes: the planner and worker can disagree, the critic can be wrong, shared state can go stale. The interview question is always "why three agents instead of one good prompt", and the answer is verifiability per role, not parallelism for its own sake. The twin mistake is "memory always helps": unverified memory compounds errors, which is why the verifier gates what enters memory.

How to read this diagram

  1. The planner turns a user task into a short sequence of tool calls. The worker executes the plan under guardrails. The critic verifies outputs and escalates failures. An orchestrator drives the cycle; all three share one state object so nothing is lost between roles.
  2. Splitting roles beats one big prompt because each role gets a narrow contract: the critic cannot take actions, the worker cannot change the plan. Narrow contracts are checkable.
  3. The self-improvement loop (green dashed box) collects rollouts, keeps only the verified successes, distills them into compact memory, and hands that memory to the planner next round.
  4. The red lines are the two failure modes the lab makes you confront: unverified traces teach the agent its own mistakes (errors compound), and stale memory rots as tasks change. The verifier gates what enters memory.

Interview relevance. Multi-agent design and agent memory are reported system design questions. The graded parts are the role contracts, the critic escalation policy, what enters memory and why, and how you evaluate the whole system end to end.

Key takeaways

  • The agent loop is propose, gate, execute, observe, repeat; guardrails and stop conditions are the shippable parts.
  • Inference-time scaling works through verifiers; verifier quality sets the ceiling, not sample count.
  • Split agents by verifiable role contracts; let only verified rollouts become memory.
  • Measure operational metrics (success rate, cost per task, iterations) for every agent change.

@dataclass
class Tool:
    name: str
    func: Callable[[Dict[str, Any]], Dict[str, Any]]
    cost: float


def tool_add(args: Dict[str, Any]) -> Dict[str, Any]:
    a = int(args['a'])
    b = int(args['b'])
    return {'result': a + b}


def tool_lower(args: Dict[str, Any]) -> Dict[str, Any]:
    s = str(args['s'])
    return {'result': s.lower()}


def tool_lookup_city_country(args: Dict[str, Any]) -> Dict[str, Any]:
    city = str(args['city']).strip().lower()
    table = {
        'paris': 'france',
        'tokyo': 'japan',
        'delhi': 'india',
        'seattle': 'usa',
    }
    if city not in table:
        return {'error': 'unknown_city'}
    return {'result': table[city]}


TOOLBOX: Dict[str, Tool] = {
    'add': Tool('add', tool_add, cost=1.0),
    'lower': Tool('lower', tool_lower, cost=0.2),
    'lookup_city_country': Tool('lookup_city_country', tool_lookup_city_country, cost=0.5),
}

check('toolbox_has_3', len(TOOLBOX) >= 3)

@dataclass
class Action:
    tool_name: str
    args: Dict[str, Any]


def policy(prompt: str) -> Optional[Action]:
    """Very small heuristic policy.

    Returns an Action, or None if no tool should be called.
    """
    p = prompt.strip()

    # arithmetic: "add 2 and 3"
    m = re.search(r"add\s+(-?\d+)\s+(and|to)\s+(-?\d+)", p, flags=re.IGNORECASE)
    if m:
        return Action('add', {'a': int(m.group(1)), 'b': int(m.group(3))})

    # lowercasing: "lower: HeLLo"
    m = re.search(r"lower\s*:\s*(.+)$", p, flags=re.IGNORECASE)
    if m:
        return Action('lower', {'s': m.group(1)})

    # lookup: "country of Tokyo"
    m = re.search(r"country\s+of\s+([A-Za-z ]+)$", p, flags=re.IGNORECASE)
    if m:
        return Action('lookup_city_country', {'city': m.group(1).strip()})

    return None

check('policy_add', policy('add 2 and 3').tool_name == 'add')
check('policy_lower', policy('lower: HeLLo').tool_name == 'lower')

TASKS = [
    ('add 2 and 3', '5'),
    ('lower: HeLLo', 'hello'),
    ('country of Tokyo', 'japan'),
    ('country of Paris', 'france'),
]


def evaluate(tasks, *, toolbox, allowlist=None):
    oks = 0
    steps = []
    costs = []
    for t, expected in tasks:
        r = run_agent(t, toolbox=toolbox, allowlist=allowlist, max_steps=3, budget=3.0)
        ok = r.ok and (r.answer == expected)
        oks += int(ok)
        steps.append(r.steps)
        costs.append(r.cost)
    return {
        'n': len(tasks),
        'success_rate': oks / len(tasks),
        'avg_steps': float(np.mean(steps)),
        'avg_cost': float(np.mean(costs)),
    }

metrics = evaluate(TASKS, toolbox=TOOLBOX, allowlist=set(TOOLBOX.keys()))
print(metrics)
check('good_success', metrics['success_rate'] >= 0.75)

def sample_candidate(problem: dict, temperature: float, rng: np.random.Generator):
    logits = np.array([c['logit'] for c in problem['candidates']], dtype=np.float64) / float(temperature)
    logits = logits - logits.max()
    probs = np.exp(logits)
    probs = probs / probs.sum()
    idx = int(rng.choice(len(problem['candidates']), p=probs))
    chosen = problem['candidates'][idx]
    return {k: chosen[k] for k in chosen}

def verify(problem: dict, cand: dict) -> bool:
    return str(cand['text']).strip() == str(problem['gold']).strip()

def best_of_n(problem: dict, n_samples: int, temperature: float, rng: np.random.Generator):
    sampled = [sample_candidate(problem, temperature=temperature, rng=rng) for _ in range(n_samples)]
    chosen = sampled[0]
    solved = False
    for cand in sampled:
        if verify(problem, cand):
            chosen = cand
            solved = True
            break
    return chosen, solved, sampled

def success_rate(problem_bank, n_samples: int, temperature: float, trials: int = 200):
    vals = []
    for seed in range(trials):
        trial_rng = np.random.default_rng(seed)
        ok = 0
        for problem in problem_bank:
            _, solved, _ = best_of_n(problem, n_samples=n_samples, temperature=temperature, rng=trial_rng)
            ok += int(solved)
        vals.append(ok / len(problem_bank))
    return float(np.mean(vals))

check('after1_ge_before3', after1 >= before3)

Source: S30 AI Lab, https://ai.thes30.com/problems/w15-d7-self-improving-agents.

Key takeaways

  • The intro lab installs the loop, the guardrails, and the operational-metrics habit; everything else builds on it.
  • The multi-agent lab teaches decomposition by verifiable contracts, not by adding agents for their own sake.
  • The inference-time scaling lab teaches the ceiling lesson: verifier quality dominates sample count.
  • The self-improvement lab teaches the gate lesson: only verified rollouts become memory.

On the board

  • Sketch the executor loop with its guardrail gates and stop conditions from memory.
  • Your critic keeps rejecting good worker outputs. Is the fix a better worker or a better critic? (Measure first: log which rejections were wrong.)

Interview clearance

Agent interviews grade the harness, not the model: guardrails, verification, evaluation, and the tradeoffs between them. The questions below rehearse the reported shapes.

On the board: the agent warm-ups

  • Design a tool-calling agent loop for a coding assistant. Name the guardrails before the tools.
  • When is best-of-N worth the cost, and what sets its ceiling? (Cheap reliable verifier; the verifier sets the ceiling.)
  • Why three agents (planner, worker, critic) instead of one good prompt? (Verifiable role contracts.)
  • What may enter the agent memory store, and what must never enter? (Only verified successes; never unverified traces.)

Q1. Your production agent calls tools that can write to customer systems. Which guardrail matters most?

Answer: C. Irreversible writes are the catastrophic failure mode, so human confirmation on writes dominates every other guardrail in production.

  • A, wrong: A larger iteration budget: this makes runaway loops more expensive, not safer.
  • B, wrong: A faster policy model: latency is nice but irrelevant to the safety question.
  • C, right: Human confirmation for irreversible writes, plus idempotency keys and read-versus-write tool classification, is the production answer.
  • D, wrong: More tools: a larger tool surface increases the wrong-tool risk; the reported guidance is fewer, more capable tools.

Q2. You have a fixed inference budget per problem. Do you spend it on best-of-16 with a noisy judge, or on fewer samples with an exact verifier?

Worked answer. Prefer fewer samples with the exact verifier. The coverage math 1 - (1-p)^N assumes the selector picks the true best; a noisy judge breaks that assumption and wastes samples on confidently wrong picks. The lab comparison shows the judge curve climbing less and ceilinging lower. Spend the budget where the selector is trustworthy: exact verification first, and only scale samples while the selector keeps up. If no exact verifier exists, say so and price the judge error explicitly.

Trap. Answering "more samples" without asking about the selector. Sample count is the wrong knob when the judge is the bottleneck.

Q3. Your agent solved 40 tasks and you want it to improve on the next 40 similar tasks. What do you do?

Answer: B. Distilling verified successes into memory is the self-improvement loop, but the verifier gate is what keeps it safe.

  • A, wrong: Feed all 40 raw transcripts into the prompt: unverified traces teach the agent its own mistakes, and raw transcripts waste context.
  • B, right: Keep only verifier-accepted rollouts, distill them into compact reusable memory, and evaluate before versus after against extra sampling.
  • C, wrong: Fine-tune the policy on all 40 outcomes: without the verifier gate you bake in the failures too.
  • D, wrong: Add a fourth agent: more roles add coordination overhead without addressing the learning question.

Q4. A customer says your RAG-based assistant hallucinates. You have 48 hours. What do you do first?

Worked answer. Diagnose before tuning. Collect 10 to 20 concrete failing examples with expected answers, then trace each to one of four diseases: retrieval miss (search problem), retrieval hit with wrong synthesis (grounding problem), question outside the corpus (missing abstention path), or expectation mismatch (data problem). Build a tiny harness scoring retrieval recall separately from answer faithfulness, quantify the split, and only then pick the fix: re-ranking, citation-required prompting with an abstention instruction, or a corpus gap to fill. Report the split to the customer; most "hallucination" complaints are retrieval problems wearing a generation costume.

Trap. Tuning the prompt or the model first. Without the diagnosis you cannot know whether the disease is retrieval, grounding, abstention, or data.

Key takeaways

  • Name guardrails before tools in every agent design answer; writes need human confirmation.
  • Verifier quality sets the inference-time scaling ceiling; price the selector before the sample count.
  • Only verified rollouts enter memory; evaluate memory against extra sampling.
  • Diagnose agent failures into retrieval, grounding, abstention, or data before tuning anything.

On the board: final checks

  • State the 1 - (1-p)^N coverage math and when it breaks. (Breaks when the selector is noisy.)
  • What are the three roles in the multi-agent lab, and what can each one not do? (Planner cannot act; worker cannot replan; critic cannot act.)
