Evaluation and Debugging: Knowing What Works

Volume 19 built the models. This volume builds the judgment: measure what matters, stop leaks before they poison your metrics, and debug models with evidence instead of guesses.

6 labs42 tasksDifficulty: Medium, all six labsWeek 5, days 1 through 6

Why this category exists

Volume 19 built the models: logistic regression, trees, boosting, SVMs, nearest neighbors. This volume answers the question that comes next and never goes away: does it actually work, and how do you know? In research and in production, a model is only as trustworthy as the process that measured it. A leaky evaluation can make a useless model look brilliant. A wrong metric can make a brilliant model look useless. Debugging without slice-level evidence is guessing.

Without these skills, four things fail. First, leakage (information from the answer sneaking into the features) silently inflates your scores, and you ship a model that collapses on real data. Second, the wrong metric optimizes the wrong behavior: a 95 percent accurate fraud model that catches nothing. Third, uncalibrated probabilities mislead every downstream decision that trusts them. Fourth, aggregate metrics hide cohort failures: the model is fine overall and terrible for one customer group.

The six labs are all Medium difficulty and run across Week 5, days 1 through 6. They form a tight arc: engineer features safely, measure correctly, understand failure modes, debug with evidence, combine everything on a hard dataset, then compress with PCA (principal component analysis).

How to read this diagram

  1. Data is split into train, validation, and test before anything is fit.
  2. Features are engineered inside pipelines so statistics come from train rows only.
  3. The model fits on train and emits scores (probabilities) on the rest.
  4. Metrics plus a cost-aware threshold turn scores into decisions.
  5. Slice analysis and error inspection find the failing cohorts.
  6. The loop closes: fixes go back into the features, never into the metric.

Core ideas, worked end to end

Concept 1: pick the metric that matches the decision

A metric is a number that summarizes model quality. For binary classification, every prediction falls into one of four cells. True positives (TP): predicted positive, actually positive. False positives (FP): predicted positive, actually negative. False negatives (FN): predicted negative, actually positive. True negatives (TN): predicted negative, actually negative. From these: precision = TP / (TP + FP), the fraction of flagged items that are real. Recall = TP / (TP + FN), the fraction of real items that were flagged. Accuracy = (TP + TN) / total.

Accuracy exists because it is the default score in every library. It fails under class imbalance (one class much rarer than the other), which is the norm in fraud, churn, and medical screening. A model that predicts the majority class every time scores high accuracy and learns nothing. The fix is to measure ranking quality: sort by score and sweep the threshold, then summarize with the PR curve (precision-recall curve) and its area, PR-AUC (precision-recall area under the curve). The older ROC curve (receiver operating characteristic curve) plots true positive rate against false positive rate; it looks flattering when negatives dominate, so report the base rate (fraction of positives) alongside any curve.

The mechanics, step by step: score every validation example; sort descending by score; walk down the list treating each score as a candidate threshold; at each step count TP, FP, FN among the items above the line and compute precision and recall; plot precision against recall; the area under that curve is PR-AUC. A perfect ranker has PR-AUC near 1. A random ranker has PR-AUC near the base rate, not 0.5.

Concrete numbers. 1,000 customers, 50 churn (base rate 5 percent). A majority baseline that always predicts "no churn": accuracy = 950 / 1000 = 95 percent, recall = 0 / 50 = 0, precision undefined. Now a real model at one threshold: TP = 30, FP = 40, FN = 20, TN = 910. Accuracy = 940 / 1000 = 94 percent, worse than the baseline. Precision = 30 / 70 = 43 percent. Recall = 30 / 50 = 60 percent. The baseline wins on accuracy; only the model finds any churners at all.

The misunderstanding interviewers exploit: "my ROC-AUC is 0.92, so the model is great." Under 1 percent base rate, ROC-AUC can sit at 0.92 while precision at any useful recall is single digits. The correct answer names PR-AUC, states the base rate, and asks what decision the scores feed.

How to read this diagram

  1. Rows are the actual class, columns are the predicted class.
  2. The top-left cell (TP = 30) is churn predicted and churn observed.
  3. The top-right cell (FP = 40) is churn predicted but no churn: the cost of false alarms.
  4. The bottom-left cell (FN = 20) is missed churners: the cost of silence.
  5. Precision uses the predicted-positive column: 30 / 70 = 43 percent.
  6. Recall uses the actual-positive row: 30 / 50 = 60 percent.
  7. Accuracy mixes all four cells: 94 percent, which still loses to the do-nothing baseline.

Interview relevance. "When can accuracy be misleading?" is a standing checkpoint in the w5-d2 lab, and Google, Netflix, and Airbnb all list metrics and evaluation as high-confidence interview topics for these labs.

Key takeaways

  • Accuracy rewards the majority class; under imbalance it is nearly useless.
  • Precision = TP/(TP+FP), recall = TP/(TP+FN); both derive from the four confusion-matrix cells.
  • Compare models with PR-AUC under imbalance, and always report the base rate.
  • ROC-AUC looks optimistic when negatives dominate; do not trust it alone.

Concept 2: thresholds, costs, and calibration

A model outputs scores; a business needs decisions. The decision threshold is the score cutoff above which you predict positive. Calibration means the predicted probabilities match observed frequencies: among cases scored 0.7, about 70 percent are positive. ECE (expected calibration error) measures this: split predictions into bins, take the absolute gap between average predicted probability and actual fraction positive in each bin, and average those gaps weighted by bin size.

Thresholds exist because errors have prices, and the prices are rarely equal. Missing a fraudulent transaction (FN) may cost ten times flagging a legitimate one (FP). The threshold that maximizes accuracy ignores that entirely. The fix: choose the threshold that minimizes expected cost = FP_cost * FP + FN_cost * FN on validation data. Calibration exists because downstream systems trust probabilities: a 0.9 that behaves like 0.6 breaks every risk calculation built on it. Temperature scaling repairs miscalibration after training by dividing logits by a single learned temperature T before the softmax, which softens or sharpens the distribution without changing the ranking.

Calibration mechanics: bin predictions by score into ten equal bins; per bin compute mean predicted probability and fraction of positives; plot fraction positive against mean probability (the reliability curve); a perfectly calibrated model hugs the diagonal. The reliability diagram is that plot; points below the diagonal mean overconfidence.

Concrete numbers. FN costs $10, FP costs $1. Threshold A: FP = 40, FN = 20, cost = 40 * 1 + 20 * 10 = $240. Threshold B (stricter): FP = 10, FN = 35, cost = 10 + 350 = $360. Threshold C (looser): FP = 90, FN = 8, cost = 90 + 80 = $170. The cheapest threshold is the loosest one, because false negatives are expensive. For ECE: a bin [0.8, 0.9) holds 50 items with 30 positives. Mean confidence 0.85, accuracy 0.60, gap 0.25. Its contribution to ECE is 0.25 * (50 / N) where N is the total count.

The misunderstanding: "calibration improves accuracy." It does not change a single prediction at a fixed threshold. It fixes trust in the probabilities, which is what the rest of the system consumes. Thresholds fix decisions; calibration fixes confidence.

How to read this diagram

  1. The x-axis is what the model claimed; the y-axis is what actually happened.
  2. The dashed diagonal is perfect calibration: claim equals outcome.
  3. Every bin sits below the diagonal: the model claims 0.7 but delivers about 0.55.
  4. ECE is the bin-size-weighted average of these vertical gaps.
  5. Temperature scaling would pull these dots toward the diagonal without changing their order.
  6. You would then re-pick the threshold by cost, not by accuracy.

Interview relevance. "How do you pick a threshold if false negatives cost 10x false positives?" is the interview angle on the w5-d2 lab, and it is also the expected-cost calculation above.

Key takeaways

  • Pick thresholds by minimizing expected cost on validation, not by maximizing accuracy.
  • Calibration means predicted probabilities match observed frequencies; ECE quantifies the gap.
  • Reliability curves diagnose overconfidence; temperature scaling fixes it post hoc.
  • Ranking quality (PR-AUC) and decision quality (cost at threshold) are separate questions.

Concept 3: bias, variance, and regularization

Bias is error from the model being too simple to capture the pattern: a straight line fit to a curve. Variance is error from the model being too sensitive to the particular training sample: it memorizes noise. A learning curve plots training and validation error against training-set size or against model capacity (depth, number of features, regularization strength). Regularization is any penalty that discourages complexity; the two workhorses are L1 (lasso) and L2 (ridge) penalties on the weights.

This exists because "the model is wrong" is not a diagnosis. High bias means the model cannot fit even the training data: get a more expressive model or better features. High variance means training error is low and validation error is high: the model memorized. The cures differ completely, and the labs make you read the signature from curves: depth sweep, C sweep for L2 logistic regression, and training on increasing data sizes. As built in Volume 19, logistic regression is a high-bias, low-variance baseline, which is why it anchors the w5-d3 experiments.

L1 vs L2 mechanics: L2 adds lambda * sum(w^2) to the loss, which shrinks every weight toward zero smoothly; the gradient of the penalty is proportional to the weight, so small weights shrink slowly and rarely reach exactly zero. L1 adds lambda * sum(|w|), whose penalty gradient has constant magnitude, so it drives weights to exactly zero and performs feature selection. The gotcha the lab plants: L1 zeroes out correlated features arbitrarily, picking one survivor from a redundant group, which makes feature-importance readings unstable.

Concrete numbers from the depth sweep. Tree depth 1: train error 30 percent, validation 32 percent. Both high: high bias. Depth 12: train error 2 percent, validation 30 percent. Big gap: high variance. Depth 5: train 12 percent, validation 16 percent. The U-shape bottom is the sweet spot. For logistic regression, sweeping C (inverse regularization strength) from 0.001 to 1000 traces the same curve in the other direction.

The misunderstanding: "more regularization is always safer." Push it too far and bias climbs: the model underfits and both errors rise. And "more data fixes everything": more data shrinks variance, but a biased model stays biased. The interview angle on the lab asks exactly this: how do you know whether to collect more data or regularize harder?

How to read this diagram

  1. The x-axis is model capacity: tree depth, inverse regularization strength, feature count.
  2. The blue curve (training error) falls monotonically: more capacity always fits train better.
  3. The amber curve (validation error) falls then rises: the classic U-shape.
  4. Left of the dashed line: both errors high, training and validation close. High bias.
  5. Right of the dashed line: training error low, validation error climbing. High variance.
  6. The fix depends on the zone: capacity or features on the left, regularization or data on the right.

Interview relevance. "How do you know whether to get more data vs regularize more?" is the interview angle attached to the w5-d3 lab. The answer is the learning curve, not a guess.

Key takeaways

  • High bias: both errors high and close; fix with capacity or better features.
  • High variance: train low, validation high; fix with regularization, more data, or simpler models.
  • L2 shrinks weights smoothly; L1 drives them to exactly zero but picks arbitrarily among correlated features.
  • Logistic regression is the canonical high-bias, low-variance baseline.

Concept 4: error analysis, slices, and the leakage discipline

Error analysis is the systematic inspection of the examples the model gets wrong, split into false positives and false negatives. A slice is a subgroup of the data defined by a feature: new vs returning customers, one region, one device type. Feature ablation removes one feature group, retrains, and measures how much the metric drops: a large drop means the group mattered. Label leakage is the silent killer: a feature that carries information about the answer that will not exist at prediction time, like an aggregate computed over the future, or a target encoding fit on the whole dataset including the validation rows.

Aggregate metrics exist to compare models, not to debug them. "Overall accuracy looks fine" can hide severe cohort failures, which is the exact gotcha the w5-d4 lab plants. Slice metrics find the failing cohorts. FP vs FN inspection tells you which error type dominates and whether the cost model in Concept 2 matches reality. Ablation tells you which features earn their place. And leakage discipline exists because a leaky feature is indistinguishable from a brilliant one on your validation set: the metric looks amazing right up until the model meets production.

The leakage mechanics, step by step: naive target encoding replaces a categorical value with the mean label of that category, computed on the full dataset. Because the validation labels contributed to those means, the feature smuggles the answer into the validation rows. Cross-validation alone does not save you: the leak happened before the split. The fix is a pipeline: split first, then fit every preprocessing step (imputation, encoding, scaling) inside each fold on train rows only. The w5-d1 lab demonstrates the leak deliberately: naive target encoding shows stellar validation PR-AUC and collapses on the holdout.

Concrete numbers. Overall accuracy 92 percent; slice "customers joined in the last 30 days" sits at 68 percent. That slice is the debugging target, not the 92 percent. Ablation: dropping the engineered "title" feature group moves validation PR-AUC from 0.81 to 0.75, so the group earns its keep. Leakage demo: naive target encoding gives validation PR-AUC 0.91 and holdout 0.62; the leak-safe version gives 0.79 and 0.77.

The misunderstanding: "I used cross-validation, so my evaluation is trustworthy." Cross-validation only protects you if nothing outside the fold saw the validation rows. Preprocessing fit before the split, aggregates over the full time window, and target statistics computed globally all leak through cross-validation untouched.

How to read this diagram

  1. Left path: impute and encode on the full dataset, then split. The imputer saw validation rows.
  2. Validation scores from the left path are optimistic and meaningless.
  3. Right path: split first, then fit every preprocessing step inside the pipeline.
  4. Each fold fits the imputer and encoder on train rows only, then transforms the validation rows.
  5. This is the only arrangement where the validation score estimates production behavior.
  6. The w5-d1 lab shows the left path failing live: great validation, broken holdout.

Interview relevance. Google lists feature engineering, error analysis, and model debugging as high-confidence topics for these labs. "Why is a pipeline required for trustworthy debugging?" is the standing checkpoint on the w5-d4 lab.

Key takeaways

  • Aggregate metrics compare; slice metrics debug. Always break errors down by cohort and by FP vs FN.
  • Feature ablation measures what each feature group earns; drop what does not pay.
  • Leakage is invisible in validation scores; only pipeline discipline (split first, fit inside folds) prevents it.
  • A metric that looks too good on validation and collapses on holdout is the signature of a leak.

On the board

  • When do interaction features help linear models? (Hint: the w5-d1 interview angle.)
  • Your slice analysis shows one cohort at 60 percent accuracy. What are your next three moves?

def pca_fit(X, k):
    Xc, mu = center(X)
    C = covariance_matrix(Xc)
    vals, vecs = np.linalg.eigh(C)
    idx = np.argsort(vals)[::-1]
    vals = vals[idx]
    vecs = vecs[:, idx]

    vals_k = vals[:k]
    vecs_k = vecs[:, :k]
    evr = vals_k / np.sum(vals)

    return {
        'mean': mu,
        'components': vecs_k,
        'explained_variance': vals_k,
        'explained_variance_ratio': evr,
    }

Q1. A fraud model flags 200 of 10,000 transactions. 60 are real fraud. The dataset has 100 real frauds total. What are precision and recall?

Answer: precision = 60 / 200 = 30 percent; recall = 60 / 100 = 60 percent.

  • 30% / 60%, right: precision divides by predicted positives (200), recall by actual positives (100).
  • 60% / 30%, wrong: this swaps the denominators: the classic precision-recall mixup.
  • 99% accuracy, wrong: accuracy is (60 + 9,800) / 10,000 = 98.6 percent, which says nothing about the 40 missed frauds.

Q2. Your reliability curve sits entirely below the diagonal. What does this mean, and what is the cheapest fix?

Answer: the model is overconfident at every probability level; apply temperature scaling (learn T on validation, divide logits by T).

  • Overconfident + temperature scaling, right: below the diagonal means claimed probability exceeds observed frequency; scaling fixes calibration without touching ranking.
  • Underconfident, wrong: underconfidence would sit above the diagonal.
  • Retrain with more data, wrong: more data does not systematically fix miscalibration, and it is the expensive move.

Q3. Validation PR-AUC is 0.90 but holdout is 0.63. Name the two most likely causes and the test that distinguishes them.

Answer: label leakage (preprocessing fit before the split) or distribution shift between validation and holdout. Test: rebuild the pipeline leak-safe (split first, fit inside folds) and re-score; if validation drops to about 0.63, it was leakage.

  • Leakage vs shift + rebuild test, right: the rebuild experiment separates the two cleanly.
  • Overfitting to hyperparameters, wrong: tuning on validation moves scores a little, not 27 points.
  • Bad luck, wrong: a 27-point gap on a real holdout is never noise; it is a process bug.
