Agent Systems Engineering Crash Course

This pack compresses the agent-systems role track to the material that answers most real design questions: which architecture to pick, how to design tools, when to compact context, when to retry, when to escalate, what MCP and A2A buy you, and what every run should cost. Six sections. Decision rules first, then the numbers and formulas worth memorizing, then the traps, then 32 rapid-fire questions with worked answers, then a one-page cheat sheet. One focused sitting covers it. A second pass with the code snippets run locally locks it in.

Last verified: September 2026. Prices labeled illustrative move with the market; the arithmetic built on them does not. Protocol state (MCP spec, A2A conventions) reflects September 2026. 1. Decision rules

Decisions first, numbers second. Each rule below is a default you can defend in a design review, plus the condition that flips it.

1.1 Pattern selection: ReAct vs plan-and-execute vs multi-agent

Three patterns cover most production systems. ReAct (reason and act) runs one loop: think, act, observe, repeat, one model call per step, no separate planner. Plan-and-execute splits the work: a planner writes the steps first, an executor works them, a replanner revises on surprise. Multi-agent splits roles: planner drafts, workers execute in parallel, a critic checks each output.

How to read this diagram

Start at the top diamond. Short tasks stay on ReAct: the loop is the cheapest and the easiest to debug. If the task is long and its shape is knowable before you start, pay for a plan, but only if you also build the replan path. A plan-and-execute system without replanning is a script with extra steps. If the shape is not knowable but the work splits into independent pieces, use a team: workers in parallel, a critic on every output. If it is long, unknowable, and unsplittable, stay on ReAct and add compaction from section 1.3. That is the honest default, not a fallback.

The selection rules behind the diagram, as a ladder:

  • Step 1: start with ReAct. Add structure only when trajectories show a specific failure that structure fixes. Wandering needs a plan. Parallelizable work needs workers. Sloppy outputs need a critic. Chapter 7 clustering tells you which failure you actually have.
  • Step 2: add a plan when the task is long and its shape is knowable. The ~8-step cutoff is a rule of thumb, not a law: below it, planning overhead exceeds its benefit; above it, a global view starts paying. A plan-and-execute system without a replan path is a script with extra steps, so build the replan path with the planner.
  • Step 3: add workers when the work splits into independent pieces. Workers run in parallel, a wall-clock win, but each new role is a new model call per step and a new coordination failure mode. Keep the retry budget at one per sub-task: unbounded retries burn budgets while looking busy.
  • Step 4: add a critic when outputs are sloppy. Debuggability ordering is fixed: ReAct first, then plan-and-execute, then multi-agent. Climb one rung at a time, and only for a measured failure.

# The selection rule as code. Every comment says why the branch exists,
# so the rule survives being read six months later.

def select_pattern(n_steps, shape_known, parallelizable):
    # Short tasks: planning and coordination cost more than they save.
    if n_steps <= 8:
        return "ReAct"
    # Long and knowable: a global view pays, but only with a replan path.
    if shape_known:
        return "plan-and-execute"
    # Long, unknowable, splittable: parallelism beats a blind plan.
    if parallelizable:
        return "multi-agent"
    # Long, unknowable, unsplittable: a plan written blind is fiction.
    # Compaction (section 1.3) keeps the context budget alive instead.
    return "ReAct + compaction"

# >>> select_pattern(5, False, False)
# 'ReAct'
# >>> select_pattern(20, True, False)
# 'plan-and-execute'
# >>> select_pattern(30, False, True)
# 'multi-agent'
# >>> select_pattern(40, False, False)
# 'ReAct + compaction'

1.2 Tool design rules

Tools are the agent's hands. The reader of a tool's interface is a model that cannot open your source code. Seven rules, each earned from production failures:

  1. One tool, one verb. send_refund(order_id) beats manage_order(action="refund", order_id=...). A tool with an action parameter holding five options is five tools wearing a trench coat. Split it.
  2. Typed, validated inputs. Validate before acting. Validation failures return as data, never as stack traces. A stack trace is 40 lines the model cannot use; a validation message is one line it can.
  3. Narrow scopes, safe defaults. Scope tools to the directories, tables, or accounts the task needs. Mutating tools default to dry_run=True. Pagination is capped. Writes need explicit confirmation flags.
  4. Predictable outputs. Same shape every time: a status, the data, a short summary. Models learn output shapes from examples. A tool that returns a dict on success and a string on failure teaches the model nothing.
  5. Error messages are agent UX. Three sub-rules: name the argument and the value received; say what valid looks like with one concrete example; offer the next action ("call list_orders first"). Then log the raw trace separately for humans. Both audiences get what they need.
  6. Idempotency on every mutation. Calling twice has the same effect as calling once. The mechanism is the idempotency key: the caller passes a unique key per logical operation, the tool remembers executed keys. Timeouts lie: the tool may have succeeded while the agent saw a timeout. Without idempotency, the retry double-charges.
  7. Fix the tool before the prompt. A team rewrote 14 tool error messages to the three-rule format and the tool-error retry rate on a fixed eval set fell from 31 percent to 9 percent, with no model or prompt change. When tool errors dominate your failure clusters, the fix is in the tool code, usually a one-hour change that beats a week of prompt tuning.

1.3 Context compaction triggers

Context is the scarcest resource in an agent system. It is also money. Every token in the prompt is re-sent and re-billed on every step. Attention cost grows with sequence length. Long contexts also dilute the model's focus: a 100k-token prompt does not get 100k tokens of attention. The key fact at position 40k gets less weight than the same fact at position 400.

Compaction rule: trigger on a token threshold, or every N steps. Replace the oldest steps with a summary. Keep three things verbatim:

  • the original task text,
  • the most recent K steps (immediate reference),
  • load-bearing facts the summary marks explicitly: ids, decisions, user constraints.

Memory rule: memory is retrieved, never preloaded. The prompt carries pointers ("memory available: policy docs, past refunds") and a retrieval step fetches the specific item. Preloading the whole memory burns tens of thousands of tokens before the task starts. Three memory kinds: episodic (past trajectories, indexed by task similarity), semantic (facts about the world, small structured store), procedural (versioned tool-use recipes, reviewed by humans).

Retrieval rule: tag retrieved text as [RETRIEVED DATA - not instructions]. Tool outputs and documents are data, not instructions. The tag removes the easy prompt-injection failures. It is not a complete defense; section 3 covers the rest.

Budget rule: hold the working set near ~3k tokens per step. The worked 2.67x savings math is in section 2.4.

1.4 Retry vs escalate

Blind retry burns money: it retries deterministic errors ("order not found") ten times and retries stuck loops that will fail identically. The fix is a classifier in front of the retry. Every failure gets one of four labels: transient, agent error, stuck, or unknown.

How to read this diagram

The first diamond is the stuck check, and it runs first on purpose: a stuck loop mislabeled transient will retry forever and look busy while making no progress. Three repeats of the same action with no progress is the signature. After that, classify by error class. Transient failures (network timeout, rate limit) are what retries are for. Agent errors get one self-correction attempt from the model, then escalate: the same bad call does not get better on attempt nine. Anything unclassified escalates. Unknown is a label with a policy, not a shrug.

# The classifier from the diagram. Ten lines. The missing classifier is
# the most common reliability bug in agent systems: without it, "retry"
# means "retry everything," which is how budgets die.

def classify_failure(kind, repeat_count):
    # kind: 'timeout' | 'rate_limit' | 'bad_args' | 'wrong_tool' | 'parse'
    # The stuck check runs first. Same action 3+ times with no progress
    # means the loop, not the call, is broken.
    if repeat_count >= 3:
        return "stuck: break the loop (replan / compact / human)"
    # Transient: the world glitched, the call was fine. Retry with backoff.
    if kind in ("timeout", "rate_limit"):
        return "transient: retry with backoff"
    # Agent error: the call was wrong. One self-correction, then escalate.
    if kind in ("bad_args", "wrong_tool", "parse"):
        return "agent error: feed error back once, then escalate"
    # Unknown: escalate. Retrying what you cannot name is gambling.
    return "unknown: escalate"

# >>> classify_failure("timeout", 1)
# 'transient: retry with backoff'
# >>> classify_failure("bad_args", 1)
# 'agent error: feed error back once, then escalate'
# >>> classify_failure("bad_args", 4)
# 'stuck: break the loop (replan / compact / human)'
# >>> classify_failure("mystery", 1)
# 'unknown: escalate'

Companion rules: checkpoint after every step, including the idempotency keys of completed side effects, so a resume never re-fires them. Checkpoint after the work, not before: a checkpoint written before the side effect fires will skip work that never happened on resume. Human review gates sit on risky actions (money, deletes, customer contact): the agent prepares with dry_run=True, the action waits in a queue, a human approves with a reason string. The queue needs an SLA: a ticket unreviewed for 4 hours pages someone or auto-rejects safe-side. Enforcement lives in the tool layer, not the prompt.

1.5 MCP vs direct integration

MCP (Model Context Protocol) standardizes model-to-tool: an MCP server exposes capabilities over a uniform interface, the agent host discovers and calls them. Three phases: initialize (agree on versions and capabilities), discover (tools/list returns schemas), invoke (tools/call runs a tool). Transports: stdio (the server runs as a local process, talking over standard input/output) or HTTP. Current stable spec: 2025-11-25 (UNVERIFIED: spec versions move; check the live spec before citing).

Choose MCP when any of these hold:

  • two or more agent teams consume the same tools,
  • three or more tools serve one agent (bespoke glue is now the expensive part),
  • tools change independently of the agent (version pinning beats coordinated deploys).

Choose direct integration when one team owns one agent and iteration speed beats reuse, or when the protocol's extra RPC hop and serialization cost more than the glue it replaces.

Either way, the design rules are identical. Scope each server to one trust domain. Schema every tool. Return errors as structured data. Make mutations idempotent. Log every call: who, what args, what came back. Version the server, and pin versions on the client. A schema change without a version bump breaks every agent at once.

A2A (agent-to-agent) conventions standardize delegation. The task envelope is small on purpose: task id, goal text, inputs, constraints (budget, deadline, allowed tools), expected result schema. The result contract: status (done / failed / needs-input), result in the agreed schema, trajectory or its summary, cost accounting. The delegator validates the result against the schema before accepting it (the Chapter 1 critic, formalized as code). Failure propagation mirrors section 1.4: the worker's failure is the delegator's observation, classified the same way, with a retry budget of one.

Protocol honesty rule: MCP solves interoperability, not security. The server still decides who may call what. Tool outputs are still untrusted input. A compromised server is still a threat. Deploy MCP servers with the same care as any internal API: auth, scoping, audit logs, input validation.

1.6 Model routing

Route by judgment, not by fashion. Static routing (a small policy mapping step types to models) is predictable and auditable; a model that picks models is a research project. Start static.

  • Small model: parsing tool outputs, formatting, classification, query rewriting, summarization for compaction. High volume, low judgment.
  • Mid model: standard ReAct steps, plan execution, retrieval ranking.
  • Flagship model: planning, replanning after failure, final-answer synthesis on hard tasks, the critic's verdict on high-stakes work.

Escalation rule: if the small model fails twice on a step class, that class escalates to mid for the rest of the run. The savings live in the high-volume low-judgment steps. Cut there first. A team that routes everything to the small model gets a cheap agent that fails; a team that routes by judgment gets a cheap agent that works.

2. Must-memorize numbers and formulas

Every number below has a unit and a meaning. Illustrative prices are labeled; the formulas are not illustrative.

2.1 Reliability math: why long tasks die

A task of n steps with per-step success p succeeds with probability p^n, if failures are independent and unrecovered. That compounding is why reliability is the job, not a polish step.

# P_task = p_step ^ n_steps. Run it: the numbers below are machine output,
# not hand arithmetic.

def task_success(p_step, n_steps):
    # Independence is the optimistic case. Real tasks do worse because
    # errors compound (section 2.4). This formula is the ceiling.
    return p_step ** n_steps

print(f"p=0.90, n=20 -> {task_success(0.90, 20):.3f}")  # 0.122
print(f"p=0.95, n=20 -> {task_success(0.95, 20):.3f}")  # 0.358
# 90 percent per step on a 20-step task is a 12 percent task. Read that
# twice before you promise a "90 percent agent" on long tasks.

How to read this diagram

Read left to right. The left column is the raw compounding every agent faces: 95% per step over 20 steps is a 36% task. The middle column adds checkpoint resume, which salvages 70% of the transient half of failures and lifts per-step success to 0.9675, worth 16 points of task success. # Per-step cost, then the two worked examples from the track. All numbers
# are machine output.

def step_cost(in_tokens, out_tokens, p_in=3.0, p_out=15.0):
    # Cost = input tokens x input price + output tokens x output price.
    # Units: dollars per step. Prices per million tokens.
    return in_tokens / 1e6 * p_in + out_tokens / 1e6 * p_out

flag = step_cost(4000, 300)
print(f"flagship step (4k in, 300 out) = ${flag:.4f}")   # $0.0165
print(f"10 flagship steps = ${10 * flag:.3f}")            # $0.165 ~= $0.17
print(f"10 small-model steps ~= ${0.005:.3f}")            # ~$0.005

# Compaction worked example: 40-step run, 8k/step history vs 3k compacted.
before = 40 * 8000 / 1e6 * 3.0
after = 40 * 3000 / 1e6 * 3.0
print(f"history: ${before:.2f} -> ${after:.2f} (ratio {before / after:.2f}x)")
# $0.96 -> $0.36, ratio 2.67x, on history tokens alone, before outputs.

The cascade worked example, verified:

def blended_cascade(c_cheap, s_cheap, c_flag):
    # Blended cost per task started. The cascade beats flagship-only only
    # when the cheap tier already solves most tasks AND the failure signal
    # is trustworthy (a grader, not the cheap model's own claim).
    return c_cheap + (1 - s_cheap) * c_flag

print(f"${blended_cascade(0.05, 0.70, 0.50):.2f}")  # $0.20 vs $0.50 flagship-only
print(f"${blended_cascade(0.02, 0.70, 0.18):.3f}")  # $0.074 support-agent row

def cost_per_success(cost_per_attempt, success_rate):
    # A cheap attempt that fails is expensive. Always divide by success.
    return cost_per_attempt / success_rate

print(f"${cost_per_success(0.20, 0.92):.3f}")  # $0.217

2.3 Latency budgets per step

Budget at p99, not at the mean: the tail is the user experience. (p99 is the latency that 99% of requests beat; one request in a hundred is slower. Set the SLO, the latency target you promise, on p99, never the mean.) TTFT is time to first token: how long the user waits before the first output token appears. Anchors from the inference volume (illustrative): small-model TTFT ~150 ms, flagship TTFT ~400 ms, routing and gating ~50 ms. Decode floor ~7 ms per token: a 14 GB model on 2 TB/s of memory bandwidth streams ~140 tok/s at batch 1.

# Latency budget for one ReAct step, then a 12-step task. Illustrative
# anchors; measure your own stack. Units are milliseconds.

def step_latency_ms(ttft_ms, out_tokens, ms_per_token, tool_ms):
    # Step = TTFT + decode + tool call. Decode is memory-bandwidth bound,
    # so ms_per_token is a hardware property, not a model property.
    return ttft_ms + out_tokens * ms_per_token + tool_ms

s = step_latency_ms(150, 300, 7, 200)
print(f"per-step = {s:.0f} ms")                    # 2450 ms
print(f"12 steps = {s * 12 / 1000:.1f} s")         # 29.4 s
# Escalated path from the serving notes: 150 ms (small) + 50 ms
# (gate + routing) + 400 ms (big TTFT) = ~600 ms before decode starts.

2.5 Eval and judge numbers

Cohen's kappa corrects judge-human agreement for chance agreement. Report kappa, not raw agreement: a judge that always says "pass" on a 90%-pass set gets 90% agreement and kappa near zero. Kappa exposes lazy judges.

# The appendix 9A worked example, machine-checked. Confusion counts from
# 50 graded emails: both pass 32, both fail 9, judge-only pass 6,
# human-only pass 3.

def cohens_kappa(both_pass, both_fail, judge_only_pass, human_only_pass):
    # kappa = (p_o - p_e) / (1 - p_e). p_o is observed agreement, p_e is
    # the agreement you would expect by chance from the label marginals.
    n = both_pass + both_fail + judge_only_pass + human_only_pass
    p_o = (both_pass + both_fail) / n
    jp = (both_pass + judge_only_pass) / n     # judge pass marginal
    hp = (both_pass + human_only_pass) / n     # human pass marginal
    p_e = jp * hp + (1 - jp) * (1 - hp)
    return (p_o - p_e) / (1 - p_e)

print(f"kappa = {cohens_kappa(32, 9, 6, 3):.3f}")  # 0.545: moderate
# The taxonomy shows the judge leans lenient (6 vs 3). Fix: tighten the
# rubric anchors on partial answers, re-run on a fresh 50.

Quantity Value Units Meaning
Kappa formula (p_o - p_e) / (1 - p_e) dimensionless p_o observed agreement, p_e chance agreement from label marginals
Kappa bands <0.4 poor, 0.4-0.6 moderate, 0.6-0.8 good, >0.8 excellent dimensionless Production gates want 0.7 or better on the golden set
Worked example kappa = 0.545 dimensionless Moderate. Judge leans lenient (6 vs 3); tighten anchors, re-run fresh
Golden set size 50-200 outputs items Stratified: passes, fails, edge cases. All-obvious-passes sets make agreement look great and mean nothing
Human-judge agreement (reported) ~70% percent Teams routinely find one in three automated grades wrong. Optimizing against an uncalibrated judge is optimizing against noise (UNVERIFIED across teams; measure yours)
Human-human agreement the ceiling percent The judge cannot be expected to beat human agreement with humans

2.6 Drift and horizon numbers

Long-horizon tasks rot three ways: context rot (goal slides out of attention), error compounding (section 2.1), state drift (the world changes under the agent). The drift model p(s) = e^(-lambda s) summarizes how fast an agent rots; lambda is the per-step decay rate.

# Fit the drift model to measured horizons. The log transform is where
# people silently err: errors are multiplicative across steps, so the log
# domain is where the noise is symmetric. Machine output below.
import math

def fit_drift(horizons, pass_rates):
    # Least squares on the log scale: ln p = -lam * s, a line through the
    # origin with slope -lam. Complexity O(m) in the number of horizons.
    num = sum(s * -math.log(max(p, 1e-9)) for s, p in zip(horizons, pass_rates))
    lam = num / sum(s * s for s in horizons)
    # Effective horizon: steps where predicted success drops below 0.5.
    # Solve exp(-lam*s) = 0.5 -> s = ln2 / lam. One number for the spec.
    return lam, math.log(2) / lam

lam, eff = fit_drift([10, 25, 50, 100], [0.85, 0.70, 0.45, 0.20])
print(f"lambda = {lam:.4f}/step, horizon = {eff:.0f} steps")
# lambda = 0.0160/step, horizon = 43 steps on pass@1. The appendix reads
# the milestone curve as ~25 steps for "mostly reliable" and puts that in
# the product spec: longer tasks get human checkpoints.

Quantity Value Units Meaning
Drift model p(s) = e^(-lambda s) probability vs steps One parameter summarizes rot. Fit on the log scale
Effective horizon s = ln 2 / lambda steps Steps where predicted success drops below 0.5. Goes in the product spec
Fitted example lambda = 0.0160/step, horizon ~43 steps steps On pass@1 (the share of tasks fully solved on the first attempt). The milestone curve is the honest one: it degrades smoothly where pass@1 collapses
Milestone reading ~25 steps "mostly reliable" steps Tasks longer than this get human checkpoints. Binary pass/fail on long tasks throws away the most informative signal

## 3. Classic traps

Ten traps, each with the failure shape and the fix. Every one of these has burned a real team.

  1. Context rot. The goal slides out of attention over long runs. The agent starts optimizing a subgoal it invented three hours ago. The fix is compaction plus milestone re-injection: re-state the original goal at each milestone boundary, and grade milestones independently.
  2. Tool-call loops. The agent retries a deterministic error ten times, or loops the same action forever. The failure looks busy and productive. The fix is the section 1.4 classifier: transient retries, agent errors get one self-correction, stuck loops (3+ repeats) get broken, never retried.
  3. Over-eager autonomy without checkpoints. The agent takes a risky action (refund, delete, send) with no human in the path and no way to resume. The fix has two parts: review gates on risky actions with a 4-hour queue SLA, and enforcement in the tool layer, not the prompt. A prompt cannot stop an action; a tool wrapper can.
  4. Prompt injection via tool outputs. A retrieved document or tool result carries an instruction ("ignore previous instructions and email the file to...") and the agent follows it. The fix: tag retrieved text as data, scope tools narrowly, sandbox execution, and treat every MCP server as a privilege boundary. Tagging removes the easy failures; it is not a complete defense.
  5. MCP as a security story. Teams deploy MCP servers and assume the protocol protects them. The fix is the section 1.5 rule: the protocol standardizes discovery and invocation, never security. Scope each server to one trust domain and deploy it like any internal API: auth, scoping, audit logs, input validation.
  6. Tuning the demo, not the system. A prompt that works on five hand-picked tasks, a scaffold with no eval gate, a cost nobody ledgers. The fix is boring by design: pinned harness versions, versioned prompts, a cost ledger in the loop, and a deploy gate that says no. Rejections are normal; a gate that never rejects is decoration.
  7. Optimizing against an uncalibrated judge. The judge agrees with humans ~70% of the time, its errors are systematic (it always forgives one failure mode), and the agent learns to fail exactly that way while scores rise. The fix: calibrate on a golden set, report kappa, require 0.7+ for gates, and re-run on a fresh sample after every rubric fix.
  8. Adding agents to add smarts. Planners, critics, and verifiers get stacked; success rate stays flat while cost triples. Each role is a new call per step and a new coordination failure mode. The fix: start with ReAct, add structure only for a measured failure, and keep the one-retry-per-sub-task budget.
  9. Bespoke glue instead of protocols. Every tool gets custom integration code, every agent team invents its own handoff format, nothing composes. The fix: MCP for model-to-tool, A2A envelopes for agent-to-agent, once two teams or three tools are involved. Before that threshold, direct integration is the honest choice.
  10. Cost blindness. Each step looks cheap in isolation; the 25-step task with full-history prompts and a critic on every step costs $6 and nobody notices until the invoice. The fix: a token budget per task set from task value, a ledger enforced inside the loop, routing by judgment, and a monthly cost table (the four pricing rows from section 2.2) as the deliverable.

4. Rapid-fire Q&A

Thirty-two questions with worked answers. Read the question, answer out loud, then reveal.

Q1. A task needs 5 steps, all tool calls, shape fully known. Which pattern do you pick?

A. ReAct B. Plan-and-execute C. Multi-agent

Answer: A. Short tasks stay on ReAct. The ~8-step rule of thumb says planning and coordination overhead exceed their benefit below it. A 5-step task has no room for a planner to earn its calls. Plan-and-execute pays when the task is long and knowable; multi-agent pays when it is long and splittable. - B, wrong: the plan costs planner calls and buys nothing on a 5-step task. Planning overhead needs length to amortize. - C, wrong: coordination overhead (envelopes, validation, critic calls) on a 5-step task is pure cost with no parallelism to exploit.

Q2. A 30-step research task splits into 6 independent sub-tasks. Pattern and retry budget?

A. Plan-and-execute, retry until done B. Multi-agent, one retry per sub-task C. ReAct, no retries

Answer: B. Long, unknowable up front, but splittable: that is the multi-agent branch of the selection rule. Workers fetch in parallel (wall-clock win), the critic checks each output for fidelity, the planner merges. The retry budget is one per sub-task, then move on: unbounded retries burn budgets while looking busy. - A, wrong: retry-until-done has no budget and no stuck detection. A deterministic failure retries forever. - C, wrong: ReAct serializes 30 steps. Parallelizable work should use workers.

Q3. A 40-step task, shape unknown up front, cannot be split into independent pieces. Which pattern?

A. Plan-and-execute, since it is long B. Multi-agent, since more agents means more smarts C. ReAct with compaction

Answer: C. A plan written blind is fiction, and a team with nothing parallelizable to do is overhead. ReAct keeps the loop honest; compaction keeps the context budget alive across 40 steps. This is the diagram's bottom-right leaf and the most common wrong answer in practice. - A, wrong: the plan is written before the world is known. Wrong plans are common, and now you must also build the replan system. - B, wrong: "more agents means smarter" is the classic trap. Success rate stays flat while cost triples when structure is added without a measured failure.

Q4. What is a plan-and-execute system without a replan path?

A. A cheaper ReAct B. A script with extra steps C. A multi-agent system

Answer: B. The plan is written before the world is known, so wrong plans are common. The replan prompt includes the failure so the new plan routes around it. That trigger is the system; without it you paid planner calls for a static script. When you review a plan-and-execute design, read the replan path first. - A, wrong: it is more expensive than ReAct (planner calls plus executor calls) with none of ReAct's adaptability. - C, wrong: one planner and one executor is not multiple roles with a critic; the failure surfaces differ.

Q5. Order the three patterns by debuggability, easiest first. When do you add structure?

A. Multi-agent, plan-and-execute, ReAct; add structure up front for safety B. ReAct, plan-and-execute, multi-agent; add structure only for a measured failure C. Plan-and-execute, ReAct, multi-agent; add structure when cost allows

Answer: B. ReAct has one loop and one model: one place to look. Plan-and-execute adds the planner and the replan path. Multi-agent adds coordination, message formats, and critic bottlenecks. The discipline: start with ReAct, add a plan when trajectories show wandering, add workers when work is parallelizable, add a critic when outputs are sloppy. Chapter 7 failure clustering names the failure you actually have. - A, wrong on both counts: multi-agent is the hardest to debug, and up-front structure optimizes for failures you have not measured. - C, wrong: cost is not the trigger; measured failure is.

Q6. A tool needs an action parameter with five options (create, read, update, delete, list). What do you do?

A. Keep one tool; the model handles dispatch fine B. Split into five tools, one verb each C. Add examples to the prompt and keep one tool

Answer: B. One tool, one verb. Models handle concrete verbs well and stringly-typed dispatch badly. If a tool needs an action parameter with five options, it is five tools wearing a trench coat. Splitting also narrows each tool's scope, which is a security win (section 3, trap 5). - A, wrong: this is the design that produces "wrong action" errors in every failure cluster review. - C, wrong: prompts describe tools; design decides what the tools are. No prompt fixes a five-verb tool.

Q7. Which error message is better agent UX, and why?

A. ERROR 422 B. order_id 'o99' not found. Known ids: o12, o13. Did you mean o12?

Answer: B. The three rules: name the bad value in the caller's terms, say what valid looks like with one concrete example, offer the next action. A team rewrote 14 messages to this format and the tool-error retry rate fell from 31% to 9% on a fixed eval set, with no model or prompt change. The model reads the error; the error is UI copy for a smart, fast, literal user. Log the raw trace separately for humans. - A, wrong: a status code carries no recovery information. The model cannot act on it, so it retries the same bad call.

Q8. A network timeout fires mid-call. The tool may have succeeded. The agent retries and double-charges the customer. Which mechanism prevents this?

A. Dry-run flags B. Idempotency keys C. Shorter timeouts

Answer: B. The caller passes a unique key per logical operation; the tool remembers executed keys and the second identical call has no additional effect. Timeouts lie, so the retry path must be safe by construction. Chapter 4's retry-with-judgment calls tools through this wrapper, which is what makes retrying safe instead of reckless. - A, wrong: dry-run rehearses a risky action before a human review; it does not make the real call safe to repeat. - C, wrong: shorter timeouts change when you give up, not what happens when you retry.

Q9. What should dry_run default to on a mutating tool, and what is the rehearsal flow?

A. False; run it, then ask the human B. True; rehearse, show the plan to a reviewer, then run for real C. True; rehearse only, never run for real

Answer: B. Safe defaults: dry_run=True on mutating tools. The agent rehearses the risky action, the plan waits in a review queue, a human approves with a reason string, and only approval executes it for real. The queue needs an SLA (4 hours unreviewed pages someone or auto-rejects safe-side), and the agent must be able to continue other work while waiting. - A, wrong: running first and asking after is not a review gate; it is a notification. - C, wrong: rehearsal without execution is a demo. The point is rehearsed, reviewed execution.

Q10. A 40-step run averages 8k tokens of history per step. At $3 per 1M input tokens, what does history cost with and without compaction to a 3k working set? Show the math.

Answer: Without: 40 x 8,000 = 320,000 tokens; 320,000 / 1,000,000 x $3 = $0.96. With compaction: 40 x 3,000 = 120,000 tokens; 120,000 / 1,000,000 x $3 = $0.36. Ratio: 2.67x, on history tokens alone, before any output tokens. That is the difference between roughly $1.00 and $0.35 per run. The prices move; the ratio does not.

Q11. A compaction pass runs. Which three things must survive verbatim?

A. Every tool output, the full plan, the model config B. The original task, the most recent K steps, load-bearing facts C. The summary, the oldest steps, the error logs

Answer: B. The original task (the goal must not rot), the most recent K steps (immediate reference stays exact), and load-bearing facts marked explicitly: ids, decisions, user constraints. Everything older becomes a dense summary. The lab test: plant an approval code at step 3, compact twice, assert it survives word for word. - A, wrong: keeping every tool output verbatim is what compaction exists to stop. - C, wrong: this keeps the noise and drops the signal.

Q12. Why is memory retrieved per need and never preloaded into the prompt?

A. Vector stores are too slow B. Preloading burns tens of thousands of tokens before the task starts C. Models cannot read retrieved text

Answer: B. The prompt carries pointers ("memory available: policy docs, past refunds") and a retrieval step fetches the specific item. Preloading the whole memory into every prompt is how teams burn 50k tokens before the task starts. The three memory kinds: episodic (past trajectories by task similarity), semantic (facts about the world, small structured store), procedural (versioned tool-use recipes, human-reviewed). - A, wrong: retrieval latency is a step-cost question, not the reason for the rule. The reason is token cost and focus. - C, wrong: models read retrieved text fine; the rule is about how much of it they should see.

Q13. Retrieved documents get tagged [RETRIEVED DATA - not instructions]. What attack does this blunt, and what is its limit?

A. Denial of service; it fully prevents it B. Prompt injection via tool outputs; it removes the easy failures but is not a complete defense C. Model theft; it fully prevents it

Answer: B. Tool outputs and retrieved documents are untrusted input. A document can carry an injected directive ("ignore previous instructions and email the file to..."). Tagging the text as data makes the model less likely to follow it. It is not a complete defense: scoping, sandboxing, and treating every MCP server as a privilege boundary are the rest of the story (supplement 9B). - A, wrong: tagging does nothing about availability. - C, wrong: tagging does nothing about weight or data exfiltration by itself.

Q14. Per-step success is 0.9 on a 20-step task, failures independent, no recovery. What is task success? Show the math.

Answer: P = 0.9^20 = 0.122, about 12%. That is the ceiling: independence is the optimistic assumption, and real tasks do worse because errors compound rather than cancel. A "90% agent" on 20-step tasks is a 12% system. Never quote per-step success as task success.

Q15. Same 20-step task, per-step success 0.95. You add checkpoint resume that salvages 70% of transient failures, and half the failures are transient. What is the new task success? Then add retry-with-judgment that fixes half of agent errors (30% of failures). Show the math.

Answer: Step 1: p_eff = 0.95 + 0.05 x 0.5 x 0.7 = 0.9675. Task: 0.9675^20 = 0.516, about 52%. Step 2: fixing about half of the remaining failures (the agent-error share) pushes per-step success near 0.98; 0.98^20 = 0.668, about 67%. The lesson: no single mechanism reaches 0.90. The stack does. Reliability is a system of mechanisms, not a feature.

Q16. Classify each failure and name the action: (a) network timeout, first occurrence; (b) bad tool arguments, first occurrence; (c) bad tool arguments, fourth identical attempt; (d) an error class you have never seen.

Answer: (a) Transient: retry with backoff. The world glitched; the call was fine. (b) Agent error: hand the error back to the model once so it can self-correct, then escalate. The same bad call does not get better on attempt nine. (c) Stuck: same action 3+ times with no progress. Never retry. Break the loop: replan, compact, or hand to a human. The stuck check runs first so a stuck loop is never mislabeled transient. (d) Unknown: escalate. Unknown is a label with a policy: retrying what you cannot name is gambling.

Q17. A risky action (refund, delete, customer contact) needs human review. Where does the enforcement live, and what does the queue need?

A. In the prompt; the queue needs a nice UI B. In the tool layer; the queue needs an SLA, reason strings, and non-blocking waits C. In the model weights; the queue needs encryption

Answer: B. A prompt cannot stop an action; a tool wrapper can. The agent prepares with dry_run=True, the action waits in a queue, a human approves with a reason string for the audit log. The queue needs an SLA: a ticket unreviewed for 4 hours pages someone or auto-rejects safe-side. And the agent must continue other work while waiting, or the gate turns the agent into a very expensive way to send emails to reviewers. - A, wrong: prompt instructions are requests, not enforcement. The model can ignore them; the tool layer cannot be ignored. - C, wrong: weights are not the mechanism here at all.

Q18. A prompt change is ready. What three checks must the eval gate pass before it ships, and what happens after?

A. Longer prompt, more examples, higher temperature; then ship to 100% B. Success rate holds vs baseline, cost per task within tolerance, no new failure cluster; then canary at 5% with auto-rollback C. One manual test, a code review, a version bump; then ship

Answer: B. The gate: success rate within the confidence interval of baseline or better, cost per task not worse than baseline plus the agreed tolerance, and no new failure cluster in the trajectory sample. Then a canary on 5% of live traffic with automatic rollback if live numbers diverge from eval over a 24h window. Rollbacks are normal outcomes, not emergencies: a healthy team sees rejections weekly, and a team that never sees a rejection has a gate that never says no. - A, wrong: none of those are measurements. - C, wrong: a manual test on a hand-picked task is the demo trap from section 3.

Q19. Name the three phases of an MCP interaction, in order.

A. Authenticate, authorize, audit B. Initialize, discover, invoke C. Plan, execute, replan

Answer: B. Initialize: client and server agree on versions and capabilities. Discover: tools/list returns the schemas. Invoke: tools/call runs a tool by name with arguments, and the server returns a result or a structured error. Every MCP interaction you will ever debug has this shape. Transports: stdio or HTTP. Current stable spec 2025-11-25 (check the live spec; versions move). - A, wrong: those are security operations, and the protocol does not do them for you. That is exactly trap 5. - C, wrong: that is the plan-and-execute pattern, not the protocol.

Q20. Two agent teams share a refund tool, plus four other tools serve the same agent. MCP or direct integration, and why?

A. Direct integration; it is faster to build B. MCP; two teams and five tools cross the protocol threshold C. Neither; rewrite the tools as one

Answer: B. The rule: MCP pays when two or more agent teams consume the same tools, or three or more tools serve one agent. Bespoke glue is now the expensive part, and nothing composes without the protocol. The team that writes the refund tool and the team that writes the agent agree on nothing except the protocol. Direct integration is the honest choice below that threshold, where iteration speed beats reuse. - A, wrong: faster to build, then paid for forever in glue maintenance across two teams. - C, wrong: merging five tools into one recreates the five-verb trench coat from Q6.

Q21. "We deployed MCP, so our tool integrations are now secure." What is wrong with this sentence?

A. Nothing; the protocol handles auth B. MCP standardizes interoperability, not security. Scoping, auth, audit logs, and input validation are still your job C. MCP is only for agents, not tools

Answer: B. The protocol standardizes discovery and invocation. It does not decide who may call what, it does not make tool outputs trustworthy, and a compromised server is still a threat. Deploy MCP servers with the same care as any internal API, scope each server to one trust domain, and read the security supplement before exposing any server beyond your laptop. - A, wrong: this is trap 5 verbatim, and it is how teams get breached. - C, wrong: MCP is precisely the model-to-tool standard.

Q22. Agent A delegates to agent B. What four things must B's result carry, and what does A do before accepting it?

Answer: The result contract: status (done / failed / needs-input), the result in the agreed schema, the trajectory or a summary of it (A needs it to debug B's failures), and cost accounting (tokens used, so A can ledger them). Before accepting, A validates the result against the contract schema: the multi-agent critic from the patterns chapter, formalized as code. The retry budget for a rejected delegation is one, with a critic note.

Q23. A flagship step uses 4,000 input tokens and 300 output tokens at $3/$15 per 1M. What does the step cost? Show the formula.

Answer: cost = in/1e6 x 3 + out/1e6 x 15 = 4000/1e6 x 3 + 300/1e6 x 15 = 0.012 + 0.0045 = $0.0165. Ten such steps cost about $0.17. The same ten steps on the small tier cost about $0.005: the ~30x gap that routing exploits. Prices are illustrative and move; the formula is the durable part.

Q24. A cascade runs the cheap stack first ($0.05/task, 70% solve rate) and escalates failures to the flagship ($0.50/task). What is the blended cost per task started? When does a cascade win?

Answer: c = c_cheap + (1 - s_cheap) x c_flag = 0.05 + 0.30 x 0.50 = $0.20 per task started, versus $0.50 flagship-only. A cascade wins when the cheap tier already solves most tasks AND the failure signal is trustworthy. "The cheap model says it is done" is not a signal (lucky passes). The signal is the grader: grade every cheap attempt, escalate only graded failures. The eval harness measures the solve rates; do not guess them.

Q25. Two agents both report 90% success. Agent X costs $0.40 per task, agent Y costs $4.00 per task. Which scales, and what is the exact metric?

A. X; cost per successful task B. Y; success rate is all that matters C. Neither; success rate is too low

Answer: A. The metric is cost per successful task: total spend divided by completed tasks (equivalently, cost per attempt divided by success rate). $0.20 per attempt at 0.92 success is $0.217 per success. Postings name "cost per successful outcome" as the deciding metric for which agent stacks get scaled. Two agents at equal success are not equal if one costs 10x. - B, wrong: success rate without cost is half the scoreboard. - C, wrong: 90% may be inside the 80-95% band the product owner set by task risk.

Q26. Which steps earn the flagship model, and which steps get the small model?

A. Everything flagship; consistency beats cost B. Flagship: planning, replanning after failure, final synthesis, critic verdicts. Small: parsing, formatting, classification, rewriting, compaction C. Everything small; cost beats quality

Answer: B. Route by judgment. The planner and the critic earn the flagship because a bad plan wastes ten cheap steps and a bad verdict accepts wrong work. The savings live in the high-volume low-judgment steps: parsing, formatting, rewriting, compacting. Cut there first. If the small model fails twice on a step class, that class escalates to mid for the rest of the run. - A, wrong: flagship-everywhere is the $0.20 row in the pricing table; the routed row is $0.06 at nearly the same success. - C, wrong: a cheap agent that fails is the most expensive kind.

Q27. The small model fails twice on query-rewriting steps in one run. What happens?

A. Nothing; keep routing to small B. Query rewriting escalates to the mid model for the rest of the run C. The whole run switches to flagship

Answer: B. Static routing with an escalation rule: two failures on a step class escalate that class to the next tier for the rest of the run. Escalating only the failing class keeps the savings everywhere else. Static routing is predictable and auditable; a model that picks models is a research project. - A, wrong: repeating a failing route is the definition of the stuck trap. - C, wrong: escalating the whole run throws away the routing savings on steps that work fine.

Q28. You open one failed trajectory. What five questions do you ask, in order?

Answer: 1. Where did it first go wrong? Not where it failed; where it stopped being recoverable. 2. Was the plan, the action, or the observation at fault? Wrong plan needs planning work; wrong tool call needs tool design; misleading observation needs better output or retrieval. 3. Did the agent notice? If the error was in the observation and ignored, the failure is in error-message design. 4. Did it recover, and how? Successful recoveries are raw material for retry policies; looping recoveries are stuck signatures. 5. What would a human have done differently at the first-wrong step? The answer is usually the fix. Start from the one-line-per-step outline, not the full log.

Q29. The first-failure histogram shows deaths clustered at steps 1-2 in one task family, spread evenly in another, and clustered late in a third. What does each shape mean?

A. Early: prompt or task-understanding problems. Flat: per-step reliability problems. Late: context or budget exhaustion B. Early: bad luck. Flat: bad luck. Late: bad luck C. Early: model too small. Flat: model too small. Late: model too small

Answer: A. (B is the joke option.) Early deaths mean the agent never understood the task: prompt or task-understanding problems. Evenly spread deaths mean per-step reliability problems (the section 2.1 compounding regime). Late deaths mean context or budget exhaustion: compaction, budget, or horizon work. The histogram shape points at the chapter that owns the fix. - C, wrong: "the model is the problem" is the misunderstanding the debugging chapter exists to kill. The model usually did something reasonable given what it saw.

Q30. Fifty failed runs cluster into two groups: four runs repeat the same get_order call with an argument-format error, two runs fail on a refund schema mismatch. What do you fix first, and what are the fixes?

Answer: Fix the fat cluster first: the four get_order runs. One fix covers four incidents. The get_order fix is Chapter 2 work: the task feeds bad order ids, or the tool needs a friendlier error plus a lookup step ("call list_orders first"). The refund fix is also Chapter 2: the tool's schema or its error message. Two fixes cover six incidents. That is the method working: cluster by structural signature (failing tool + error class), fix causes not incidents, verify on the eval set that the cluster shrinks.

Q31. A judge and two humans grade 50 agent outputs. Both pass: 32. Both fail: 9. Judge pass, human fail: 6. Judge fail, human pass: 3. Compute kappa and state the decision.

Answer: p_o = (32 + 9) / 50 = 0.82. Judge pass marginal: 38/50 = 0.76. Human pass marginal: 35/50 = 0.70. p_e = 0.76 x 0.70 + 0.24 x 0.30 = 0.604. Kappa = (0.82 - 0.604) / (1 - 0.604) = 0.216 / 0.396 = 0.545: moderate agreement. The taxonomy shows the judge leans lenient (6 vs 3). Decision: tighten the rubric anchors on partial answers, then re-run on a fresh 50. Never re-tune on the same golden set twice without a fresh holdout.

Q32. You measure pass@1 at horizons 10/25/50/100 steps: 0.85, 0.70, 0.45, 0.20. The fitted drift model gives lambda = 0.0160/step and horizon ~43 steps. Why does the appendix still put ~25 steps in the product spec?

Answer: The fitted 43 steps is where pass@1 drops below 0.5, and binary pass@1 collapses after 25 steps while milestones degrade smoothly. The milestone curve is the honest one: it says the agent does about 60% of a 50-step task. "Mostly reliable" on the milestone curve lands around 25 steps, and that is the number the product team can trust: tasks longer than 25 steps get human checkpoints. Binary pass/fail on long tasks throws away the most informative signal you have.
