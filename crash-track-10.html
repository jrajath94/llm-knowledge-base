Crash Pack: Backend and Systems for the AI Platform

This volume is a high-density reference for the backend or systems engineer who works next to AI models rather than inside them. The research teams train and tune the models. You own the serving fleet, the queues, the APIs, the storage, and the dashboards that page you. This pack compresses the platform half of the curriculum into five parts: decision rules you apply under time pressure, numbers and formulas worth memorizing, traps that have caused real outages, 26 self-test drills with worked answers, and a one-page cheat sheet.

Figure C.1. The territory. Models sit at the center, but a working AI product is mostly platform: compute, serving, queues, storage, APIs, and observability. This pack covers the platform decisions.

Key takeaways

  • Six decision rules cover most platform calls: quorum sizing, consistency selection, queue vs stream, batch vs micro-batch, cache sizing, GPU fleet sizing.
  • Seven formulas carry the math: Little's Law, M/M/1 waits, HNSW parameters, KV-cache bytes, 2 FLOP per token, burn rate, idempotency patterns.
  • Five traps cause most outages: split-brain without fencing, exactly-once illusions, cache stampedes, p99 confusion, silent queue backlogs.
  • Every code sample in this volume was executed during writing. Expected outputs sit in comments next to the prints that produce them.

How to use this volume

Read Part 1 and Part 2 straight through once. Work every drill in Part 4 with the answers covered, out loud, until the numbers come without pausing. Keep Part 5 open during design work. Revisit Part 3 after your first on-call rotation: the traps read differently once you have been paged.

Part 1. Decision rules

A decision rule is a test you can run in under a minute that picks the design. Each rule below names its inputs, its formula or threshold, and what changes the answer.

1.1 Quorum sizing

Replication keeps copies of data on N machines. A write needs W acknowledgments. A read asks R replicas. The rule:

W + R > N: every read overlaps every write, so reads see the latest write.

That overlap is the whole trick. With N = 3, W = 2, R = 2, any read touches at least one replica the write touched, because 2 + 2 > 3. Drop to W = 1, R = 1 and a write that lands on replica A is invisible to a read that hits B and C.

QUORUM OVERLAP (N=3, W=2, R=2)

  Write touches:   [A] [B]  .
  Read touches:     .  [B] [C]
                          ^
  B is in both sets, so the read sees the write.
  2 + 2 > 3 guarantees overlap for any choice of 2.

How to read this diagram

  1. Each row is a set of replicas. Brackets mark the replicas the operation contacts.
  2. The caret marks replica B, which sits in both sets. That shared replica carries the newest write stamp.
  3. Because any 2 of 3 replicas share at least one member, no read can miss a completed write. The arithmetic does the guaranteeing, not luck.

The second half of the rule is availability: to survive f failed replicas, you need W <= N - f and R <= N - f. The standard picks:

N W R Survives Reads see writes? Use when
3 2 2 1 failure Yes Default for config, metadata, model registry versions
3 1 3 1 failure for writes Yes Write-heavy, reads can afford to ask everyone
3 3 1 1 failure for reads Yes Read-heavy, writes can afford to wait
3 1 1 2 failures No Caches and scratch data where staleness is fine
5 3 3 2 failures Yes Control planes that must survive a rack loss 

# WHAT: the quorum rule as a check you can call in a design review.
# WHY:  W + R > N guarantees every read overlaps every write, so a
#       read sees the latest write. This is the math behind the rule.
# WHAT BREAKS: picking W and R for speed (W=1, R=1) and silently
#       giving up read-your-write. Fast reads that lie are a bug.

def quorum_ok(n, w, r):
    # WHAT: True when any read overlaps any write (linearizable reads).
    return w + r > n


def survives(n, w, r, failures):
    # WHAT: True when reads and writes still find enough live replicas.
    return w <= n - failures and r <= n - failures


# Balanced 3-copy store: consistent, survives 1 failure.
print(quorum_ok(3, 2, 2), survives(3, 2, 2, 1))      # -> True True
# Write-fast 3-copy store: consistent reads die after 1 failure.
print(quorum_ok(3, 1, 3), survives(3, 1, 3, 1))      # -> True False
# Fast both ways: no overlap, reads can return stale data.
print(quorum_ok(3, 1, 1), survives(3, 1, 1, 1))      # -> False True
# N=5 tolerating 2 failures with strong reads.
print(quorum_ok(5, 3, 3), survives(5, 3, 3, 2))      # -> True True

Decision procedure: start from the failure budget (how many replicas may die), then pick the smallest W and R that satisfy both the overlap rule and the survival rule. Smaller quorums are faster; the rules tell you how small you may go.

1.2 Consistency model selection

Not every dataset needs the strongest guarantee. Stronger consistency costs latency and availability, so pick the weakest model that keeps the product correct.

Model Guarantee Price Use for
Linearizable Reads see the latest completed write, with a real-time order Quorum on every op, slowest Leader election, config, model registry versions, billing counters
Sequential / causal Everyone sees updates in the same order (or cause before effect) Lighter than linearizable Chat threads, activity feeds, agent action logs
Eventual Replicas converge if writes stop; reads may be stale Cheapest, most available Training feature snapshots, embedding caches, analytics
Read-committed snapshot Reads see a consistent point in time One coordinator Offline eval datasets, billing reports

The test: ask what breaks if a read is 5 seconds stale. If the answer is "money moves wrong" or "two leaders act at once," you need linearizable. If the answer is "a user sees a slightly old feed," eventual is fine and much cheaper. For the AI platform in particular: model artifact versions and rollout config want linearizable; the feature store's online path usually takes tunable quorums (W + R > N on hot keys); training data wants immutable snapshots, not live consistency at all.

1.3 Queue vs stream

A queue delivers each message to one consumer and deletes it on acknowledgment. A stream (partitioned log) appends messages durably; each consumer tracks its own offset and can replay history. The decision:

  • Need replay, multiple independent consumers, or per-key ordering? Use a stream (Kafka, Kinesis, Pulsar).
  • Need simple work distribution where each task runs once and nobody replays? Use a queue (SQS, Celery, Cloud Tasks).
  • Fanning out one event to 6 consumers? A stream does it with one topic; a queue needs 6 queues or a pub/sub layer you now operate.

QUEUE (each message -> one worker)

  producer -> [msg1][msg2][msg3] -> worker A gets msg1
                                     worker B gets msg2
  ack deletes the message. No replay.

STREAM (append-only log, per-consumer offsets)

  producer -> log: [e1][e2][e3][e4] ...
                       ^           ^
                 consumer X     consumer Y
                 (offset 2)     (offset 4)
  Each consumer moves its own offset. Rewind = replay.

Streams cost more to operate (partitions, retention, consumer-group rebalances) and pay back when more than one team reads the same events. A training-data pipeline and a live monitoring consumer reading the same request log is the classic stream-shaped workload.

1.4 Batch vs micro-batch

Match the pipeline shape to the freshness contract. Ask one question: how stale may the output be?

  • "Yesterday's data is fine": batch. Nightly jobs over the full dataset. Cheapest per event, simplest to reason about, easiest to re-run.
  • "The last few seconds": streaming, per-event processing. Most expensive per event, hardest to get right (late data, out-of-order events).
  • Everything between: micro-batch. Streaming cut into small batches of seconds to minutes. It reuses batch logic with tolerable latency, which is why most "streaming" ML pipelines are really micro-batch.

Cost per event rises from batch to micro-batch to streaming. Complexity rises faster than cost. A nightly embedding job over 10M documents is batch. A feature that must reflect the last 5 minutes of user behavior is streaming or tight micro-batch. Do not pay streaming prices for a batch freshness contract.

1.5 Cache sizing with Little's Law

A cache has two sizing questions: how many entries, and how long each lives.

How many entries. Size the hot path with Little's Law: capacity = service rate x maximum acceptable wait. A downstream serving 100 requests per second with a 2-second deadline gets a queue bound of 200; everything past it is rejected fast (429 or 503) instead of queued slow. The same arithmetic sizes connection pools, worker counts, and GPU batch slots.

# WHAT: Little's Law, L = arrival_rate * time_in_system.
# WHY:  it turns two measurable numbers (arrival rate, service time)
#       into the one number you must provision (concurrent slots).
# WHAT BREAKS: it assumes steady state. Bursts need burst math
#       (see 3.5, silent queue backlogs), not the average.

def little_slots(arrival_per_s, service_time_s):
    # WHAT: average concurrent jobs in the system. Units: jobs.
    return arrival_per_s * service_time_s


def queue_capacity(service_per_s, max_wait_s):
    # WHAT: bound for a queue with a latency deadline. Units: jobs.
    # WHY:  capacity = rate * wait; past this, reject fast (429/503)
    #       instead of queueing slow.
    return service_per_s * max_wait_s


# 120 req/s, each holding a GPU slot 1.5 s (prefill + decode).
print("GPU slots:", little_slots(120, 1.5))            # -> 180.0
# Bounded queue: 100 req/s service, 2 s deadline.
print("queue bound:", queue_capacity(100, 2))           # -> 200
# Cache twin: 40k reads/s through a 250 ms refresh window.
print("inflight allowance:", little_slots(40000, 0.25)) # -> 10000.0

How long entries live. The TTL is a freshness contract, not a tuning knob. If the product tolerates 5-minute-old embeddings, the TTL is 5 minutes. Two refinements: jitter the TTLs, and serve stale-while-revalidate for hot keys. A fixed 5-minute TTL on every key expires everything at once and stampedes the backend. Spread expiry over 4 to 6 minutes instead. Stale-while-revalidate returns the old value instantly and refreshes in the background.

How big in bytes. Measure the hit-ratio curve: plot hit ratio against cache size and find the knee where more memory stops buying hits. Size slightly past the knee. Size for the peak working set, not the average: caches fail at peak.

1.6 GPU fleet sizing

Serving-fleet capacity is one formula with three inputs you must measure, not guess:

GPUs = ceil( Q x (T_in + T_out) / (S x rho) ) + spares

  • Q: requests per second (demand).
  • T_in + T_out: average prompt plus completion tokens per request.
  • S: tokens per second one GPU sustains at the target batch size. Measure this on your fleet; a brochure number sizes a fleet that falls over on Monday.
  • rho: target utilization, 0.7. Section 2.2 shows why.
  • spares: at least one per failure domain, so a rack loss does not take the SLO with it.

# WHAT: GPU fleet sizing from demand, supply, and a policy.
# WHY:  capacity reviews need one number with named inputs; this is it.
# WHAT BREAKS: S (tokens/s per GPU) must be MEASURED at the target
#       batch and context mix. A brochure number sizes a fleet that
#       falls over on Monday.

import math


def gpu_fleet(q_per_s, t_in, t_out, tokens_per_s_per_gpu,
              target_util=0.7, spares=1):
    # WHAT: ceil(demand / (supply * util)) + spares. Units: GPUs.
    demand = q_per_s * (t_in + t_out)      # tokens/s the fleet must emit
    usable = tokens_per_s_per_gpu * target_util
    return math.ceil(demand / usable) + spares


# 40 req/s, 2k in / 500 out, 900 tok/s per GPU measured, util 0.7.
print("GPUs:", gpu_fleet(40, 2000, 500, 900))   # -> 160
# Same demand at util 0.9 needs 125 GPUs, but the M/M/1 wait at
# 0.9 is 9x service time versus 2.3x at 0.7. The extra 35 GPUs
# buy the latency SLO. That tradeoff is the capacity conversation.
print("GPUs at 0.9:", gpu_fleet(40, 2000, 500, 900, target_util=0.9))

Key takeaways

  • Quorums: W + R > N for correct reads; W, R <= N - f to survive f failures.
  • Consistency: weakest model that keeps the product correct; money and leadership need linearizable.
  • Queue for work distribution, stream for replay and fan-out.
  • Freshness contract picks batch, micro-batch, or streaming. Do not pay streaming prices for batch freshness.
  • Little's Law sizes queues, pools, and GPU slots: capacity = rate x wait.
  • GPU fleet = ceil(demand / (supply x 0.7)) + spares, with measured supply.

Part 2. Must-memorize numbers and formulas

Each entry gives the formula, its units, what it means in plain terms, and a worked number. These are the ones worth carrying in your head.

2.1 Little's Law: L = λW

  • Formula: L = λ x W.
  • Units: jobs = (jobs/second) x seconds.
  • Meaning: the average number of jobs inside a system equals the arrival rate times the average time each job spends inside. It holds for any steady-state system: queues, thread pools, GPU batch slots, checkout lines.
  • Worked: 120 requests/s x 1.5 s per request = 180 concurrent slots. With 8 slots per GPU (batch 8), that is 23 GPUs before headroom.
  • Boundary: steady state only. During a burst, arrivals exceed service and the queue grows without bound; size for the burst (3.5), not the average.

2.2 M/M/1 wait times: ρ/(μ(1-ρ))

  • Formula: mean queue wait = ρ / (μ x (1 - ρ)), in seconds. ρ is utilization (λ/μ, dimensionless, 0 to 1). μ is the service rate in jobs/second.
  • Meaning: with random arrivals and random service times, the wait before service starts explodes as the server fills. The last 10 percent of utilization costs roughly 10x the latency.
  • Worked (100 ms mean service time, from the verified run below):
Utilization ρ Mean queue wait As multiple of service
0.50 100 ms 1x
0.80 400 ms 4x
0.90 900 ms 9x
0.95 1900 ms 19x
  • Rule: target 60 to 75 percent utilization in production; treat 85 percent as an incident. Real traffic is burstier than the Poisson arrivals this model assumes, so treat these waits as optimistic lower bounds.

# WHAT: M/M/1 mean queue wait: rho / (mu * (1 - rho)), in seconds.
# WHY:  this one curve explains why fleets target ~70% utilization:
#       the wait explodes as rho approaches 1. Textbook result.
# WHAT BREAKS: real arrivals are burstier than Poisson, so this is
#       a LOWER bound. Budget above it, never below.

def mm1_wait_s(rho, service_time_s):
    # WHAT: mean time a job waits before service starts. Units: seconds.
    mu = 1.0 / service_time_s
    return rho / (mu * (1.0 - rho))


svc = 0.100  # 100 ms mean service time
for rho in (0.5, 0.8, 0.9, 0.95):
    w = mm1_wait_s(rho, svc)
    print(f"rho={rho:.2f}: mean queue wait {w*1000:6.1f} ms "
          f"= {w/svc:4.1f}x service time")
# Verified output:
# rho=0.50: mean queue wait  100.0 ms =  1.0x service time
# rho=0.80: mean queue wait  400.0 ms =  4.0x service time
# rho=0.90: mean queue wait  900.0 ms =  9.0x service time
# rho=0.95: mean queue wait 1900.0 ms = 19.0x service time

2.3 HNSW recall parameters

HNSW (hierarchical navigable small world) is the standard approximate nearest-neighbor index for vector search. It organizes vectors in layered graphs: cheap greedy hops on the upper layers find the right neighborhood, then a wide beam search on the bottom layer collects candidates. Three knobs matter:

  • M (typical 16): max edges per node per layer. Sets graph connectivity and memory. Higher M helps recall at high dimensions and costs memory.
  • ef_construction (typical 200): beam width at build time. Higher is slower to build, better graph quality.
  • ef / ef_search (typical 50 to 200): beam width at query time. This is the live recall knob: raise it until recall@k hits the target, latency grows roughly linearly with it.

The tuning loop: measure recall@k against brute force on a sample of real queries. Start ef at 50. Double until recall@k >= 0.95 or the latency budget runs out. If you run out of budget first, the answer is sharding or quantization, not a bigger ef.

Memory rule of thumb: vectors cost dim x 4 bytes each (FP32); the graph costs about M x 2 edges x 4 bytes per node. Worked: 1M vectors, dim 768, M = 16 gives 1M x 768 x 4 = 3.07 GB for vectors plus 1M x 16 x 2 x 4 = 128 MB for the graph.

Two facts worth memorizing: HNSW turns search from O(N) into roughly O(log N) per query, and below about 100k vectors brute force in memory is usually simpler and has perfect recall.

2.4 KV-cache math: 2 x layers x hidden x bytes

During generation the model caches the keys and values of every previous token so it does not recompute them. The cache lives in GPU memory next to the weights and grows with context length and batch size:

bytes per token = 2 (K and V) x layers x hidden_dim x bytes_per_value

For an 8B model (32 layers, hidden 4096, FP16): 2 x 32 x 4096 x 2 = 524,288 bytes, about 0.5 MB per token. An 8k context needs about 4.3 GB of cache. A batch of 32 such requests needs about 137 GB, more than an 80 GB GPU holds, before counting the 16 GB of weights. Long contexts, not model size, are usually what runs a serving fleet out of memory.

Caveat: the formula assumes standard multi-head attention. Grouped-query attention stores fewer key/value heads and shrinks the cache; check the model card before sizing.

2.5 The 2-FLOP-per-token rule

A forward pass costs about 2 floating-point operations per parameter per token: one multiply and one add per weight. For an 8B model that is 16 GFLOP per token. Uses:

  • Compute-bound time floor: 16 GFLOP / 300 TFLOPs effective = about 53 microseconds per token. Real decoding is memory-bound (streaming weights dominates), so treat this as a floor, not a promise.
  • Prefill estimates: prompt processing is closer to compute-bound, so the rule gives usable throughput estimates there.
  • Quantization: halving the bytes per parameter (FP16 to INT8 to INT4) halves weight memory and roughly doubles memory-bound throughput, at the cost of accuracy cliffs you must version and test.

# WHAT: the ML-literacy formulas a systems engineer reaches for.
# WHY:  capacity reviews for serving fleets reduce to these three:
#       memory per token, compute per token, and the weights.
# WHAT BREAKS: the KV-cache line assumes standard multi-head
#       attention. Grouped-query attention stores fewer KV heads,
#       which shrinks the cache; check the model card.

def kv_cache_bytes_per_token(layers, hidden, bytes_per_value=2.0):
    # WHAT: 2 (K,V) x layers x hidden x bytes. Units: bytes/token.
    return 2 * layers * hidden * bytes_per_value


def forward_flops_per_token(params):
    # WHAT: ~2 FLOP per parameter per token (one multiply-add).
    return 2 * params


def model_bytes(params, bytes_per_param=2.0):
    # WHAT: weight memory. FP16=2.0, INT8=1.0, INT4=0.5 bytes/param.
    return params * bytes_per_param


# 8B model, 32 layers, 4096 hidden, FP16.
bpt = kv_cache_bytes_per_token(32, 4096)
print(f"KV cache: {bpt/1e6:.2f} MB/token")          # -> 0.52 MB/token
print(f"8k context: {bpt*8192/1e9:.1f} GB")         # -> 4.3 GB
print(f"weights FP16: {model_bytes(8e9)/1e9:.0f} GB")  # -> 16 GB
print(f"weights INT4: {model_bytes(8e9, 0.5)/1e9:.1f} GB")  # -> 4.0 GB
print(f"forward: {forward_flops_per_token(8e9)/1e9:.0f} GFLOP/token")  # -> 16

2.6 Burn-rate alerting

Alert on how fast you are consuming your error budget, not on raw thresholds. "Alert me when latency exceeds 2 seconds" pages you for one slow request at 3am and misses a real degradation holding 30 percent of requests at 1.9 seconds.

  • Burn rate = observed error ratio / budgeted error ratio. A 99.9 percent SLO allows 0.1 percent errors; errors running at exactly 0.1 percent burn at 1x.
  • Page tier: 10x burn over 5 minutes. At 10x, the monthly budget is gone in 3 days. That pages.
  • Ticket tier: 2x burn over 1 hour. At 2x, the budget lasts 15 days. That tickets, no page.
  • Two alerts, two urgencies, zero 3am pages for single blips.

# WHAT: burn-rate math for SLO alerting.
# WHY:  thresholds page on single blips and miss slow leaks; burn rate
#       ties the alert to the error budget, so urgency is automatic.
# WHAT BREAKS: a burn-rate alert needs a window. Too short (1 min)
#       pages on noise; too long (6 h) pages after the budget is gone.

def burn_rate(observed_error_ratio, slo_error_budget_ratio):
    # WHAT: budget consumption speed. 1.0 = exactly on budget.
    #       Units: dimensionless multiple.
    return observed_error_ratio / slo_error_budget_ratio


def budget_days_left(burn, window_days=30.0):
    # WHAT: days until the budget is gone at this burn.
    return window_days / burn if burn > 0 else float("inf")


SLO = 0.001  # 99.9% SLO allows 0.1% errors
# Page tier: 1% errors sustained 5 min -> burn 10x.
b = burn_rate(0.01, SLO)
print(f"burn {b:.0f}x -> budget gone in {budget_days_left(b):.1f} days")
# -> burn 10x -> budget gone in 3.0 days. Pages.
# Ticket tier: 0.2% errors over an hour -> burn 2x.
b = burn_rate(0.002, SLO)
print(f"burn {b:.0f}x -> budget gone in {budget_days_left(b):.1f} days")
# -> burn 2x -> budget gone in 15.0 days. Tickets, no page.

Nines table, worth memorizing (30-day month = 43,200 minutes):

SLO Allowed downtime/month
99% 7.2 hours
99.9% 43 minutes
99.99% 4.3 minutes
99.999% 26 seconds

2.7 Idempotency patterns

Networks fail mid-request, so clients retry, and the server cannot tell a retry from a new request. The fix is an idempotency key: a client-generated unique token sent with the request. The server keeps a table of key to result. A repeated key returns the stored result instead of running the job again.

Three details matter:

  1. Key scope: one key per logical operation, generated by the client before the first attempt, reused across retries.
  2. TTL: the table entry must outlive the longest retry window (attempts x backoff cap). A TTL shorter than that lets a late duplicate re-execute.
  3. Exactly-once = at-least-once delivery + idempotent receiver. There is no exactly-once delivery over a fallible network; what exists is effectively-once processing. Kafka's idempotent producer (per-partition sequence numbers) and transactional consume-process-produce narrow the window, but the receiver-side dedupe is what closes it.

# WHAT: idempotency keys, the receiver half of "effectively once".
# WHY:  networks fail mid-request, so clients retry. The server keeps
#       key -> result; a repeated key returns the stored result
#       instead of running the job again.
# WHAT BREAKS: a TTL shorter than the longest retry window lets a
#       late duplicate re-execute. TTL must exceed (attempts x backoff).

class IdempotentStore:
    def __init__(self):
        self._results = {}  # key -> result, with a TTL in production

    def run_once(self, key, fn, *args):
        # WHAT: run fn at most once per key; repeats return the stored
        #       result. Units: one result per unique key.
        if key in self._results:
            return self._results[key], "duplicate"
        result = fn(*args)
        self._results[key] = result
        return result, "executed"


calls = []
store = IdempotentStore()
for _ in range(3):  # client retries twice after timeouts
    out, how = store.run_once(
        "job-9f31",
        lambda t: calls.append(t) or f"embedding({t})", "text-3")
    print(how, "->", out)
print("side effects:", len(calls))
# Verified output:
# executed -> embedding(text-3)
# duplicate -> embedding(text-3)
# duplicate -> embedding(text-3)
# side effects: 1

Key takeaways

  • Little's Law: L = λW, in jobs. Sizes queues, pools, slots.
  • M/M/1: wait = ρ/(μ(1-ρ)). At 0.9, 9x service time. Target 0.6 to 0.75.
  • HNSW: M ~ 16, ef_construction ~ 200, tune ef_search (50-200) against recall@k.
  • KV cache: 2 x layers x hidden x bytes per token. Context length OOMs fleets.
  • 2 FLOP per param per token. Quantization halves memory per bit-ladder step.
  • Burn rate: 10x over 5 min pages, 2x over 1 h tickets.
  • Idempotency: client key + server key→result table with TTL beyond the retry window.

Part 3. Classic traps

These five have caused real outages. Each one looks reasonable until it fails, which is what makes it a trap.

3.1 Split-brain without fencing

A network partition splits the cluster. Both sides elect a leader. The partition heals. Now two leaders have both been writing, and the data is corrupt in ways no quorum can untangle afterward. The mistake is treating leader election as sufficient. It is not: you also need fencing.

Every write carries a token from a monotonic sequencer (a tiny strongly-consistent service, or a database row with an atomic increment). The store only accepts a write whose token exceeds every token it has seen. When the new leader takes over, it fetches a fresh, larger token. The old leader's writes arrive with smaller tokens and are rejected. Split-brain becomes harmless: the old leader shouts into a void.

FENCING TIMELINE (partition, then heal)

  time -->
  leader A (token 41) writes........ | partition
                                      |  leader B elected, token 42
                                      |  B writes accepted (42 > 41)
  partition heals: A (still token 41) tries to write
    store: 41 <= 42 seen -> REJECTED
  Result: one writer won, before the conflict, not after.

The trap version: "we have Raft, so we cannot have two leaders." Raft prevents two leaders in the same term, but a partitioned old leader that never learns about the new term can still issue writes to followers it can reach. Fencing is the second lock on the door. Any design with a leader needs to answer: what rejects the old leader's writes?

3.2 Exactly-once illusions

"No, our pipeline is exactly-once" is the most expensive sentence in data engineering. Over a network that can drop, delay, or duplicate packets, exactly-once delivery is impossible: the sender can never be sure the receiver got the message exactly once, because the acknowledgment itself can be lost. This is the Two Generals problem, and it has no protocol fix.

What exists:

  • At-most-once: fire and forget. Fast, lossy. Metrics and logs can live here.
  • At-least-once: retry until acknowledged. Nothing is lost, some things run twice. The default for anything important.
  • Effectively-once: at-least-once delivery plus an idempotent receiver (2.7). The effect happens once even though the delivery happened twice. This is what people mean when they say exactly-once, and naming it honestly keeps the dedupe logic from being forgotten.

Kafka's idempotent producer (per-partition sequence numbers) kills duplicates from producer retries. Its transactions make consume-process-produce atomic within the log. Both narrow the window. Neither removes the need for receiver-side idempotency at the boundary where the pipeline touches the outside world (charging, sending email, writing to a third-party API). Audit every "exactly-once" claim by asking: where is the dedupe key, and what is its TTL?

3.3 Cache stampedes

A hot key expires. In the next 100 ms, 5,000 requests miss the cache and hit the database at once. The database falls over, which causes more timeouts, which cause more retries, which deepen the outage. The cache was protecting the backend; its synchronized expiry removed the protection all at once.

Three fixes, in order of value:

  1. Request coalescing (singleflight). The first miss does the backend call; concurrent requests for the same key wait on that one in-flight result. 5,000 requests become 1 backend call. The verified implementation below holds a lock only around the table, never around the backend call, so unrelated keys still proceed in parallel.
  2. Jittered TTLs. Spread expiry over a window (4 to 6 minutes instead of exactly 5) so keys do not expire in lockstep.
  3. Probabilistic early refresh. A background process refreshes hot keys before they expire; or each request refreshes with probability rising as expiry nears.

# WHAT: request coalescing (singleflight), the fix for cache stampedes.
# WHY:  when a hot key expires, N concurrent requests must produce ONE
#       backend call, not N. The first request does the work; the rest
#       wait on the same in-flight result.
# WHAT BREAKS: holding the lock while calling the backend serializes
#       everything. The lock must guard the TABLE only; the backend
#       call happens outside it.

import threading
import time


class Singleflight:
    def __init__(self):
        self._lock = threading.Lock()
        self._inflight = {}  # key -> (event, result slot)
        self.backend_calls = 0

    def get(self, key, loader):
        with self._lock:
            if key in self._inflight:
                ev, slot = self._inflight[key]
                waiter = True
            else:
                ev, slot = threading.Event(), {}
                self._inflight[key] = (ev, slot)
                waiter = False
        if waiter:
            ev.wait()            # share the in-flight result
            return slot["value"]
        try:
            self.backend_calls += 1
            time.sleep(0.05)     # stand-in for a slow DB/model call
            slot["value"] = loader()
            return slot["value"]
        finally:
            with self._lock:
                del self._inflight[key]
            ev.set()


sf = Singleflight()
results = []
threads = [threading.Thread(
    target=lambda: results.append(sf.get("hot-key", lambda: "fresh-value"))
) for _ in range(50)]
[t.start() for t in threads]
[t.join() for t in threads]
print("requests:", len(results), "| backend calls:", sf.backend_calls,
      "| all equal:", len(set(results)) == 1)
# Verified output:
# requests: 50 | backend calls: 1 | all equal: True

3.4 Confusing p99 with worst case

p99 = 300 ms does not mean "the slowest request takes 300 ms." It means 1 percent of requests are slower than 300 ms. At 10,000 requests per second, that is 100 slow requests every second, each one a user having a bad time. The trap is reporting the p99 as if it describes the tail. It describes where the tail starts.

The second half of the trap is composition. A request that fans out to 20 backend calls, each with p99 = 100 ms, is not p99 = 100 ms end to end. The chance that all 20 calls land under their p99 is 0.99^20 ≈ 0.818, so about 18 percent of end-to-end requests exceed 100 ms somewhere. Tail latency multiplies across hops: the end-to-end p99 is set by the worst hop, and every hop you add drags it up.

TAIL COMPOSITION (20 hops, each p99 = 100 ms)

  P(all 20 under 100 ms) = 0.99^20 = 0.818
  P(at least one over)   = 1 - 0.818 = 0.182

  End-to-end p99 >> any single hop's p99.
  Rule: budget the tail per hop, measure p99.9/p99.99
  for anything user-facing.

Practical rules: measure p99.9 and p99.99 for user-facing paths. Keep fan-out shallow, or budget each hop's tail explicitly. When someone quotes a p99, ask "at what request rate," because 1 percent of a big number is a big number.

3.5 Silent queue backlogs

The most boring outage shape: a queue that grows 2 percent faster than the consumer drains it. Nothing alerts. Latency creeps up over days. Then a deploy restarts the consumer, the backlog must be reprocessed, and the queue that looked "a little behind" turns out to hold 14 hours of work.

The trap is monitoring queue depth instead of queue age. Depth without a rate is meaningless: 100,000 messages is 10 seconds at 10k/s and 28 hours at 1/s. Monitor lag in seconds:

lag_seconds = queue_depth / consumption_rate_per_s

Alert on two things: lag exceeding a fraction of the freshness contract (say, 10 percent of the allowed staleness), and lag growing over a sustained window even while below the threshold. The growth alert is the one that catches the 2-percent drift months before it becomes an incident.

The same trap hides in dead-letter queues. A DLQ with no reader and no alert is a second silent backlog: poison messages accumulate, nobody looks, and the data loss is discovered during an audit. Every DLQ needs a reader (even a daily digest to a human) and an age alert.

Key takeaways

  • Fencing tokens make split-brain harmless. Election alone does not.
  • Exactly-once delivery is impossible; effectively-once (at-least-once + idempotent receiver) is the real target.
  • Stampedes die to singleflight coalescing, jittered TTLs, and early refresh.
  • p99 is where the tail starts, not the worst case; tails multiply across hops.
  • Monitor queue lag in seconds and its growth rate, not raw depth. Alert on DLQ age.

Part 4. Rapid-fire drills

Twenty-six drills with worked answers. Cover the answers, answer out loud, then reveal. The categories match the platform: distributed systems, APIs and queues, storage, observability, pipelines, ML literacy, capacity planning.

Distributed systems

D1. A metadata store runs 5 replicas with W = 3, R = 3. Two replicas go down during a deploy. Do reads and writes still work? What breaks if a third replica fails?

Answer: reads and writes both still work, but there is no failure tolerance left.

Worked: W = 3 needs 3 live replicas for a write; R = 3 needs 3 for a read. With 2 down, exactly 3 remain, so both succeed. The quorum rule holds (3 + 3 > 5), so reads still see the latest writes. But one more failure leaves 2 live replicas: both reads and writes block until a replica returns. The design survives 2 failures only while all 5 are healthy; during the deploy it survives zero.

D2. A network partition splits your 3-replica store (W = 2, R = 2) into a side with 2 replicas and a side with 1. Which side keeps serving writes, and what must the other side do?

Answer: the 2-replica side keeps serving; the 1-replica side must refuse writes (and, strictly, reads that need the quorum).

Worked: a write needs W = 2 acknowledgments. Only the majority side has 2 live replicas, so only it can complete writes. The minority side with 1 replica cannot reach quorum; if it accepted writes anyway, the two sides would diverge and the quorum guarantee would be broken. This is the availability half of the tradeoff: the minority side chooses correctness over availability.

D3. The partition heals. The old leader on the minority side never learned it was deposed and kept issuing writes to the one follower it could reach. What mechanism makes those writes harmless?

Answer: fencing tokens.

Worked: every write carries a token from a monotonic sequencer. The new leader fetched token 42; the old leader still holds token 41. The store rejects any write whose token does not exceed the highest token seen, so the old leader's writes are dropped on arrival. Without fencing, the healed cluster has two divergent histories and no quorum math can repair them.

D4. You need a consensus group that tolerates 2 simultaneous failures. How many nodes, and how many votes to commit a write?

Answer: 5 nodes, 3 votes.

Worked: the rule is 2f + 1 nodes to tolerate f failures, so f = 2 needs 5. A commit needs a majority: floor(5/2) + 1 = 3. With 2 nodes down, 3 remain, which is exactly a majority, so the cluster keeps committing. Note 4 nodes also tolerate only 1 failure (majority of 4 is 3, and 4 - 1 = 3), so the even number buys nothing: always size consensus groups odd.

D5. 1M keys are spread over 10 nodes by hash mod 10. One node is removed. About how many keys move with consistent hashing versus naive mod-N hashing?

Answer: about 100k with consistent hashing; nearly all 1M with naive mod-N.

Worked: consistent hashing places keys on a ring and only the removed node's keys (K/N = 1M/10 = 100k) need reassignment to its neighbor. Naive mod-N renumbers every key's home (mod 9 instead of mod 10), so almost every key maps somewhere new. That is why membership changes use a ring, not a modulus.

APIs and queues

A1. A client POST to /jobs times out after the server already processed it. The client retries. Name the mechanism that keeps the customer from being charged twice, and the one detail that breaks it.

Answer: an idempotency key with a server-side key-to-result table; it breaks if the entry TTL is shorter than the retry window.

Worked: the client generates one key (say job-9f31) before the first attempt and reuses it on retries. The server runs the job once, stores key to result, and returns the stored result for repeats. If the TTL expires after, say, 1 hour but the client retries for 2 hours with backoff, the late duplicate finds no entry and re-executes. TTL must exceed attempts x backoff cap.

A2. One event stream must feed 6 consumers, and a new consumer next month needs the last 24 hours of history. Queue or stream, and why?

Answer: a stream (partitioned log).

Worked: a queue deletes each message on acknowledgment, so 6 consumers need 6 queues (or a pub/sub fan-out you now operate), and history is gone once consumed. A stream keeps the log durably; each consumer tracks its own offset, and the new consumer rewinds 24 hours and replays. One topic serves all current and future consumers.

A3. A consumer serves 100 requests per second. The latency deadline is 2 seconds. What queue bound do you set, and what happens to request 201?

Answer: bound 200; request 201 is rejected fast with 429 or 503.

Worked: Little's Law, capacity = rate x wait = 100 x 2 = 200. A queue longer than 200 means the 201st request would wait more than its deadline even if everything ahead succeeds, so queueing it only wastes its time and the consumer's memory. Rejecting fast lets the caller retry elsewhere, shed load, or degrade gracefully instead of queueing slow.

A4. A thousand clients hammer a recovering endpoint with retries in lockstep. Write the backoff formula that fixes it.

Answer: full jitter: sleep = random_between(0, min(cap, base x 2^attempt)).

Worked: exponential growth (1s, 2s, 4s, ...) spreads attempts over time; the random draw in [0, computed] breaks the lockstep so the thousand clients do not retry in the same millisecond and re-crash the endpoint. The cap (say 8 or 30 seconds) bounds the worst case. Missing jitter turns every recovery into a retry thundering herd.

Storage

S1. A hot key's TTL expires and 5,000 requests per second hit the database at once. Name the failure and give two fixes.

Answer: a cache stampede (thundering herd). Fixes: request coalescing and jittered TTLs.

Worked: coalescing (singleflight) makes the 5,000 concurrent misses share one in-flight backend call, so the database sees 1 query instead of 5,000. Jittered TTLs (expire over 4 to 6 minutes instead of exactly 5) stop keys from expiring in lockstep, so the herd never forms. A third layer is probabilistic early refresh of hot keys before expiry.

S2. Your HNSW index scores recall@10 = 0.88 against brute force. The target is 0.95 and the latency budget has headroom. Which knob do you turn, which direction, and when do you stop?

Answer: raise ef_search (say 50 to 100 to 200); stop at recall@k >= 0.95 or when the latency budget runs out.

Worked: ef is the query-time beam width; wider beams examine more candidates, so recall rises and latency grows roughly linearly. Measure recall@10 against brute force on real queries after each step. If the latency budget runs out before 0.95, the answer is not a bigger ef: it is sharding the index, quantizing vectors, or accepting the recall with a product-level fallback.

S3. Under mod-N hashing, one shard holds 40 percent of the keys while others sit idle. Give two fixes.

Answer: consistent hashing with virtual nodes, or a better shard key.

Worked: virtual nodes place many small virtual replicas of each physical node on the ring, which evens out the key distribution and smooths the load when nodes join or leave. If the skew comes from the key itself (say, shard by tenant and one tenant is huge), no hash fixes it: split the hot tenant's key space or shard by a more uniform attribute.

S4. An HNSW index holds 1M vectors of dim 768 in FP32 with M = 16. Roughly how much memory?

Answer: about 3.2 GB total: 3.07 GB for vectors, ~128 MB for the graph.

Worked: vectors cost 1M x 768 x 4 bytes = 3.07 GB. Graph edges cost about 1M x 16 x 2 (bidirectional) x 4 bytes = 128 MB. The vectors dominate; graph overhead is under 5 percent. This is why vector quantization (FP32 to INT8) pays more than graph tuning when memory is tight.

Observability

O1. Your service has a 99.9 percent SLO. Errors run at 1 percent for 5 minutes. What is the burn rate, and does it page or ticket?

Answer: burn 10x; it pages.

Worked: burn = observed / budgeted = 1% / 0.1% = 10. At 10x, the 30-day budget is gone in 3 days (30/10). The page tier is 10x over 5 minutes, so this pages. A 0.2 percent error rate would be burn 2x over an hour: ticket, look today, no page.

O2. "Alert me when p99 latency exceeds 2 seconds" pages you at 3am for a single slow request, yet misses a real degradation holding 30 percent of traffic at 1.9 seconds. What is wrong, and what replaces it?

Answer: threshold alerts ignore the error budget; replace with burn-rate alerts.

Worked: a single 3-second request trips the threshold but consumes a negligible slice of the monthly budget: a false alarm. Thirty percent of traffic at 1.9 seconds never trips it but burns budget fast: a missed real incident. Burn-rate alerting (10x over 5 min pages, 2x over 1 h tickets) ties urgency to budget consumption, so each alert carries its own severity.

O3. A request fans out to 20 backend calls, each with p99 = 100 ms. Roughly what fraction of end-to-end requests exceed 100 ms somewhere?

Answer: about 18 percent.

Worked: P(all 20 under p99) = 0.99^20 ≈ 0.818, so P(at least one over) = 1 - 0.818 ≈ 0.182. The end-to-end p99 is set by the worst hop and sits well above any single hop's p99. Rule: budget the tail per hop, and measure p99.9/p99.99 on user-facing paths.

O4. A service handles 10,000 requests per second with p99 = 300 ms. How many requests per second are slower than 300 ms?

Answer: about 100 per second.

Worked: p99 means 1 percent of requests exceed 300 ms; 1 percent of 10,000 is 100. p99 is where the tail starts, not the worst case. Reporting "p99 is 300 ms" as if the slowest request takes 300 ms hides 100 slow requests every second.

Pipelines

P1. A nightly job scores 10M documents with a model. The output may be a day old. Batch, micro-batch, or streaming, and why?

Answer: batch.

Worked: the freshness contract ("yesterday is fine") is the loosest possible, and batch is the cheapest per event, the simplest to reason about, and the easiest to re-run when something goes wrong. Streaming would cost more per event and add late-data and ordering complexity for zero product benefit. Match the shape to the contract.

P2. A ranking feature must reflect user events from the last 5 minutes. Which pipeline shape?

Answer: streaming, or tight micro-batch if minutes of delay are acceptable.

Worked: the freshness contract is seconds, which rules out batch entirely. Micro-batch with 1-minute windows is usually the pragmatic pick: it reuses batch logic and hits the contract with margin. True per-event streaming only if the product needs sub-minute reaction and someone is willing to operate the complexity (late data, out-of-order events, exactly-once effects).

P3. A poison message crashes the worker on every retry, forever. What breaks the loop?

Answer: an attempt cap plus a dead-letter queue with a reader and an alert.

Worked: cap attempts (say 5, with jittered backoff between them). After the cap, route the message to the DLQ instead of requeueing: the poison stops blocking the healthy messages behind it. The DLQ needs a human-readable payload, a daily reader or digest, and an age alert, or it becomes a silent backlog where data loss is discovered during an audit.

ML literacy

M1. A 70B model has 80 layers and hidden size 8192, served in FP16 with standard multi-head attention. What is the KV cache per token, and per 4k-token request?

Answer: about 2.5 MB per token; about 10 GB per 4k request.

Worked: 2 (K and V) x 80 layers x 8192 hidden x 2 bytes = 2,621,440 bytes ≈ 2.5 MB per token. Times 4096 tokens ≈ 10.7 GB. That is before weights (140 GB for 70B in FP16), so one request's cache alone exceeds an 80 GB GPU's spare room: long contexts are what OOM serving fleets.

M2. An 8B model's forward pass costs about 16 GFLOP per token. On hardware delivering 300 TFLOPs effective, what is the compute-bound time per token, and why is real decoding slower?

Answer: about 53 microseconds; real decoding is memory-bound.

Worked: 16 GFLOP / 300 TFLOP/s ≈ 53 µs. But each token's decode step must stream all 16 GB of weights from GPU memory, and memory bandwidth (not FLOPs) is the binding constraint, so the FLOP math is a floor, not a promise. This is also why batching helps: one weight-streaming pass serves many tokens at once.

M3. 8B weights in FP16 take 16 GB. What do INT8 and INT4 give you, and what do you give up?

Answer: 8 GB and 4 GB; you give up accuracy margin.

Worked: 8B x 1 byte = 8 GB; 8B x 0.5 bytes = 4 GB. Each step down the bit ladder roughly halves memory and doubles memory-bound throughput. The cost is accuracy cliffs on some tasks, so the quantized artifact must be versioned and evaluated like any model change, not treated as a free compression.

Capacity planning

C1. Requests arrive at 120 per second; each holds a GPU slot for 1.5 seconds. How many slots, and how many GPUs at batch 8?

Answer: 180 slots; 23 GPUs before headroom.

Worked: Little's Law, L = 120 x 1.5 = 180 concurrent slots. At 8 slots per GPU (batch 8), 180 / 8 = 22.5, so 23 GPUs. That is the steady-state average: add headroom for bursts and a spare per failure domain, and size the batch from the latency/throughput knee, not from this division.

C2. A fleet runs at 90 percent utilization and p99 latency is blowing up. Name two fixes and the number that justifies the first.

Answer: add capacity to reach ~70 percent, or shed load; the M/M/1 curve justifies the first.

Worked: at ρ = 0.9 the mean queue wait is 9x the service time; at ρ = 0.7 it is 2.3x. The fleet is only about 29 percent over-provisioned relative to the 0.7 target ((0.9-0.7)/0.7), but that capacity buys a 4x latency cut. When adding machines is slow, the other lever is shedding load (reject fast, degrade features) to pull ρ down immediately.

C3. Demand is 100k tokens/s. One GPU sustains 900 tokens/s measured. Target utilization 0.7, plus 2 spares. How many GPUs?

Answer: 161 GPUs.

Worked: usable per GPU = 900 x 0.7 = 630 tokens/s. 100,000 / 630 = 158.7, ceil to 159, plus 2 spares = 161. Every input here is load-bearing: if the 900 was a brochure number at a different batch size, the whole answer is fiction. Measure S on your fleet at the target batch and context mix.

Key takeaways

  • Say the number, then the unit, then the reason. "180 slots" beats "a lot of GPUs."
  • Every drill above reduces to one formula or one rule from Parts 1 and 2. If an answer feels like memorization, trace it back to the formula.
  • The traps in Part 3 are where drills become incidents. Re-read them after your first on-call week.

Part 5. One-page cheat sheet: 30 numbers and rules

  1. W + R > N. Every read overlaps every write. The quorum rule.
  2. W, R <= N - f to survive f failed replicas. Pick the smallest pair that satisfies both rules.
  3. 3, 2, 2 is the default: consistent, survives 1 failure.
  4. Consensus needs 2f + 1 nodes, f + 1 votes. 5 nodes tolerate 2 failures; always odd.
  5. Consistent hashing moves K/N keys on membership change, not all K.
  6. Fencing tokens make split-brain harmless. Election alone does not.
  7. Weakest consistency that keeps the product correct. Money and leadership need linearizable.
  8. L = λW. Little's Law, in jobs. The first number in every capacity review.
  9. capacity = rate x max wait. Past the bound, reject fast (429/503), never queue slow.
  10. M/M/1 wait = ρ/(μ(1-ρ)). At 0.5: 1x; 0.8: 4x; 0.9: 9x; 0.95: 19x service time.
  11. Target 60-75% utilization; 85% is an incident. Real traffic is burstier than Poisson.
  12. Queue or stream? Replay, fan-out, or per-key order → stream. Simple work distribution → queue.
  13. Batch, micro-batch, or streaming? Ask how stale the output may be. Yesterday → batch; seconds → stream; between → micro-batch.
  14. Full jitter: sleep = random_between(0, min(cap, base x 2^attempt)).
  15. Idempotency key TTL > attempts x backoff cap, or late duplicates re-execute.
  16. Effectively-once = at-least-once + idempotent receiver. Exactly-once delivery does not exist.
  17. Stampede fix order: singleflight coalescing, jittered TTLs, probabilistic early refresh.
  18. p99 is where the tail starts, not the worst case. 1% of 10k/s = 100 slow requests/s.
  19. Tails multiply across hops: 20 hops at p99 = 100 ms → ~18% of requests exceed it somewhere.
  20. Lag in seconds = depth / drain rate. Alert on lag and its growth, not raw depth.
  21. Every DLQ needs a reader and an age alert, or it is a silent backlog.
  22. HNSW: M ~ 16, ef_construction ~ 200, tune ef_search (50-200) until recall@k >= 0.95.
  23. Below ~100k vectors, brute force wins: simpler, perfect recall.
  24. KV cache = 2 x layers x hidden x bytes per token. 8B FP16 ≈ 0.5 MB/token.
  25. Long contexts OOM fleets, not model size. Check the model card for grouped-query attention.
  26. 2 FLOP per param per token. 8B → 16 GFLOP/token; a compute floor, since decode is memory-bound.
  27. Quantization halves memory per step (FP16→INT8→INT4); version and eval each artifact.
  28. GPUs = ceil(Q x (T_in + T_out) / (S x 0.7)) + spares. Measure S on your fleet.
  29. Burn 10x over 5 min pages (budget gone in 3 days); burn 2x over 1 h tickets (gone in 15 days).
  30. Nines per month: 99% → 7.2 h; 99.9% → 43 min; 99.99% → 4.3 min; 99.999% → 26 s.
