Unit1

Unit 1 · The reason

Why this category exists

From the lesson 25-ai-lab-mlops-systems.html, opening section

A model in a notebook is a hypothesis. A model in production is a system: a retrain schedule, a version for every artifact, quality gates before promotion, traffic behind a contract, and an alert when the world changes under the model.

The gap between the two states is where most ML value dies, and the failure modes are concrete. A retrain nobody can reproduce. A production model nobody can identify. Silent data drift that rots accuracy for weeks. A deploy that breaks the client contract. A service that falls over at ten times the traffic.

Week 12 walks the production loop in order. Day 1 builds ML pipelines as code with CI-style checks. Day 2 adds the model registry. Day 3 watches the model in the wild. Day 4 does the scaling math in a simulator. Day 5 ships a model behind an HTTP service contract with contract tests. The next unit zooms out to full architecture design. This unit builds the machinery that design assumes. The chart below shows the study plan.

Unit 2 · Core ideas, worked end to end

1. Pipelines as code: CI/CD for machine learning

From the lesson 25-ai-lab-mlops-systems.html, core ideas

An ML pipeline is the training workflow as code with one entrypoint: config in, artifacts out. CI/CD for ML extends software CI with ML-specific checks. Data schema validation checks names, types, ranges, and nulls at load. Determinism demands byte-identical outputs for identical inputs. Quality gates demand that metrics clear a threshold before promotion. Artifact lineage records the code version, data version, config, and seed behind every saved model.

Notebook training is stateful: cells run out of order, variables linger, and a good result from yesterday stays unverifiable. The lab makes the failure concrete. Without a seeded, config-driven entrypoint, two runs of the same code produce two different models, and nobody can name the model in production.

The steps run in order. One config file plus a single run_pipeline entrypoint, with every random choice from a recorded seed. Data load, then schema checks that fail loud. Training on versioned code and data. Evaluation behind the quality gate. Artifact save with lineage. The CI simulation runs the pipeline twice and asserts identical outputs, then asserts the regression gate blocks a deliberate worse model.

The trap is a shallow read of CI: unit tests on training code are necessary and miss the ML failures, unvalidated data, nondeterministic runs, and silent metric regressions. Determinism does not mean the model is good. Determinism means the process is honest: a deterministic bad model is debuggable, and a nondeterministic good model is luck.

Transfer. Add a determinism check to every training pipeline you own. The check costs one extra run and buys trust in all later runs.

2. The model registry: versions are facts, stages are pointers

From the lesson 25-ai-lab-mlops-systems.html, core ideas

A model registry is the database of record for trained models. Each version is immutable: artifacts, metadata with metrics and config and lineage, and a deterministic version id derived from content. Stages are movable pointers to versions: staging, production, archived. Promotion moves a pointer after gates pass, and rollback moves the pointer back.

Without a registry, the production model is a file on a laptop or a storage path in a chat log. A misbehaving model then has no identity, no comparison set, and no confident rollback target. The registry exists to kill that state.

Audit is the payoff property. At any moment the registry answers which version is live, what trained that version, and how the version differs from neighbor versions. The promotion flow enforces the order: metric thresholds, contract checks, and policy approval all pass before the production pointer moves, in Nugget 5.

Nugget 5 · Versions are facts From the lesson Concept 2 of the unit
The lesson

Why it matters. Promotion moves a pointer after gates pass. Rollback moves the pointer back. Audit answers three questions at any moment: the live version, the lineage behind the version, and the difference from neighbor versions.

Transfer. Never name a model by a file path or a chat message. Identity comes from the registry or the model has no identity.

3. Monitoring and drift detection: noticing when the world moves

From the lesson 25-ai-lab-mlops-systems.html, core ideas

Drift detection compares production data against training data and raises the alarm at divergence. PSI, the population stability index, measures distribution shift across bins. The KS statistic measures the largest gap between two cumulative distributions with no shape assumption. Performance monitoring tracks live metrics, accuracy where labels exist plus latency and error rate, against baselines. Alerting rules turn signals into pages.

Models decay in silence. The training distribution is a photograph and production is a moving scene: user behavior shifts, upstream pipelines change, seasons change. The lab generates a baseline batch and a drifting production batch, and the metrics move before any model output looks wrong. Without this layer, the first drift signal is a customer complaint weeks later.

The steps fix the baseline first: training-time feature distributions and metric values. Each production batch gets PSI per feature across matched bins, the KS statistic, and mean and variance shifts. Alert rules apply thresholds plus sustain counts: a page at PSI over 0.25 on a key feature, a page at an accuracy drop over two points for three consecutive batches. The alert triggers the retrain decision, and the loop closes back to the Day 1 pipeline and the Day 2 gates.

Transfer. Write alert rules as threshold plus sustain: three bad batches, not one. The rule design is the on-call health design.

4. Deployment and scaling: the contract and the math behind it

From the lesson 25-ai-lab-mlops-systems.html, core ideas

Deployment exposes a model as a service behind a service contract. The contract names endpoints: /health for liveness and /predict for inference. The contract fixes JSON request and response shapes, status codes, and a latency budget. Contract tests verify the contract from a client, CI-style, so a deploy that breaks clients never ships.

A model without a contract is a rumor. Clients guess shapes, break on upgrades, and cannot separate a model error from a network error. The Day 5 lab makes the contract executable: a small deterministic model behind HTTP, with a client test suite as the ship gate.

Scaling is the math of service volume: throughput in requests per second against latency in seconds per request, moved by three levers. Micro-batching groups requests and amortizes fixed cost. Caching skips recomputation on repeats. Workers add parallelism. The Day 4 simulator separates the levers on one workload: batch size sweeps, cache hit-rate sweeps, worker counts, with the bottleneck on record at each point. The worked batch numbers sit in Nugget 4.

3.3xthroughput gain from a batch of 8 requests
Nugget 4 · Batch of 8, priced in latency From the lesson Concept 4 of the unit
The lesson

At 20 ms fixed cost plus 5 ms per request, a batch of 8 takes 60 ms in total: 7.5 ms amortized per request, 3.3x the throughput at 2.4x the latency of one request.

Why it matters. Batching buys throughput with latency as the price. An 80 percent cache hit rate at 1 ms per hit is the one lever in the lab that improves both metrics at once.

Transfer. Quote throughput and latency as a pair, always. A throughput number alone hides the price the users pay.

Unit 7 · The gate

Interview clearance

From the lesson 25-ai-lab-mlops-systems.html, interview clearance

The postmortem prompt opens the gate: a nightly retrain shipped a worse model, and the answer walks the five labs in order and names the mechanism in each lab that catches the failure. The versioning prompt asks for a full design for a team of twenty: version ids, stages, promotion gates, rollback, with product names barred until the mechanics stand.

The judgment prompts carry the rest. A key feature crosses PSI 0.25 with accuracy flat: page or ticket, with the alerting rule defended. A serving tier needs 10k requests per second with p99 under 100 ms at 20 ms fixed cost plus 5 ms per request: show the batching arithmetic. One whiteboard holds the full production loop with a check marked at every handoff.

The graded answers are short. Different metrics from one seed mean nondeterminism in the pipeline. A staging version with better metrics waits for gates before the production pointer moves. Late labels mean label-free drift metrics plus serving metrics carry the watch this week.
