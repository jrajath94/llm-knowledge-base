MLOps and Systems: From Notebook to Production

Five expert labs move a model from a notebook into production: versioned pipelines with quality gates, a model registry with staged promotion, drift detection and alerting, and serving with the scaling math that decides throughput and latency.

5 labs28 tasksWeek 12Difficulty: all Expert

Why this category exists

A model in a notebook is a hypothesis. A model in production is a system: it retrains on a schedule, versions every artifact, passes quality gates before promotion, serves traffic behind a contract, and pages someone when the world changes under it. The category exists because the gap between those two states is where most ML value dies. The failure modes are concrete: a retrain that is not reproducible, a "production" model nobody can identify, a silent data drift that rots accuracy for weeks, a deploy that breaks the client contract, a service that falls over at 10x traffic.

Week 12 walks the production loop in order. Day 1 builds ML pipelines as code with CI-style checks: config-driven entrypoints, schema checks on data, training, evaluation with quality gates, saved artifacts, and a determinism check that proves the pipeline reproduces itself. Day 2 adds the model registry: deterministic version ids, registration with metadata, stage pointers (staging versus production), promotion gates, and audit. Day 3 watches the model in the wild: drift metrics (PSI, KS, mean and variance shift), performance monitoring, and alerting rules. Day 4 does the scaling math: a simulator with a single worker, micro-batching, and caching, then experiments that separate what batching buys from what caching buys. Day 5 ships: a model behind an HTTP service contract with health and prediction endpoints, verified by contract tests from a client.

All five labs are rated Expert, the highest difficulty in the AI Lab program. They assume the modeling volumes are behind you; what is new here is systems thinking applied to models. Volume 26 (System Design) will zoom out from these mechanics to full architecture; this volume is the machinery it assumes.

Core ideas, worked end to end

1. Pipelines as code: CI/CD for machine learning

What it is, in plain words. An ML pipeline is the training workflow expressed as code with one entrypoint: config in, artifacts out. CI/CD (continuous integration, continuous delivery) for ML extends software CI with ML-specific checks: data schema validation, determinism (the same inputs produce byte-identical outputs), quality gates (metrics must clear a threshold before promotion), and artifact lineage (every saved model records the code version, data version, config, and seed that produced it).

Why it exists. Notebook training is stateful: cells run out of order, variables linger, and "it worked yesterday" is unverifiable. The Day 1 lab makes the failure concrete: without a seeded, config-driven entrypoint, two runs of the same code produce different models and nobody can say which one is in production. Schema checks catch the other classic: the upstream data changed shape and training silently consumed garbage. Quality gates catch the third: a retrain that is worse than the current model must not promote itself.

How it works, step by step. (1) A config file plus a single run_pipeline entrypoint; every random choice flows from a recorded seed. (2) Data generation or loading, then schema checks: column names, types, ranges, no silent nulls. (3) Training with versioned code and data. (4) Evaluation that computes metrics and applies the quality gate: promote only if the new metrics beat the baseline by a margin. (5) Artifact saving: model weights, metrics, and the config, all with lineage. (6) CI simulation: run the pipeline twice and assert identical outputs (determinism check), and assert the regression gate blocks a deliberately worsened model.

Worked example. The lab's pipeline trains logistic regression on generated data. Run one with seed 42 produces accuracy 0.87 and a fixed artifact hash. Run two with seed 42 must produce accuracy 0.87 and the same hash; if it does not, the pipeline has an unseeded random source or an ordering bug, and the CI check fails loudly. The regression gate is set at baseline plus a margin: a candidate at 0.85 does not promote, no matter how fresh it is.

The misunderstanding interviewers exploit. "CI for ML is just running pytest on training code." Unit tests are necessary but miss the ML-specific failures: unvalidated data, nondeterministic runs, and silent metric regressions. The follow-up trap: determinism does not mean the model is good, it means the process is honest. A deterministic bad model is debuggable; a nondeterministic good model is luck.

How to read this diagram

  1. The pipeline flows left to right: a seeded config entrypoint, data with schema checks, training on versioned code and data, evaluation behind a quality gate, and saved artifacts carrying lineage.
  2. The determinism panel states the key CI check: run_pipeline with the same seed twice must yield byte-identical metrics and artifacts.
  3. The bottom panel contrasts software CI with ML CI: data validation, reproducibility, metric gates, and artifact lineage are the ML additions.

Interview relevance. "Your nightly retrain produced a worse model and it is live. What broke?" The complete answer walks the missing pieces: no determinism check, no regression gate, no artifact lineage to identify the bad version.

Key takeaways

  • ML pipelines: config in, artifacts out, every random choice seeded and recorded.
  • ML CI adds data validation, determinism checks, and metric regression gates to software CI.
  • Lineage (code, data, config, seed per artifact) is what makes a bad deploy debuggable.

2. The model registry: versions are facts, stages are pointers

What it is, in plain words. A model registry is the database of record for trained models. Each version is immutable: artifacts (weights), metadata (metrics, config, lineage), and a deterministic version id derived from content. Stages (staging, production, archived) are movable pointers to versions. Promotion moves a pointer after gates pass; rollback moves the pointer back. Audit is the ability to answer, at any moment, which version is live, what trained it, and how it differs from its neighbors.

Why it exists. Without a registry, "the production model" is a file on someone's laptop or an S3 path in a chat log. When it misbehaves, you cannot identify it, compare it, or roll it back with confidence. The Day 2 lab builds the registry from scratch precisely so the concepts are not product names but mechanics: deterministic ids so the same content always gets the same version, stage pointers so promotion is explicit, gates so promotion is earned, audit so the whole thing is inspectable.

How it works, step by step. (1) Define the artifact bundle and compute a deterministic version id (a hash of content, not a counter). (2) Register: store artifacts plus metadata. (3) List versions and resolve stage pointers: "production" currently means v3. (4) Promote with gates: v4 moves from staging to production only when metric gates and checks pass. (5) Audit: load the production artifacts and diff v4 against v3, metrics and config side by side. The critical invariant: versions never change; only pointers move. That is what makes rollback a one-line, trustworthy operation instead of a scramble.

Worked example. v3 is in production with accuracy 0.87. v4 registers with accuracy 0.89 and a new feature set. The promotion gate requires accuracy above 0.88 on the held-out set plus all contract checks green. v4 passes; the production pointer moves v3 to v4. Two days later a data bug is found in v4's training set: rollback moves the pointer back to v3 in seconds, and the audit trail shows exactly what v4 changed. No files are deleted; no one re-trains in a panic.

The misunderstanding interviewers exploit. "Versioning is just naming files v1, v2." Names are not identity: a deterministic content-derived id guarantees the same artifacts always map to the same version, which is what makes comparisons and rollbacks trustworthy. The second trap: treating promotion as deployment. Promotion changes which version the stage pointer names; deployment (Day 5) is the separate act of serving it. Conflating them is how teams "roll back" and discover the old artifacts are gone.

How to read this diagram

  1. Three immutable versions sit at the top, each with artifacts, metadata, and a deterministic content-derived id.
  2. Stages are pointers, not copies: staging names v4, production names v3, and either pointer can move.
  3. Promotion is gated: v4 reaches production only after metric gates and checks pass; rollback is moving the pointer back to v3.
  4. The audit panel states the payoff: which model is live, what trained it, and how versions differ must be answerable in minutes.

Interview relevance. "Design model versioning for a team of twenty" tests whether you reach for content-derived ids, stage pointers, and promotion gates, or just say "we use MLflow". Mechanics first, product names second.

Key takeaways

  • Versions are immutable facts with content-derived ids; stages are movable pointers.
  • Promotion is gated and explicit; rollback is moving a pointer, not a rescue operation.
  • Audit answers "what is live, what trained it, what changed" in minutes.

3. Monitoring and drift detection: noticing when the world moves

What it is, in plain words. Drift detection compares the data your model sees in production against the data it trained on, and raises the alarm when the two diverge. PSI (population stability index) measures how much a feature's distribution shifted across bins. The KS (Kolmogorov-Smirnov) test measures the largest gap between two cumulative distributions without assuming any shape. Performance monitoring tracks live model metrics (accuracy where labels exist, latency, error rate) against their baselines. Alerting rules turn those signals into pages: drift over threshold, or a sustained metric drop, summons a human.

Why it exists. Models decay silently. The training distribution is a photograph; production is a moving scene: user behavior changes, upstream pipelines change, seasons change. The Day 3 lab generates a baseline batch and a drifting production batch so you can watch the metrics move before any model output looks wrong. Without this layer, the first sign of drift is a customer complaint weeks later, and the debugging starts from "when did it break", a question the monitoring should have answered.

How it works, step by step. (1) Fix the baseline: the training-time feature distributions and metric values. (2) For each production batch, compute PSI per feature across matching bins, the KS statistic, and mean and variance shifts. (3) Track model performance metrics on whatever labeled or proxy signal exists. (4) Apply alerting rules: for example, page when PSI exceeds 0.25 on a key feature, or when accuracy drops more than two points for three consecutive batches. (5) The alert triggers the retrain decision, which runs the Day 1 pipeline and the Day 2 promotion gates: monitoring closes the loop back to training.

Worked example. A feature "session length" has baseline bin shares [0.2, 0.5, 0.3] and this week's shares [0.35, 0.4, 0.25]. PSI = sum over bins of (actual - expected) x ln(actual / expected) = 0.15 x ln(1.75) + (-0.10) x ln(0.8) + (-0.05) x ln(0.833) = 0.084 + 0.022 + 0.009 = 0.115. That lands in the 0.1 to 0.25 watch band: not a page, but a ticket. If next week it crosses 0.25 on a revenue-driving feature, the alert fires and the retrain loop starts.

The misunderstanding interviewers exploit. "Drift detection means watching accuracy." Accuracy needs labels, which often arrive weeks late or never; input drift metrics like PSI and KS are the early warning system, and they work with no labels at all. The second trap: alerting on every wiggle. Thresholds plus sustain rules (three bad batches, not one) are what keep the on-call rotation sane; the lab's alerting section is really about that discipline.

How to read this diagram

  1. The baseline batch (blue, training-time distribution) and the production batch (red, this week) both feed the drift metrics box (amber): PSI, KS, and mean/variance shift.
  2. The middle panel defines the three measures and the PSI rule of thumb: under 0.1 no shift, 0.1 to 0.25 watch, over 0.25 significant.
  3. Performance monitoring tracks live model metrics against baseline: accuracy, latency, error rate.

Key takeaways

  • PSI, KS, and mean/variance shift detect input drift with no labels: the early warning system.
  • Performance monitoring tracks live metrics; alerting rules (threshold plus sustain) keep pages meaningful.

4. Deployment and scaling: the contract and the math behind it

What it is, in plain words. Deployment is exposing a model as a service behind a service contract: named endpoints (/health for liveness, /predict for inference), JSON request and response shapes, status codes, and a latency budget. Contract tests verify that contract from a client, CI-style, so a deploy that breaks clients never ships. Scaling is the math of serving more: throughput (requests per second) versus latency (seconds per request), moved by three levers: micro-batching (group requests to amortize fixed cost), caching (skip recomputation on repeats), and workers (parallelism).

Why it exists. A model without a contract is a rumor: clients guess at shapes, break on upgrades, and cannot tell a model error from a network error. The Day 5 lab makes the contract executable: a tiny deterministic model behind HTTP, with health and prediction endpoints, verified by a client test suite. Scaling exists because the naive service falls over: one request at a time means the fixed per-request cost dominates, and the Day 4 simulator shows you exactly where the time goes before you spend money on more machines.

How it works, step by step. Deployment: (1) Wrap the model in an HTTP service with /health and /predict. (2) Freeze the JSON shapes for requests and responses. (3) Write client-side contract tests: correct predictions, correct shapes, correct error codes on bad input, health endpoint alive. (4) Deploy only when the tests pass. Scaling: (1) Model one worker with a fixed cost per batch plus a per-request cost. (2) Experiment: vary the batch size and measure throughput versus latency; add a cache and vary the hit rate; add workers and watch the bottleneck move. (3) Choose the operating point the latency budget allows. The lab's key separation: batching buys throughput at the price of latency, caching buys both when the hit rate justifies it.

Worked example. A single worker costs 20 ms fixed plus 5 ms per request. One request takes 25 ms. A batch of 8 takes 20 + 40 = 60 ms total, which is 7.5 ms amortized per request: 3.3x the throughput at 2.4x the latency of a single request. Whether that trade is good depends on the budget: at a 100 ms latency target it is pure win; at a 30 ms target it is forbidden. Add a cache with an 80 percent hit rate at 1 ms per hit, and most requests skip the 25 ms path entirely: caching is the only lever that improves both metrics at once.

The misunderstanding interviewers exploit. "Just add more workers." Workers help until the bottleneck moves: to the batching logic, the cache, the network, or the database behind the model. The simulator's lesson is to find the bottleneck by measurement, not by purchasing. The second trap: optimizing throughput when the product needs latency. A batch of 64 looks heroic on requests per second and terrible on the p99 latency the users actually feel; always name which metric the product pays for.

How to read this diagram

  1. The client (blue) and the HTTP service (green) are bound by the contract (amber): endpoint names, JSON shapes, status codes, latency budget. Contract tests verify it from the client side.
  2. The scaling panel names the three levers: micro-batching amortizes fixed cost, caching skips recomputation, workers parallelize until the bottleneck moves.
  3. The worked numbers show the batching trade: 8 requests in 60 ms is 3.3x the throughput at 2.4x the latency of one request; caching at 80 percent hit rate beats both.

Interview relevance. "Design model serving for 10k requests per second at p99 under 100ms" is a systems interview in ML clothing. The answer that names the contract first and then does the batching arithmetic beats the answer that reaches for Kubernetes.

Key takeaways

  • The service contract (/health, /predict, JSON shapes, latency budget) is verified by client-side contract tests.
  • Batching trades latency for throughput; caching is the only lever that improves both; workers help until the bottleneck moves.
  • Name the metric the product pays for (throughput or p99 latency) before choosing the operating point.

def make_synthetic(n: int, d: int, seed: int):
    rng = np.random.default_rng(seed)
    X = rng.standard_normal((n, d))
    w_true = rng.standard_normal((d,))
    b_true = 0.2
    logits = X @ w_true + b_true
    p = 1.0 / (1.0 + np.exp(-logits))
    y = (p > 0.5).astype(np.int64)
    return X.astype(np.float64), y

def train_test_split(X, y, train_frac: float, seed: int):
    rng = np.random.default_rng(seed)
    n = X.shape[0]
    idx = rng.permutation(n)
    nt = int(train_frac * n)
    tr, te = idx[:nt], idx[nt:]
    return X[tr], y[tr], X[te], y[te]

def schema_checks(X, y):
    check("X_2d", X.ndim == 2)
    check("y_1d", y.ndim == 1)
    check("n_match", X.shape[0] == y.shape[0])
    check("no_nan", np.isfinite(X).all() and np.isfinite(y).all())
    check("binary_y", set(np.unique(y).tolist()) <= {0,1})

def sigmoid(z):
    return 1.0 / (1.0 + np.exp(-z))

def log_loss(y, p, eps: float = 1e-12):
    p = np.clip(p, eps, 1.0 - eps)
    return float(-np.mean(y * np.log(p) + (1-y) * np.log(1-p)))

def fit_logreg(X, y, lr: float, steps: int, l2: float, seed: int):
    rng = np.random.default_rng(seed)
    n, d = X.shape
    w = 0.01 * rng.standard_normal((d,))
    b = 0.0
    for _ in range(steps):
        z = X @ w + b
        p = sigmoid(z)
        # gradients
        gw = (X.T @ (p - y)) / n + l2 * w
        gb = float(np.mean(p - y))
        w -= lr * gw
        b -= lr * gb
    return {"w": w, "b": b}

def predict_proba(model, X):
    return sigmoid(X @ model["w"] + model["b"])

def predict(model, X):
    return (predict_proba(model, X) >= 0.5).astype(np.int64)

def save_artifacts(cfg: dict, model: dict, metrics: dict):
    outdir = Path(cfg["artifacts_dir"])
    outdir.mkdir(parents=True, exist_ok=True)
    # Save weights (numpy) + metadata (json)
    np.save(outdir / "weights.npy", model["w"])
    (outdir / "bias.txt").write_text(str(float(model["b"])), encoding="utf-8")
    (outdir / "metrics.json").write_text(json.dumps(metrics, indent=2), encoding="utf-8")
    (outdir / "config.json").write_text(json.dumps(cfg, indent=2), encoding="utf-8")
    return str(outdir)

    rng = np.random.default_rng(seed)

def stable_hash_bytes(parts: list[bytes]) -> str:
    h = hashlib.sha256()
    for p in parts:
        h.update(p)
    return h.hexdigest()[:16]

def version_id(model: dict, cfg: dict, metrics: dict) -> str:
    # stable: same (weights+cfg+metrics) => same id
    w_bytes = model["w"].tobytes()
    b_bytes = np.float64(model["b"]).tobytes()
    cfg_bytes = json.dumps(cfg, sort_keys=True).encode("utf-8")
    met_bytes = json.dumps(metrics, sort_keys=True).encode("utf-8")
    return stable_hash_bytes([w_bytes, b_bytes, cfg_bytes, met_bytes])

def sigmoid(z):
    return 1.0 / (1.0 + np.exp(-z))

def make_batch(n: int, d: int, seed: int, mean_shift: float = 0.0, scale_shift: float = 0.0, label_shift: float = 0.0):
    rng = np.random.default_rng(seed)
    X = rng.standard_normal((n, d)).astype(np.float64)
    k = max(1, d // 4)
    X[:, :k] = (1.0 + scale_shift) * X[:, :k] + mean_shift
    w_true = np.linspace(-1.0, 1.0, d)
    b_true = 0.0
    p = sigmoid(X @ w_true + b_true)
    p = np.clip(p + label_shift, 0.0, 1.0)
    y = (p >= 0.5).astype(np.int64)
    return X, y

def log_loss(y, p, eps: float = 1e-12):
    p = np.clip(p, eps, 1.0 - eps)
    return float(-np.mean(y*np.log(p) + (1-y)*np.log(1-p)))

D = 8
W = np.linspace(-1.0, 1.0, D).astype(np.float64)
B = 0.1

def sigmoid(z):
    return 1.0 / (1.0 + np.exp(-z))

def predict_one(x: np.ndarray):
    x = np.asarray(x, dtype=np.float64)
    if x.shape != (D,):
        raise ValueError(f"expected shape ({D},) got {x.shape}")
    p = float(sigmoid(float(x @ W + B)))
    y = int(p >= 0.5)
    return p, y

x_demo = rng.standard_normal((D,))
p_demo, y_demo = predict_one(x_demo)
print('demo', p_demo, y_demo)
check('p_range', 0.0 <= p_demo <= 1.0)

Design prompt

  • Your nightly retrain shipped a worse model. Walk the postmortem: which of the five labs' mechanisms would have caught it, in order?
  • Design model versioning for a team of twenty: version ids, stages, promotion gates, rollback. No product names until the mechanics are done.
  • A key feature's PSI crossed 0.25 but accuracy has not moved. Page or ticket? Defend your alerting rule.
  • Size a serving tier: 10k requests per second, p99 under 100ms, 20ms fixed cost plus 5ms per request. Show the batching arithmetic.
  • Draw the full production loop on one whiteboard and mark every handoff where this week's labs add a check.

Q1. Two runs of your pipeline with the same seed produce different metrics. What is the most likely class of cause?

Answer: B. Nondeterminism in the pipeline: an unseeded random source, unordered file reads, or a race in parallel aggregation.

  • A, wrong: The quality gate is miscalibrated. The gate judges metrics; it does not change them between identical runs.
  • B, right: An unseeded RNG, nondeterministic ordering, or a parallel race: the determinism CI check exists for exactly this.
  • C, wrong: The model architecture is wrong. Architecture affects metric values, not run-to-run reproducibility.
  • D, wrong: The registry version id collided. Content-derived ids do not collide; and the metrics differ before any registry is involved.

Q2. Version v4 is in staging with better metrics than production v3. What must happen before the production pointer moves?

Answer: C. The promotion gates must pass: metric thresholds, contract checks, and whatever approval the policy requires.

  • A, wrong: Nothing; better metrics mean it should go live immediately. Metrics are necessary but not sufficient; gates exist for the rest.
  • B, wrong: Delete v3 to save space. Versions are immutable; deleting the rollback target is exactly the failure mode.
  • C, right: Gated promotion: metrics, checks, and approval. Only then does the pointer move.
  • D, wrong: Retrain v4 with a new seed for safety. That creates a new version with new lineage, not a safer v4.

Q3. Production labels arrive six weeks late. How do you watch model health this week?

Answer: A. Label-free input drift metrics (PSI, KS, mean/variance shift) plus serving metrics like latency and error rate.

  • A, right: Input drift metrics need no labels; serving metrics catch system failures. Accuracy joins when labels arrive.
  • B, wrong: Wait for labels; accuracy is the only real signal. Six weeks of blindness is the failure the lab prevents.
  • C, wrong: Retrain weekly regardless of signals. Scheduled retrains without monitoring waste compute and can ship regressions.
  • D, wrong: Watch the loss on the training set. Training loss says nothing about production data.

Q4. Your service handles 8 requests per batch in 60ms total (20ms fixed + 5ms each). The product needs p99 latency under 40ms. What do you do?

Answer: D. Batching is forbidden by the latency budget here; reach for caching or more workers, and verify by measurement.

  • A, wrong: Increase the batch to 16 for more throughput. That raises latency further past the budget.
  • B, wrong: Keep the batch of 8; 60ms amortized is fine. 60ms exceeds the 40ms budget; amortized math does not pay the user's latency.
  • C, wrong: Remove the fixed cost by deleting health checks. The fixed cost is in the serving path, not the health endpoint.
  • D, right: The latency budget rules out this batch size; use caching or parallelism and measure the p99.

Key takeaways

  • MLOps interviews test the loop: determinism, versioning, gates, drift, contracts, scaling math.
  • Answer in mechanics before product names: content-derived ids, stage pointers, PSI thresholds, batching arithmetic.
  • Every production decision is a measured tradeoff with a named metric and an owner.
