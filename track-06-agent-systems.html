About this track

This track uses the base research-engineer curriculum. It focuses on one role: the agent systems engineer. The base curriculum teaches you how language models work. This track teaches you how to add scaffolds, tools, memory, and guardrails to these models. This helps the models do multi-step work. This work must operate correctly with real users and real systems.

The model is almost never the difference between a demo agent and a production agent. The difference is everything around the model. The agent scaffold is the loop. It drives thought, action, and observation. Then you design the tools. You set the context budget.

You make a checkpoint and recovery plan. The eval gate decides if a change ships. The cost ledger tracks costs. This track makes these items the main subject.

The track has three parts. Part 0 describes the role. It shows what the role owns. It shows what a normal day looks like. It shows how to measure the work. Part 1 maps the base volumes to this role.

It gives a specific reading order. This helps you avoid reading 16 volumes without a plan. Part 2 is new material. It has seven in-depth chapters on the systems work. The base curriculum only touches on this work. Each chapter has runnable Python, a visual, and a lab.

Part 0: The role

What an agent systems engineer owns

A research engineer trains models. An agent systems engineer ships systems. Models are one component in these systems. The agent harness and everything it touches is the owned surface.

How to read this diagram

  1. Start with the control loop. This is the pattern the agent runs in.
  2. Tool use and memory are what the loop touches. Reliability keeps a 30-step run alive.
  3. Cost and evaluations close the loop. Cost is the budget you spend. Evaluation is the grade you earn.
  • The control loop. This includes ReAct-style loops, plan-and-execute planners, and multi-agent orchestration. The engineer selects the pattern. The engineer sets the step budget. The engineer wires the stop conditions.
  • Tool use. This is the design of the functions the agent can call. These functions have narrow scopes. They have machine-checkable schemas. Error messages are for a model reader. Side effects are idempotent.
  • Multi-step reliability. Checkpoints make sure that a failed 30-step run starts again at step 24. It does not start again at step 1. Retry policies know the difference between a temporary network problem and a stuck agent. Human review points are necessary for risky actions.
  • Memory and context. This includes what enters the prompt. It includes what gets summarized. It includes what lives in a vector store.
  • It also includes the budget. Context is the most limited resource in an agent system. This engineer manages the context.
  • Evaluation as a gate. Task harnesses, graders, judge calibration, and CI gates stop a bad prompt or tool change from shipping.
  • Cost engineering. This includes token budgets per task. It includes model routing per step. It also includes cascade design. The phrase cost per task is common in this role. It means how much money a completed task costs.

What the role does not usually own: model pre-training, weight-level fine-tuning of frontier models, or GPU cluster operations. It sits between the model and the user, and the team measures it on outcomes there.

A normal day

The day runs in a loop. This loop is similar to the agent loop.

Morning: look at the numbers. The engineer opens the agent dashboard. They check three numbers from the last 24 hours. First, task success rate. This is the share of tasks that reached a verified done state. Second, cost per task.

This is the total model and tool spend divided by completed tasks. Third, recovery rate. This is the share of failed runs that a retry or checkpoint-resume saved. The engineer investigates any number that is not in its range today.

Mid-morning: read a trajectory. A failed run from overnight opens step by step. The engineer does not read model output for general impressions. They answer a question. Did it fail in the plan? Did it fail in a tool call?

Did it fail in the observation parsing? Did it fail in the stop condition? Each answer shows a different fix. Chapter 7 of this track teaches a method for this.

Afternoon: change one thing. A tool's error message gets rewritten. This makes sure the agent stops calling it with the wrong arguments. A risky action gets a human-review checkpoint. Risky actions include refund, delete, and send. A summarization pass gets added at step 12.

This makes sure long runs do not use too much context budget. Make one change. Then the eval suite runs.

Evening: gate the release. The eval harness runs the changed agent on a fixed task set. Compare the success rate, cost, and a sample of trajectories to the pinned baseline. If the numbers are good, the change ships. If the numbers are not good, the trajectories go back into the morning queue.

Progress is the loop running. Progress is not any single change.

How success is measured

Three numbers define the role. All other information is for diagnosis.

How to read this diagram

  1. An outcome check grades task success. The agent's own claim never grades it.
  2. Cost per task includes tokens, tool calls, storage, and compute. Two 90 percent agents are not equal if one costs $0.40 and the other costs $4.00.
  3. Recovery asks if failed runs start again instead of restarting.

Task success rate. This is the share of started tasks that reach a verified done state. An outcome check grades this. The agent's own claim does not grade this. A production agent system targets a band. The product owner agrees on this band.

This band is often 80 to 95 percent. The task risk changes the band. Always report the number with the harness version. Always report the number with the attempt count. (Supplement 9A of the base curriculum contains the measurement machinery.)

Cost per task. This is the total spend divided by completed tasks. Total spend includes model tokens, tool calls, storage, and compute. Two agents can have 90 percent success. They are not equal if one costs $0.40 per task. They are not equal if the other costs $4.00 per task.

Postings in 2026 name "cost per successful outcome" as the deciding metric. Teams use this metric to pick which agent stack to scale. Chapter 6 shows the math.

Recovery rate. Some runs fail. What share of these runs finish after a retry? What share finish after a checkpoint resume? What share finish after a human nudge? This number separates teams that fight flaky agents.

This number separates teams that absorb failure. This is the direct output of Chapter 4's reliability work.

Diagnostic numbers are below these. These numbers are: tool call error rate, average steps per task, and context overflow rate. They are: judge-human agreement, depth of the human review queue, and p99 task latency. The p99 task latency is the latency that 99 percent of tasks finish within. A core metric moves. The engineer examines these numbers to find the reason.

This role must avoid a trap: Do not tune the demo. Tune the system. A prompt works on five hand-picked tasks. A scaffold has no eval gate. This is a demo. Production work is boring by design.

It has pinned harnesses. It has versioned prompts. It has ledgered costs. It has a deploy gate that says no. The boring parts are the job.

Chapter 1: Agent architecture patterns

Step 1: the simplest version

An agent architecture is the shape of the loop. This loop is between the model, the tools, and the task. Three patterns cover most production systems.

ReAct (reason and act) is the simplest loop. The model thinks one step. It takes one action. It reads the observation. It repeats this. Thought, action, observation, thought, action, observation.

This continues until the model emits a final answer or hits the step budget. One model call per step. There is no separate planner.

Plan-and-execute splits the work in two. A planner model writes a full plan first. This is a list of steps. An executor then works the steps one by one. A replanner revises the plan when a step fails or surprises. Planning and acting use different prompts.

They often use different models.

Multi-agent splits the work across roles. A common trio is a planner, workers, and a critic. A planner drafts the approach. Workers execute sub-tasks in parallel. A critic checks each worker's output before the critic accepts it. The roles talk through a shared message board or a coordinator.

Each role can use a different model. Each role can use a different tool set. Each role can use a different budget.

How to read this diagram

  1. Start at the center. This is the language model. It only predicts text.
  2. Retrieval feeds it fresh facts. It was not trained on these facts.
  3. Tools let it act on the world. It can read files. It can call APIs. It can run code.
  4. Memory carries state across steps. This gives the loop continuity.

Step 2: why it matters

The pattern decides your failure modes. It decides your cost curve. It decides your latency profile. It does this before you write a line of prompt.

  • ReAct fails one step at a time. It is easy to debug. But it has no global view. It can wander on a 20-step task. Each step is sensible in its local context. But the system is lost in the global context.
  • Plan-and-execute keeps the global view. But it has a cost. The system writes the plan before it knows the world. So, wrong plans are common. Replanning is a second system to build.
  • Multi-agent systems parallelize well. They let you use a cheap model for easy roles. But coordination is a new failure point. Workers disagree. The critic becomes a bottleneck. Message formats change.

Pick the pattern by the task shape. Do not pick it by fashion.

ReAct: one loop, one model, one budget

How to read this diagram

  1. Start at the top box: Thought. The model reasons about the next step.
  2. Follow the arrow to Action. The model calls one tool with chosen arguments.
  3. Follow the arrow to Observation. The tool returns a result to the model.
  4. The arrow returns to Thought. The loop repeats with the new information.
  5. The loop exits on two conditions: the task is done, or the step budget is spent.

The parts

  • Thought. What it is: the model's reasoning step. Why it exists: it picks the next action from the history so far. If it fails: the agent picks the wrong tool or wrong arguments.
  • Action. What it is: one tool call. Why it exists: it changes the world or fetches data. If it fails: the error message guides the next thought.
  • Observation. What it is: the tool's result. Why it exists: it grounds the next thought in facts. If it fails: the model reasons from stale or wrong data.

The scaffold below is the complete ReAct loop. It has about 80 lines. Read it as the reference implementation for the rest of the track. Every later chapter plugs into this loop. This includes budgets, checkpoints, retries, and cost ledgers.

Source: Anthropic, "Building Effective Agents" (Dec 2024).

How to read this diagram

  1. The model receives the task and the tool list.
  2. It emits one action. This action is a tool name with arguments.
  3. The tool runs. Its output returns as an observation.
  4. The loop repeats. A final answer ends the run. The step budget ends it if there is no final answer.

import json
import re
import time
from dataclasses import dataclass, field

# ---------------------------------------------------------------------------
# Stand-in model. WHAT: a fake LLM with scripted responses so labs run free
# and deterministically. WHY: the scaffold (loop, budget, parsing) is the
# subject, not any real model's behavior. WHAT BREAKS if changed: if you
# swap this for a real API, keep the return contract identical (a plain
# string). Everything downstream parses that string.
# ---------------------------------------------------------------------------
class MockLLM:
    """Returns the next scripted response each time it is called."""

    def __init__(self, script):
        # script: list of strings, one per model call, in order.
        self.script = list(script)
        self.calls = 0

    def complete(self, prompt):
        # The prompt is ignored: determinism beats realism in a lab.
        # self.calls counts model calls so cost math stays honest.
        if self.calls >= len(self.script):
            raise RuntimeError("script exhausted at call %d" % self.calls)
        out = self.script[self.calls]
        self.calls += 1
        return out


# A tool is a named Python function with a text description.
# The scaffold exposes the description list to the model; the model picks
# a tool by name and supplies arguments as JSON.
@dataclass
class Tool:
    name: str
    description: str
    func: callable


@dataclass
class Step:
    """One recorded step of the trajectory."""
    thought: str
    action: str          # tool name, or "finish"
    action_input: dict
    observation: str
    latency_s: float


class ReActAgent:
    """WHAT: the ReAct control loop. WHY: the simplest agent that can use
    tools, and the baseline every fancier pattern must beat.
    WHAT BREAKS: the action parser below is strict on purpose. A loose
    parser hides model mistakes; a strict one surfaces them as errors you
    can count and fix."""

    def __init__(self, llm, tools, max_steps=10):
        self.llm = llm
        # index tools by name for O(1) lookup per step
        self.tools = {t.name: t for t in tools}
        self.max_steps = max_steps
        self.trajectory = []  # the full record; Chapter 7 mines this

    def _tool_list_text(self):
        return "\n".join(" - %s: %s" % (t.name, t.description)
                         for t in self.tools.values())

    def _parse_action(self, text):
        # Contract: the model emits either
        #   ACTION: <tool_name> {json args}
        #   FINAL: <answer text>
        # Strict regexes; anything else is a parse error, not a guess.
        m = re.match(r"ACTION:\s*(\w+)\s*(\{.*\})?", text.strip(), re.DOTALL)
        if m:
            name = m.group(1)
            args = json.loads(m.group(2) or "{}")
            return ("action", name, args)
        m = re.match(r"FINAL:\s*(.*)", text.strip(), re.DOTALL)
        if m:
            return ("finish", None, {"answer": m.group(1).strip()})
        return ("parse_error", None, {})

    def run(self, task):
        # The main loop. Each iteration costs exactly one model call plus
        # at most one tool call, which makes cost math trivial (Chapter 6).
        history = ""
        for step_n in range(self.max_steps):
            prompt = (
                "Task: %s\nTools:\n%s\nHistory:\n%s\n"
                "Respond with ACTION: <tool> {args} or FINAL: <answer>."
                % (task, self._tool_list_text(), history)
            )
            t0 = time.time()
            raw = self.llm.complete(prompt)
            thought = raw  # the whole output is the "thought" for the log
            kind, name, args = self._parse_action(raw)

            if kind == "finish":
                self.trajectory.append(Step(thought, "finish", args,
                                           args["answer"],
                                           time.time() - t0))
                return args["answer"]
            if kind == "parse_error" or name not in self.tools:
                obs = "ERROR: unknown action. Use ACTION: <tool> {args} or FINAL: <answer>."
            else:
                try:
                    # Tool runs inside try/except: a crashing tool must not
                    # crash the loop. The error becomes an observation and
                    # the model gets a chance to recover (Chapter 4 refines
                    # this into retry-with-judgment).
                    obs = str(self.tools[name].func(**args))
                except Exception as e:  # noqa: BLE001 - labs catch broadly on purpose
                    obs = "ERROR: tool %s failed: %s" % (name, e)
            self.trajectory.append(Step(thought, name or "parse_error",
                                        args, obs, time.time() - t0))
            history += "\nStep %d action: %s\nObservation: %s" % (step_n, raw, obs)
        return None  # budget exhausted without a FINAL

How to read this diagram

  1. The loop builds a prompt. It uses the task, the tool list, and the history so far.
  2. MockLLM.complete returns the next scripted response. A real model will generate it.
  3. _parse_action enforces the output contract. It uses strict regular expressions. Sloppy output becomes a visible parse error.
  4. A valid action runs its tool inside a try/except block. Tool crashes become observations. They do not become loop crashes.
  5. FINAL ends the run and returns the answer. Running out of steps returns None. The caller must handle this as a distinct outcome. It is not an answer.

Run it end to end with a two-tool task:

# --- a tiny lab task: add two numbers fetched from a fake store -----------
store = {"a": 21, "b": 21}

def fetch(key):
    # WHAT: fake data tool. WHY: stands in for any read-only API.
    return store[key]

def add(x, y):
    return x + y

tools = [
    Tool("fetch", "fetch(key): read a value from the store", fetch),
    Tool("add", "add(x, y): add two numbers", add),
]

script = [
    "ACTION: fetch {\"key\": \"a\"}",
    "ACTION: fetch {\"key\": \"b\"}",
    # NOTE: the script below pretends the model must add; a real model
    # would see observations 21 and 21 and compute 42.
    "ACTION: add {\"x\": 21, \"y\": 21}",
    "FINAL: 42",
]
agent = ReActAgent(MockLLM(script), tools, max_steps=10)
print(agent.run("What is a + b from the store?"))  # -> 42
print("model calls:", agent.llm.calls)             # -> 4
print("steps:", len(agent.trajectory))             # -> 4

There are four model calls. There are three tool calls. There is one answer. This is the unit of work that this track optimizes.

Plan-and-execute: plan once, then work the plan

The planner writes numbered steps. The executor runs them. A monitor watches for surprise. It triggers a replan. The scaffold below reuses the same MockLLM and Tool classes.

How to read this diagram

  1. Step one runs. It produces an output.
  2. The gate checks the output against the step contract.
  3. If it passes, the next step runs with the output as input. If it fails, the run exits or replans.
  4. No step ever runs on a bad input from the step before.

class PlanExecuteAgent:
    """WHAT: separate planning from acting. WHY: long tasks need a global
    view that ReAct's one-step-at-a-time loop loses. WHAT BREAKS: the plan
    is a guess about the future. Without the replan path below, a wrong
    step-2 poisons steps 3-10 silently."""

    def __init__(self, llm, tools, max_steps=12):
        self.llm = llm
        self.tools = {t.name: t for t in tools}
        self.max_steps = max_steps
        self.trajectory = []

    def _plan(self, task):
        # Planner prompt: produce a numbered list, nothing else.
        raw = self.llm.complete("Plan for task: %s\nNumbered steps only." % task)
        steps = [l.strip(" .") for l in raw.splitlines()
                 if l.strip() and l.strip()[0].isdigit()]
        return steps

    def _execute_step(self, step_text):
        # Executor prompt: one step in, one action out. Same strict
        # ACTION/FINAL contract as ReAct so tooling is shared.
        raw = self.llm.complete("Do this step: %s\nTools: %s\nReply ACTION or FINAL."
                                % (step_text, list(self.tools)))
        m = re.match(r"ACTION:\s*(\w+)\s*(\{.*\})?", raw.strip(), re.DOTALL)
        if not m or m.group(1) not in self.tools:
            return "ERROR: bad action: %s" % raw.strip()
        try:
            return str(self.tools[m.group(1)].func(**json.loads(m.group(2) or "{}")))
        except Exception as e:  # noqa: BLE001
            return "ERROR: %s" % e

    def run(self, task):
        plan = self._plan(task)
        results = []
        for i, step_text in enumerate(plan):
            obs = self._execute_step(step_text)
            results.append((step_text, obs))
            self.trajectory.append((step_text, obs))
            # Replan trigger: an ERROR observation invalidates the rest of
            # the plan, because later steps assumed this one worked.
            if obs.startswith("ERROR") and i < len(plan) - 1:
                plan = self._plan(task + " (previous attempt failed at: %s -> %s)"
                                  % (step_text, obs))
                # cap total work: replanning must not restart the budget
                if len(self.trajectory) >= self.max_steps:
                    break
        return results

The replan trigger is the key line. A plan-and-execute system without replanning is only a script with extra steps. The replan prompt includes the failure. So, the new plan routes around it.

Multi-agent: planner, workers, critic

There are three roles. There is one shared task board. Workers run in sequence here. Parallelism is an executor detail. The protocol is what matters.

How to read this diagram

  1. The orchestrator receives the task. It splits the task into sub-tasks.
  2. Each worker runs one sub-task. It uses its own tools and budget.
  3. Workers report back. Failures stay local to one worker.
  4. The synthesizer merges the sub-results. It makes the final answer.

class MultiAgentTeam:
    """WHAT: role-separated agents coordinating through a shared board.
    WHY: lets you spend a strong model on planning and critique while
    cheap models do the legwork (Chapter 6 prices this). WHAT BREAKS:
    role outputs are free text by default. The critic below enforces a
    PASS/FAIL verdict format; without it, workers cannot tell acceptance
    from commentary."""

    def __init__(self, planner_llm, worker_llm, critic_llm):
        self.planner = planner_llm
        self.worker = worker_llm
        self.critic = critic_llm
        self.board = []  # shared message board: every role reads everything

    def _post(self, role, text):
        self.board.append({"role": role, "text": text})

    def run(self, task):
        # 1. Planner decomposes the task into sub-tasks.
        plan = self.planner.complete("Decompose into sub-tasks: %s" % task)
        self._post("planner", plan)
        subtasks = [l.strip(" .") for l in plan.splitlines()
                    if l.strip() and l.strip()[0].isdigit()]
        accepted = []
        # 2. Each sub-task goes to a worker, then to the critic.
        for st in subtasks:
            board_view = "\n".join("%s: %s" % (m["role"], m["text"]) for m in self.board)
            work = self.worker.complete("Board:\n%s\nDo sub-task: %s" % (board_view, st))
            self._post("worker", work)
            verdict = self.critic.complete("Sub-task: %s\nWork: %s\nReply PASS or FAIL: reason"
                                           % (st, work))
            self._post("critic", verdict)
            # 3. Only PASSed work is accepted. FAIL sends the sub-task
            # back to the worker once, with the critic's reason attached.
            if verdict.strip().upper().startswith("PASS"):
                accepted.append((st, work))
            else:
                retry = self.worker.complete("Redo sub-task: %s\nCritic said: %s" % (st, verdict))
                self._post("worker-retry", retry)
                accepted.append((st, retry))  # accepted with a flag in real code
        return accepted

This is the loop. One retry per sub-task occurs. Then the system moves on. Source: Anthropic, "Building Effective Agents" (Dec 2024).

How to read this diagram

  2. The evaluator scores the solution against the acceptance bar.
  3. If accepted, the solution ships. If rejected, feedback goes back to the generator.
  4. The loop tries again a fixed number of times. This is bounded retries. Then the system escalates.

Perform one retry per sub-task. Then move on. Unbounded retries make multi-agent systems use budgets. The systems look busy.

Chapter 2: Tool design for agents

Chapter 1 fixed the loop's shape. A loop with no tools is a model talking to itself. Every real agent acts through tools. This chapter designs the tools. The model can then use them.

Step 1: the simplest version

Tools are the agent's hands. Tools are the functions that the agent can call. The agent uses these functions to read and change the world. Tool design is the craft of making these functions safe and clear for a model caller. The audience of a tool's interface is not a human developer. It is a language model.

The language model cannot read your mind. It cannot open your source code. It will confidently call your function with the wrong arguments at 3 a.m.

Good tool design has three parts. First, an API shape that the model can use. This means a narrow scope, typed inputs, and predictable outputs. Second, error messages written as agent UX. The model reads the error text. This text determines if the model recovers.

Third, idempotency. If you call the tool twice, the effect is the same as calling it once.

Step 2: why it matters

Look at the failed agent trajectories for any week. Count the causes of failure. In most teams, tool-call errors are the largest single group. These errors include wrong argument names, missing required fields, ambiguous outputs that the model misreads, and side effects. These side effects fire twice because a retry re-ran a non-idempotent call. Each of these is a design defect.

It is not a model defect. If a model fails your tool 10 percent of the time, the tool is unclear. Fix the tool before you blame the model.

API shape agents can use

How to read this diagram

  1. Top row, left to right: name, description, input schema. These tell the model what the tool is and how to call it.
  2. Bottom row: output schema, error messages, idempotency key. These tell the model what comes back and make retries safe.
  3. Read each box's two lines. They state the rule for that part.

The parts

  • Name. What it is: a verb phrase like search_orders. Why it exists: the model picks tools by name. If it fails: the model calls the wrong tool.
  • Description. What it is: when to use the tool and when not to. Why it exists: it stops misuse before it happens. If it fails: the agent uses the tool for the wrong job.
  • Input schema. What it is: typed fields, required versus optional, with examples. Why it exists: it makes valid calls the default. If it fails: every call needs a repair round.
  • Output schema. What it is: the predictable shape of the result. Why it exists: the model can parse it without guessing. If it fails: the agent misreads the result.
  • Error messages. What it is: what went wrong and what to try next. Why it exists: the error is the user interface of the tool. If it fails: the agent retries blindly.
  • Idempotency key. What it is: a key that makes repeats safe. Why it exists: the same key gives the same result, so retries cannot double-charge. If it fails: a retry can cause real damage.

There are four rules. Each rule comes from production failures.

1. One tool, one verb. Use send_refund(order_id). Do not use manage_order(action="refund", order_id=...). Models handle concrete verbs well. They handle stringly-typed dispatch badly.

If a tool needs an action parameter with five options, it is five tools. Split it.

2. Typed, validated inputs. Each argument has a type. The tool validates before it acts. Validation errors return as data. Refer to the error messages below.

Validation errors do not return as stack traces. A stack trace has 40 lines. The model cannot use it. A validation message has one line. The model can use it.

3. Narrow scopes and safe defaults. A search_files tool reads the whole filesystem. It will read something that it must not read. Scope tools to the directories, tables, or accounts that the task needs. Defaults must be the safe choice.

Use dry_run=True on mutating tools. Cap pagination. Writes need explicit confirmation flags.

4. Predictable outputs. Return the same shape each time. This includes a status, the data, and a short summary. The summary must be readable by humans and models. Models learn output shapes from examples.

A tool returns a dict on success. It returns a string on failure. This teaches the model nothing.

THE FOUR RULES, SIDE BY SIDE
GOOD TOOL                              BAD TOOL
send_refund(order_id)                  manage_order(action="refund", ...)
  one verb, concrete                     five tools wearing a trench coat

typed inputs, validated                untyped inputs, stack trace on error
  before acting                          (40 lines the model cannot use)

The registry below enforces these rules in code. It is also the piece Chapter 5's MCP server wraps.

import inspect
from dataclasses import dataclass

# ---------------------------------------------------------------------------
# Tool registry with machine-checkable schemas.
# WHAT: every tool declares typed parameters; the registry validates calls
# before the function runs. WHY: validation-before-action turns model
# mistakes into cheap, readable errors instead of half-executed side
# effects. WHAT BREAKS if changed: if you skip validation for "simple"
# tools, the first malformed call will execute with garbage inputs.
# ---------------------------------------------------------------------------
@dataclass
class Param:
    name: str
    type: type
    required: bool = True
    description: str = ""

class ToolDef:
    def __init__(self, name, description, func, params, read_only=True):
        self.name = name
        self.description = description
        self.func = func
        self.params = {p.name: p for p in params}
        # read_only=False marks tools with side effects. The scaffold uses
        # this flag for dry-run defaults and human-review gates (Ch 4).
        self.read_only = read_only

    def schema_text(self):
        # The exact text the model sees. Keep it short: name, one-line
        # description, and typed params. Long schemas cost tokens on every
        # step and models skim them.
        lines = ["%s: %s" % (self.name, self.description)]
        for p in self.params.values():
            req = "required" if p.required else "optional"
            lines.append("  %s (%s, %s): %s"
                         % (p.name, p.type.__name__, req, p.description))
        return "\n".join(lines)

    def call(self, **kwargs):
        # Validate everything before touching the world.
        for pname, p in self.params.items():
            if p.required and pname not in kwargs:
                return {"status": "error",
                        "error": "missing required argument '%s'. Got: %s"
                                 % (pname, sorted(kwargs))}
            if pname in kwargs and not isinstance(kwargs[pname], p.type):
                return {"status": "error",
                        "error": "argument '%s' must be %s, got %s"
                                 % (pname, p.type.__name__,
                                    type(kwargs[pname]).__name__)}
        try:
            result = self.func(**kwargs)
        except Exception as e:  # noqa: BLE001
            # Never leak a stack trace to the model. One line it can act on.
            return {"status": "error",
                    "error": "%s failed: %s" % (self.name, e)}
        return {"status": "ok", "data": result}

    if customer_id not in fake_db:
        raise KeyError("unknown customer_id '%s'" % customer_id)
    return fake_db[customer_id]

lookup_customer = ToolDef(
    name="lookup_customer",
    description="Read a customer record by id. Read-only.",
    func=_db_lookup,
    params=[Param("customer_id", str, True, "e.g. 'c100'")],
    read_only=True,
)

print(lookup_customer.call(customer_id="c100"))
print(lookup_customer.call(customer_id=100))      # typed error, no crash

The API has a shape. But tools fail. When tools fail, the error message is the only signal that the model gets.

Error messages as agent UX

The model reads each error message that your tools emit. You do not read it. Write it like UI copy for a user. This user is smart, fast, and literal.

Bad: ERROR 422. Good: order_id 'o99' not found. Known ids: o12, o13. Did you mean o12?

Bad: Invalid input. Good: start_date 'next friday' is not a date. Use YYYY-MM-DD, e.g. 2026-10-02.

There are three rules for agent-facing errors:

  1. Say what was wrong. Use the caller's terms. Name the argument and the value that the tool received.
  2. Say what valid looks like. Give the format and one concrete example.
  3. Offer the next action. Suggest the corrected call. Or name the tool that produces the missing value. For example, "call list_orders first to get a valid order_id".

Then log the raw error separately for humans. The model gets the friendly line. Your logs keep the stack trace. Both audiences get what they need.

ANATOMY OF A GOOD ERROR MESSAGE
1. WHAT WAS WRONG (in the caller's terms)
     order_id 'o99' not found.            <- names the argument + the value

  2. WHAT VALID LOOKS LIKE (format + example)
     Known ids: o12, o13.                 <- one concrete example

  3. THE NEXT ACTION (the corrected call)
     Did you mean o12?                    <- or: call list_orders first

  BAD:  ERROR 422                         <- names nothing, helps nobody
  GOOD: the three parts above             <- the model can act on it

  Measured: rewriting 14 tool errors to this format cut the
  tool-error retry rate from 31% to 9%, no model or prompt change.

This is a worked example of the measured difference. A team rewrote 14 tool error messages to this format. The tool-error retry rate on a fixed evaluation set fell from 31 percent to 9 percent. There was no model or prompt change. The errors were the bug.

Idempotency: the retry contract

Agents retry. Networks fail during a call. Timeouts do not always show the true status. The tool may succeed even if the agent sees a timeout. If calling a tool twice is not safe, your agent will eventually charge twice, send twice, or write twice. Idempotency means that the second identical call has no additional effect.

The standard mechanism is the idempotency key. The caller passes a unique key for each logical operation. The tool remembers which keys it has already used.

import hashlib
import json

# ---------------------------------------------------------------------------
# Idempotency wrapper.
# WHAT: remembers executed keys and returns the stored result on replay.
# WHY: retries after ambiguous failures (timeouts) are then safe: the
# model can retry without fear of double side effects. WHAT BREAKS: if
# the key does not capture the full operation (same key, different args),
# a replay returns a stale result for a different request. The key must
# hash the operation name AND the arguments.
# ---------------------------------------------------------------------------
class Idempotent:
    def __init__(self, func, op_name):
        self.func = func
        self.op_name = op_name
        self._done = {}  # key -> result. Production: a durable store.

    def key_for(self, **kwargs):
        # Deterministic key from operation + sorted arguments.
        blob = json.dumps([self.op_name, sorted(kwargs.items())],
                          sort_keys=True, default=str)
        return hashlib.sha256(blob.encode()).hexdigest()[:16]

    def call(self, idempotency_key=None, **kwargs):
        key = idempotency_key or self.key_for(**kwargs)
        if key in self._done:
            # Replay: same result, zero side effects.
            return {"status": "ok", "data": self._done[key],
                    "note": "replay of earlier call"}
        result = self.func(**kwargs)
        self._done[key] = result
        return {"status": "ok", "data": result}

# --- demo: a mutating tool that must not double-fire -------------------------
sent = []

def _send_email(to, subject):
    sent.append((to, subject))   # the "side effect"
    return "queued"

safe_send = Idempotent(_send_email, "send_email")
k = safe_send.key_for(to="a@example.com", subject="hi")
print(safe_send.call(idempotency_key=k, to="a@example.com", subject="hi"))
print(safe_send.call(idempotency_key=k, to="a@example.com", subject="hi"))
print("emails actually sent:", len(sent))  # -> 1, not 2

Two calls have one side effect. The retry path in Chapter 4 calls tools through this wrapper. This makes "retry with judgment" safe.

A dry-run flag completes the picture for mutating tools: send_email(to, subject, dry_run=True) returns what would happen without doing it. The agent can rehearse a risky action, show the plan to a human reviewer (Chapter 4), and only then run it for real.

Watch out: the common misunderstanding

"Tool design is prompt engineering." This is not true. Prompts describe tools. Design decides what the tools are. No prompt can fix a tool that has five verbs, untyped inputs, and non-idempotent writes. Tool errors can be the main cause of your failure clusters (Chapter 7). In this case, fix the tool code.

This fix usually takes one hour. It gives a bigger success-rate gain than one week of prompt tuning.

Follow the arrows from the model's action. Validation happens before anything touches the world. Failures loop back to the model as readable errors. Mutating tools pass through the idempotency check. This makes retries safe. Every path ends in the same output shape.

  • Use one tool and one verb. Validate typed inputs before the action. Use narrow scopes and safe defaults.
  • Error messages are agent UX. Name the bad value. Show a valid example. Suggest the next call.
  • Idempotency keys make retries safe. Dry-run flags make risky actions rehearsable.

Chapter 3: Context management at scale

Tools work. Now run the loop long enough. It will hit the wall that every agent hits: the context window. This chapter describes what lives past it. This includes compaction, memory, retrieval per step, and checkpoints.

Step 1: the simplest version

Context management is the process of deciding what the model sees at each step. It covers which history to keep exactly, what to summarize, what to get when needed, and what to remove. The context window is the agent's working memory. It is its scarcest resource. Every token in the prompt costs money at every step. It also makes the step slower.

(Attention cost increases with sequence length, as per Volume 4). It also reduces the model's focus. A 100k-token prompt does not get 100k tokens of attention. It gets a model that is less good at finding the 200 tokens that are important.

Three mechanisms do the job. Compaction makes a dense replacement from older history. Memory systems store facts outside the prompt. They retrieve facts when the facts are relevant. Retrieval for agents gets new information for each step. It does not preload all information.

Step 2: why it matters

Long agent runs stop in three ways. All three ways are context failures. The run reaches the window limit and stops. The run stays inside the window. But the bill becomes too high. This happens because each of 40 steps sends the full history again.

Or the run stays inside the window and stays cheap. But the model loses the thread. The key fact from step 3 is under 60k tokens of tool output. The model stops to use it. Compaction, memory, and retrieval each fix one of these stops.

  • Scratchpad. What it is: space for the current thought. Why it exists: reasoning needs room. If it fails: thoughts get cut mid-sentence.
  • Free space. What it is: the unclaimed remainder. Why it exists: it is your safety margin. If it fails: there is no room to recover.

Compaction: summarize the past, keep the future

How to read this diagram

  1. Left box: before. The full transcript with every thought and tool call.
  2. The arrow is the summarize step. A model writes the summary.
  3. Right box: after. Goal, key facts, open items, next step.
  4. Keep the four items in the right box. Drop the exact wording of old steps.

The parts

  • Summary. What it is: a short rewrite of the history. Why it exists: it frees context for the work ahead. If it fails: key facts are lost and the agent repeats old mistakes.
  • Kept items. What they are: goal, facts learned, open items, next step. Why they exist: the agent needs them to continue correctly. If they fail: the run restarts from zero.
  • Dropped detail. What it is: the exact wording of old steps. Why drop it: wording costs tokens and adds no decisions. If it is kept: the budget burns for no gain.

This is the pattern: every N steps, or when the token count goes over a limit, replace the oldest steps with a summary. Keep three things exactly as they are: the original task, the most recent K steps, and any facts the summary marks as load-bearing. These facts include ids, decisions, and user constraints.

How to read this diagram

  1. Before: every step stays in context. Cost increases and the window fills.
  2. After: the oldest steps become a summary card. The original task, the recent K steps, and load-bearing facts stay exactly as they are.
  3. The design knob is aggression. If it is too aggressive, it drops facts. If it is too timid, the window overflows.

# ---------------------------------------------------------------------------
# Compaction for a ReAct-style history.
# WHAT: replaces old steps with a summary once history grows past a
# budget. WHY: keeps long runs inside the window and inside the cost
# budget without losing decisions. WHAT BREAKS if changed: summarizing
# too aggressively drops load-bearing facts (order ids, user constraints).
# The KEEP markers below are the defense: anything tagged keep=true in
# a step survives compaction verbatim.
# ---------------------------------------------------------------------------
class Compactor:
    def __init__(self, summarizer, keep_last=4, trigger_tokens=6000):
        # summarizer: callable(list_of_steps) -> summary string. In labs
        # this is a deterministic stub; in production it is a cheap model.
        self.summarizer = summarizer
        self.keep_last = keep_last
        self.trigger_tokens = trigger_tokens
        self.summaries = []  # audit trail of what was compacted away

    def _tokens(self, steps):
        # Rough estimate: 1 token ~ 4 chars. Good enough for budgeting;
        # production uses the real tokenizer (Volume 4).
        return sum(len(s.get("text", "")) // 4 for s in steps)

    def maybe_compact(self, steps):
        # steps: list of {"text": ..., "keep": bool}. Returns the working
        # set: [summary of old] + [kept facts] + [recent steps].
        if self._tokens(steps) < self.trigger_tokens:
            return steps
        cutoff = len(steps) - self.keep_last
        old, recent = steps[:cutoff], steps[cutoff:]
        kept = [s for s in old if s.get("keep")]
        summary = self.summarizer([s for s in old if not s.get("keep")])
        self.summaries.append(summary)
        return ([{"text": "[SUMMARY of steps 0-%d]: %s" % (cutoff - 1, summary)}]
                + kept + recent)

    counts = {}

Memory systems: facts that outlive the run

Working memory is the prompt. All other things are memory systems. There are three useful kinds.

How to read this diagram

  1. Episodic: past paths indexed by task similarity. Retrieved as worked examples.
  2. Semantic: a small structured store of world facts. Queried like a database.
  3. Procedural: the scaffold's own playbooks. These include retry rules, review points, and tool checklists.

Episodic memory stores what happened. It stores past paths, indexed by task similarity. If a new task is like an old task, the agent retrieves the old path as a worked example. To build this, embed the task text. Do a nearest-neighbor search over stored paths. Inject the top 1-2 as few-shot context.

Semantic memory stores facts about the world. These facts include customer tiers, product ids, and policy rules. This is a small structured store. It is a table or a document set. It is not a vector index. The agent queries it like a database.

It is where "gold-tier customers get free return shipping" lives. So it does not have to live in the prompt.

Procedural memory stores how to do things. It stores tool-use recipes that the team has learned. For example, "to refund, first call lookup_order, then check policy, then issue_refund with dry_run". These are versioned documents. Humans review them. The system injects them when relevant.

  Carries the task, recent steps, and POINTERS ("memory available: policy docs").

The rule for all three: retrieve memory, never preload it. The prompt carries pointers ("memory available: policy docs, past refunds"), and a retrieval step fetches the specific item. Preloading the whole memory into every prompt is how teams burn 50k tokens before the task starts.

# ---------------------------------------------------------------------------
# Minimal memory store: semantic facts + episodic trajectories.
# WHAT: a tiny in-memory version of the pattern. WHY: shows the
# retrieve-don't-preload discipline in 40 lines. WHAT BREAKS: with no
# relevance scoring, retrieval returns junk. The score functions below
# are deliberately simple (keyword overlap); production uses embeddings
# (Volume 9), but the call pattern is identical.
# ---------------------------------------------------------------------------
class Memory:
    def __init__(self):
        self.facts = []        # (text, keywords)
        self.episodes = []     # (task_text, keywords, outcome)

    def add_fact(self, text, keywords):
        self.facts.append((text, set(keywords)))

    def add_episode(self, task_text, keywords, outcome):
        self.episodes.append((task_text, set(keywords), outcome))

    def _score(self, query_words, keywords):
        # Jaccard-ish overlap (Jaccard: size of the overlap divided by size of the union). Simple, explainable, good enough for labs.
        q = set(query_words)
        return len(q & keywords) / max(len(q | keywords), 1)

    def retrieve(self, query, k=2):
        words = query.lower().split()
        scored = [(self._score(words, kw), t)
                  for t, kw in self.facts]
        scored += [(self._score(words, kw), "PAST CASE: " + t + " -> " + o)
                   for t, kw, o in self.episodes]
        scored.sort(reverse=True)
        # Only return items with nonzero relevance. Silence beats noise:
        # an irrelevant memory in the prompt is worse than no memory.
        return [t for s, t in scored[:k] if s > 0]

mem.add_fact("Gold-tier customers get free return shipping.",
             ["gold", "tier", "return", "shipping"])
mem.add_episode("refund for late delivery", ["refund", "late", "delivery"],
                "issued refund after policy check")
print(mem.retrieve("customer wants a refund for late delivery"))
print(mem.retrieve("what is the weather"))  # -> [] : silence beats noise

Watch out: the common misunderstanding

"Bigger context windows removed the need for context management." They removed the crash. They did not remove the cost. They did not remove the focus problem. A run fits in a 1M-token window. But it re-sends 200k tokens per step for 30 steps. This is a $20 task.

A compacted version does it for $2. The model still attends worse over long contexts. The famous lost-in-the-middle effect means your key fact at position 40k gets less weight. The same fact at position 400 gets more weight. Compaction and retrieval put the correct tokens in the correct positions. They do not just make it fit.

Chapter 4: Reliability engineering for agents

Long-running agents do not just run out of memory. They fail in new ways. They fail silently at 3 a.m. This chapter makes the loop trustworthy. It uses retries with judgment. It uses human review points.

It uses the eval gate that decides what ships.

Step 1: the simplest version

Reliability engineering for agents is a set of mechanisms. These mechanisms let a multi-step run survive failures. The run will inevitably hit failures. The set includes checkpoints. Checkpoints are saved states. The run can resume from these states.

It includes retries with judgment. This means retrying only the failures that retrying fixes. It includes human-in-the-loop review points on risky actions. It includes eval-gated deployment. A changed agent ships only if the eval suite still passes. Together, these determine the recovery rate from Part 0.

Step 2: why it matters

An agent succeeds 90 percent of the time on step 1 of a 20-step task. It succeeds about 12 percent of the time on the whole task. This is true if failures are independent and unrecovered (0.9^20). This math shows why reliability is not a polish step. Without checkpoints and smart retries, long-horizon agents do not work. With them, the same per-step reliability compounds into a usable system.

Each failure becomes a resume instead of a restart.

Step 3: the full picture, piece by piece

The sections below build the full picture one piece at a time. Each piece ends in runnable code. Climb them in order; every visual marks a new rung on the ladder.

Retrieval feeds the run. Checkpoints protect it.

  3. Next: human-in-the-loop. A person reviews risky actions before they run.
  4. Top: eval-gated deployment. A change ships only if the eval suite passes.

  • Human-in-the-loop. What it is: a person reviews risky actions. Why it exists: some actions cannot be undone. If it fails: the agent takes irreversible actions alone.
  • Eval-gated deployment. What it is: the eval suite as a release valve. Why it exists: it stops regressions from shipping. If it fails: bad changes reach users.

Checkpoints: resume, do not restart

A checkpoint is a snapshot. It holds all data that is necessary to continue. It holds the step number. It holds the compacted history. It holds the variable state. It holds the idempotency keys of completed side effects.

This prevents a resume from re-firing the side effects. The scaffold checkpoints after every step. Storage is not expensive. Re-running 20 steps is expensive.

How to read this diagram

  1. Numbered steps run from left to right. Flags mark checkpoints every K steps.
  2. The crash at step 8 does not return to step 0. It resumes from checkpoint 5.
  3. The rule: the resume path is the normal path. Test it before you need it.

import copy
import json
import os

# ---------------------------------------------------------------------------
# Checkpointing for a step-based agent loop.
# WHAT: saves (step_index, state) to disk after each step; resume() picks
# up where a crashed run stopped. WHY: turns a failure at step 24 of 30
# into 6 more steps instead of 30 restarted steps. WHAT BREAKS: if the
# checkpoint omits the idempotency keys of finished side effects, a
# resume re-fires them (double refund). The keys MUST be in the snapshot.
# ---------------------------------------------------------------------------
class Checkpointer:
    def __init__(self, path):
        self.path = path

    def save(self, step_index, state):
        # Deep-copy so later mutation of `state` cannot corrupt the
        # snapshot. Atomic write via rename: a crash mid-write must not
        # leave a half-written checkpoint.
        snap = {"step": step_index, "state": copy.deepcopy(state)}
        tmp = self.path + ".tmp"
        with open(tmp, "w") as f:
            json.dump(snap, f, default=str)
        os.replace(tmp, self.path)

    def load(self):
        if not os.path.exists(self.path):
            return None
        with open(self.path) as f:
            snap = json.load(f)
        return snap["step"], snap["state"]

    def clear(self):
        if os.path.exists(self.path):
            os.remove(self.path)

# --- demo: a 5-step job that "crashes" at step 3, then resumes -------------
def run_job(steps, ckpt, fail_at=None):
    loaded = ckpt.load()
    # start_after: the first step NOT yet checkpointed.
    start_after, state = loaded if loaded else (-1, {"done": []})
    for i in range(start_after + 1, len(steps)):
        if fail_at is not None and i == fail_at:
            raise RuntimeError("simulated crash at step %d" % i)
        state["done"].append(steps[i])          # do the work
        ckpt.save(i, state)                      # then checkpoint it
    ckpt.clear()
    return state

ckpt = Checkpointer("/tmp/track06_demo.ckpt")
if os.path.exists(ckpt.path):
    os.remove(ckpt.path)
try:
    run_job(["a", "b", "c", "d", "e"], ckpt, fail_at=3)
except RuntimeError as e:
    print("crashed:", e)
print("resumed result:", run_job(["a", "b", "c", "d", "e"], ckpt)["done"])
# -> ['a', 'b', 'c', 'd', 'e']: steps a-c were NOT redone.

Make a checkpoint after the work. Do not make a checkpoint before the work. A checkpoint written before the side effect fires will skip work. This work never happened on resume.

Retries with judgment: classify, then decide

How to read this diagram

  1. Top: a tool call fails. Move to the diamond: what type of error is it.
  2. Left: transient, like a rate limit or timeout. Wait, then retry with backoff.
  3. Middle: agent mistake, like bad arguments. Fix the call, then retry once.
  4. Right: do not retry, like auth or config errors. Stop and alert a human.
  5. The rule at the bottom: two failures of the same kind in a row means escalate, not a third retry.

The parts

  • Transient. What it is: a temporary failure like a timeout. Why the branch exists: waiting fixes it. If misclassified: you alert a human for a blip.
  • Agent mistake. What it is: a bad call by the agent. Why the branch exists: a fixed call often works. If misclassified: you retry a broken call forever.
  • Do not retry. What it is: auth, config, or budget errors. Why the branch exists: retries cannot fix these. If misclassified: you burn budget on hopeless retries.

Blind retry makes agents use too much money. It retries a deterministic error ten times. For example, "order not found". Or it retries a stuck loop. This loop will fail in the same way. A classifier in front of the retry is the fix.

Every failure gets one of four labels.

How to read this diagram

  1. Classify first: transient, agent error, stuck, or unknown.
  2. Transient gets exponential backoff and another try. An agent error goes back to the model one time for a corrected call. Then it escalates. Break a stuck loop. Replan, compact, or give it to a human. Unknown escalates with the full error attached.
  • Transient. Network timeout, rate limit, flaky service. Retry with backoff. Retries are for these failures.
  • Agent error. Bad arguments, wrong tool, parse failure. Do not retry the same call. Give the error back to the model one time. It often corrects itself. Then escalate.
  • Stuck. The same action repeats. No progress across steps. Never retry. Break the loop. Replan, compact, or give it to a human.
  • Unknown. The failure matches no pattern. Do not guess a retry. Escalate with the full error and recent actions attached.

import time

# ---------------------------------------------------------------------------
# Retry with judgment.
# WHAT: classifies each failure, then picks retry / replan / escalate.
# WHY: blind retries multiply cost without raising success; classified
# retries spend the budget where it works. WHAT BREAKS: misclassifying a
# deterministic error as transient causes the classic 10-identical-retries
# burn. The classifier below is conservative on purpose: unknown errors
# escalate rather than retry.
# ---------------------------------------------------------------------------
def classify_failure(error_text, recent_actions):
    t = error_text.lower()
    # Stuck detection: same action 3 times in a row means the loop, not
    # the world, is the problem.
    if len(recent_actions) >= 3 and len(set(recent_actions[-3:])) == 1:
        return "stuck"
    if any(w in t for w in ("timeout", "rate limit", "503", "connection",
                            "temporarily", "try again")):
        return "transient"
    if any(w in t for w in ("not found", "invalid", "missing", "unknown",
                            "parse", "forbidden")):
        return "agent_error"
    return "unknown"  # conservative: escalate, do not retry

def run_with_retry(action_fn, max_retries=3, recent_actions=()):
    # action_fn: zero-arg callable returning a result or raising.
    # Returns (result, outcome) where outcome names what happened.
    for attempt in range(max_retries + 1):
        try:
            return action_fn(), "ok"
        except Exception as e:  # noqa: BLE001
            kind = classify_failure(str(e), recent_actions)
            if kind == "transient" and attempt < max_retries:
                time.sleep(2 ** attempt)  # exponential backoff: 1s, 2s, 4s
                continue
            if kind == "agent_error":
                return None, "agent_error: fix the call, do not retry it"
            return None, "%s: escalate" % kind
    return None, "transient: retries exhausted, escalate"

Human-in-the-loop: review points on risky actions

Some actions must never run without a human. For example, sending money, deleting data, contacting a customer, or changing access. The pattern is a review gate. The agent prepares the action with dry_run=True from Chapter 2. The action waits in a queue. A human approves or rejects it.

Only approval executes it for real.

How to read this diagram

  1. The agent proposes an action. The risk check classifies it.
  2. Read-only actions are low risk. They execute directly.
  3. Write and delete actions are high risk. A human approves, edits, or rejects them.

# ---------------------------------------------------------------------------
# Human review gate.
# WHAT: risky actions pause for human approval; the queue is the audit
# trail. WHY: bounds the blast radius of a confused agent. A wrong
# answer is embarrassing; a wrong refund is a loss. WHAT BREAKS: a gate
# that the agent can skip by calling the raw tool directly is theater.
# Enforcement must live in the tool layer (refuse non-dry-run calls
# without an approval token), not in the prompt.
# ---------------------------------------------------------------------------
class ReviewGate:
    def __init__(self):
        self.queue = []  # each item: dict with action + approval=None

    def submit(self, action_desc, dry_run_result):
        # action_desc: what will run. dry_run_result: rehearsal output.
        item = {"action": action_desc, "rehearsal": dry_run_result,
                "approval": None}
        self.queue.append(item)
        return len(self.queue) - 1  # the ticket id

    def decide(self, ticket, approved, reviewer="human"):
        self.queue[ticket]["approval"] = approved
        self.queue[ticket]["reviewer"] = reviewer

    def pending(self):
        return [i for i, it in enumerate(self.queue)
                if it["approval"] is None]

Eval-gated deployment: the release valve

The last reliability mechanism is not in the run. It is in the release process. No prompt change, tool change, or model swap ships until the eval suite passes. The gate from Supplement 9A runs a fixed task set. It compares the success rate and cost per task against the pinned baseline. It requires both to hold.

Or the success must rise enough to justify a cost rise. The mechanics are:

  1. Pin every agent version. This includes the prompt text hash, the tool registry version, and the model id.
  2. CI runs the eval set on every change. The suite is the same harness that the team uses for measurement. So "passes evals" means "measured on the real rig."
  3. Promotion needs: success rate within the confidence interval of baseline or better (Supplement 11A). Cost per task not worse than baseline plus the agreed tolerance. No new failure cluster in the trajectory sample (Chapter 7).
  4. A canary runs the new version on a small share of live traffic first. It has automatic rollback if the live numbers diverge from eval.

How to read this diagram

Changes flow top to bottom. They can only move forward through gates. The two rollback paths are normal outcomes. They are not emergencies. (CI rejects the changes, or the team rolls them back from canary.) A healthy team sees rejections each week. A team that never sees a rejection has a gate that never says no.

Watch out: the common misunderstanding

"Retries make agents reliable." Retries make transient failures survivable. They do nothing for agent errors (same bad call, same error, ten times) and they actively hide stuck loops (the run looks busy while making no progress). Reliability comes from classification first: know which failure you have, then pick the mechanism. The classifier is ten lines. The missing classifier is the most common reliability bug in agent systems.

Key takeaways

  • Checkpoint after each step. Include idempotency keys. Resume. Do not restart.
  • Classify every failure. If it is transient, retry. If it is an agent error, fix the call. If it is stuck, break the loop. Unknown failures escalate.
  • Risky actions wait for human approval. This approval occurs through a queue with an SLA. Enforcement lives in the tool layer. It does not live in the prompt.
  • Nothing ships without passing the eval gate. Rejections are normal.

Chapter 5: MCP and agent protocols in practice

A reliable agent still needs to touch the world. This chapter is the plumbing. It covers MCP for tools and data. It covers A2A for agent-to-agent handoffs. These are built and hardened in practice.

Step 1: the simplest version

Agents multiply. They need standard ways to talk to tools and to each other. Two protocol families are important in 2026.

MCP (Model Context Protocol) is the standard to connect a model to tools and data. An MCP server shows capabilities (tools, data sources, prompt templates) with a uniform interface. An MCP client (built into the agent host) finds those capabilities and calls them. The purpose is to decouple. The team that writes the refund tool and the team that writes the agent do not need to agree on anything except the protocol.

A2A (agent-to-agent) patterns are the conventions for agents to delegate to other agents. These patterns show how to hand off a task. They show what a result looks like. They show how failures spread. MCP standardizes model-to-tool. A2A standardizes agent-to-agent.

Step 2: why it matters

Protocols are necessary. Without protocols, each integration is custom. Each tool needs custom glue. Each agent team invents its own handoff format. Nothing works together. With protocols, one tool works for every agent in the company.

Agents built by different teams can subcontract to each other. The 2026 market data in the role survey shows MCP in many agent postings. Teams want to stop custom integration.

There is also a security part. You must read it. Each MCP server is a new privilege boundary. Supplement 9B covers tool-output injection. It covers over-scoped servers. It covers sandboxing.

Build the server here. Make it safe with 9B.

An MCP server uses JSON-RPC. JSON-RPC is a simple message format. Each request is a JSON object. It names a method and its parameters. The server usually uses stdio or HTTP. The host starts the server as a subprocess.

The conversation has three phases. First, initialize. The client and server agree on versions and capabilities. Second, discovery. The client asks "what tools do you have". The client gets schemas back.

Third, invocation. The client calls a tool by name with arguments. The server returns results. This is the whole protocol for an agent systems engineer.

import json
import subprocess
import sys

# ---------------------------------------------------------------------------
# Minimal MCP-shaped server (stdio JSON-RPC) and a client that drives it.
# WHAT: the server exposes tools/list and tools/call; the client
# discovers then invokes. WHY: shows the protocol mechanics with no
# dependencies, so the shape is visible instead of hidden in an SDK.
# WHAT BREAKS: real MCP adds capability negotiation, progress, and
# cancellation. This demo omits them; do not ship it as a server.
# For production, use the official `mcp` Python SDK (note at the end).
# ---------------------------------------------------------------------------
SERVER_SRC = '''
import json, sys
TOOLS = {
    "get_order": {"description": "Fetch an order by id",
                  "params": {"order_id": "string"}},
}
ORDERS = {"o12": {"total_cents": 4999, "status": "shipped"}}
def handle(req):
    m = req.get("method")
    if m == "tools/list":
        return {"tools": [{"name": n, **t} for n, t in TOOLS.items()]}
    if m == "tools/call":
        p = req.get("params", {})
        name, args = p["name"], p.get("arguments", {})
        if name == "get_order":
            oid = args.get("order_id")
            if oid in ORDERS:
                return {"content": [{"type": "text",
                                     "text": json.dumps(ORDERS[oid])}]}
            return {"error": "unknown order_id '%s'" % oid}
        return {"error": "unknown tool '%s'" % name}
    return {"error": "unknown method '%s'" % m}
for line in sys.stdin:
    req = json.loads(line)
    resp = {"jsonrpc": "2.0", "id": req.get("id")}
    out = handle(req)
    resp["result" if "error" not in out else "error"] = out
    sys.stdout.write(json.dumps(resp) + "\\n")
    sys.stdout.flush()
'''

class MiniMCPClient:
    """WHAT: drives the demo server over stdio. WHY: the client side is
    what your agent scaffold becomes: discover tools, validate args
    (Chapter 2's registry plugs in here), call, handle errors."""

    def __init__(self):
        self.proc = subprocess.Popen(
            [sys.executable, "-c", SERVER_SRC],
            stdin=subprocess.PIPE, stdout=subprocess.PIPE,
            text=True, bufsize=1)
        self._id = 0

    def _rpc(self, method, params=None):
        self._id += 1
        self.proc.stdin.write(json.dumps(
            {"jsonrpc": "2.0", "id": self._id,
             "method": method, "params": params or {}}) + "\n")
        self.proc.stdin.flush()
        return json.loads(self.proc.stdout.readline())

    def list_tools(self):
        return self._rpc("tools/list")["result"]["tools"]

    def call_tool(self, name, arguments):
        r = self._rpc("tools/call", {"name": name, "arguments": arguments})
        if "error" in r:
            # Unwrap the server's {"error": msg} envelope so callers get
            # a plain message string, matching the Chapter 2 output shape.
            err = r["error"]
            if isinstance(err, dict):
                err = err.get("error", err)
            return {"status": "error", "error": err}
        return {"status": "ok", "data": r["result"]}

    def close(self):
        self.proc.terminate()

client = MiniMCPClient()
print(client.list_tools())                       # discovery
print(client.call_tool("get_order", {"order_id": "o12"}))   # invocation
print(client.call_tool("get_order", {"order_id": "o99"}))   # clean error
client.close()

Building an MCP server: the checklist

  1. Scope it narrowly. Use one server per trust domain. The orders server reads orders. It does nothing else.
  2. A server with broad access is a confused-deputy machine. A confused-deputy machine is a component. An attacker tricks it into misusing its own authority for someone else. See Supplement 9B.
  3. Schema every tool. Give a name. Give a one-line description. Give typed parameters. This is Chapter 2's ToolDef.schema_text, serialized.
  4. Errors as data. Tool failures return structured errors through the protocol. They never return raw tracebacks.
  5. Idempotent mutations. Each mutating tool takes an idempotency key. See Chapter 2.
  6. Log every call. Log who called. Log the arguments. Log what came back. The trajectory recorder (Chapter 7) reads these logs.
  7. Version the server. Clients pin versions. A schema change without a version bump breaks all agents at the same time.

MCP connects the agent to tools and data. A2A connects agents to each other.

How to read this diagram

  1. Make the scope narrow first. Use one server per trust domain. Do this before you expose any tool.
  2. Schema every tool. Give each tool a name, a one-line description, and typed parameters.
  3. Use errors as data. Send structured errors through the protocol. Do not send tracebacks.
  4. Use idempotent mutations. Every mutating tool takes an idempotency key.

A2A: the handoff protocol

Agent A delegates to Agent B. Four items must be clear. If these items are not clear, the delegation fails in confusing ways.

The task envelope. This is a structured message. It contains a task ID, goal text, inputs, constraints (budget, deadline, allowed tools), and the expected result schema. Free-text handoffs drift. Envelopes do not drift.

The result contract. B returns a status (done / failed / needs-input). B returns the result in the agreed schema. B returns the trajectory or a summary of the trajectory. B returns cost accounting (tokens used). A needs the trajectory to debug B's failures.

A needs the cost to ledger the costs.

Failure propagation. B's failure is A's observation. The system classifies B's failure in the same way as a tool failure (Chapter 4). The failure can be transient (A retries the delegation), an agent error (A rephrases the envelope), or stuck (A replans without B).

Schema validation on both ends. A validates B's result against the contract. A does this before A accepts the result. This is the multi-agent critic from Chapter 1. The system formalizes it as code.

# ---------------------------------------------------------------------------
# A2A handoff envelope with validation.
# WHAT: the message format agents use to delegate. WHY: makes the
# delegation contract machine-checkable, so a malformed handoff fails
# fast at the boundary instead of confusing the downstream agent.
# WHAT BREAKS: if either side skips validation "because we trust each
# other", the first schema drift becomes a silent wrong answer.
# ---------------------------------------------------------------------------
from dataclasses import dataclass, field

@dataclass
class TaskEnvelope:
    task_id: str
    goal: str
    inputs: dict
    constraints: dict = field(default_factory=dict)
    # constraints: {"max_cost_usd": 0.5, "allowed_tools": [...], ...}
    result_schema: dict = field(default_factory=dict)
    # result_schema: {"field": "type"} pairs the result must satisfy

    def validate_result(self, result):
        # Every promised field present, with the promised type name.
        for fname, ftype in self.result_schema.items():
            if fname not in result:
                return False, "missing result field '%s'" % fname
            if type(result[fname]).__name__ != ftype:
                return False, ("field '%s' should be %s, got %s"
                                % (fname, ftype,
                                   type(result[fname]).__name__))
        return True, "ok"

# --- demo: planner delegates research to a worker agent ----------------------
envelope = TaskEnvelope(
    task_id="t-881",
    goal="Summarize the refund policy for gold-tier customers.",
    inputs={"customer_tier": "gold"},
    constraints={"max_cost_usd": 0.50, "allowed_tools": ["policy_search"]},
    result_schema={"summary": "str", "sources": "list"},
)

# Worker returns its result; the delegator validates before accepting.
worker_result = {"summary": "Gold tier: free return shipping, 30-day window.",
                 "sources": ["policy v3.2"]}
ok, msg = envelope.validate_result(worker_result)
print(ok, msg)   # True

bad_result = {"summary": "Gold tier: free return shipping."}  # missing sources
print(envelope.validate_result(bad_result))  # (False, "missing result field 'sources'")

The envelope is small on purpose. Every field earns its place. The ID is for tracing. The constraints are for the cost ledger. The result schema is for the critic. Agents must not negotiate anything else during a task.

How to read this diagram

Time flows downward. The delegator sends a validated envelope. The worker uses MCP tools in the same way a single agent would. The result returns with the accounting attached. Validation happens two times. The worker validates the envelope.

The delegator validates the result. The retry budget is one. This matches Chapter 1's multi-agent rule.

Watch out: the common misunderstanding

"MCP solves tool security." MCP solves tool interoperability. Security is a separate layer. Security is mostly unchanged. The server still decides who can call what. Tool outputs are still untrusted input. A malicious or compromised server is still a threat.

Teams that deploy MCP servers with the same care they give to any internal API do well. These teams use authentication, scoping, audit logs, and input validation. Teams that treat the protocol as a security boundary learn otherwise. Read Supplement 9B before you expose any server beyond your laptop.

Key takeaways

  • MCP standardizes model-to-tool. This includes initialize, discover, and invoke. Build servers narrow. Schema everything. Version them.
  • A2A standardizes agent-to-agent. This includes envelopes, result contracts, failure propagation, and validation on both ends.
  • The protocol is plumbing. Chapters 2 through 4 are the design. Plumbing without design is only faster ways to fail.
  • Protocols do not give security. Harden with Supplement 9B.

Chapter 6: Cost control

Each tool call and model call now costs money. This chapter adds a ledger to the loop. Budgets come from task value. The ledger routes each step to the correct model. Cascades try cheap options first.

Step 1: the simplest version

Cost per task is the money that a completed task spends. Cost control is the engineering of cost per task. It keeps the spend of a completed task inside a budget. It also keeps the success rate steady. Cost control has three levers.

Token budgets limit the money that a task can spend. The system enforces this limit in the loop. Model routing uses a cheaper model for easy steps. It uses a stronger model when it is important. Cascade design tries cheap options first. It uses expensive options only if the cheap options fail.

Step 2: why it matters

Agent cost increases with steps. Steps increase with ambition. A 5-step support task can cost $0.30 at frontier prices. The same task can grow to 25 steps. It can use full-history prompts and a critic on each step. This task can cost $6.

Nobody sees this until the bill arrives. This is because each step seems cheap alone. Cost control shows the total cost before the system spends it. It gives the scaffold the tools to stay within the budget. In 2026 team postings, "cost per successful outcome" is the metric. This metric decides which agent stacks will scale and which will not.

Worked example. One history-heavy flagship step: 4,000 in-tokens and 300 out-tokens. (4,000 ÷ 106) × $3 = $0.012 in. Plus (300 ÷ 106) × $15 = $0.0045 out. This is $0.0165 per step. Ten steps: $0.165, about $0.17.

The same ten steps on the small model: 10 × ((4,000 ÷ 106) × $0.10 + (300 ÷ 106) × $0.40) = 10 × $0.00052 = $0.0052, about $0.005. The 30x difference is what routing uses.

# ---------------------------------------------------------------------------
# Cost ledger with per-task budgets.
# WHAT: records every model call's token usage and dollar cost, and
# refuses to start steps past the budget. WHY: makes cost visible inside
# the loop, where it can still change behavior, instead of on the
# invoice, where it cannot. WHAT BREAKS: prices below are illustrative
# 2026 numbers. If you hard-code them and prices move, budgets silently
# mislead. Load prices from config (see PRICES dict) and review them.
# ---------------------------------------------------------------------------
PRICES = {
    # dollars per million tokens, illustrative September 2026 frontier
    # pricing for the model classes used in labs. Replace with your
    # provider's current sheet.
    "flagship": {"in": 3.00, "out": 15.00},
    "mid":      {"in": 0.60, "out": 2.40},
    "small":    {"in": 0.10, "out": 0.40},
}

class CostLedger:
    def __init__(self, budget_usd):
        self.budget_usd = budget_usd
        self.spent_usd = 0.0
        self.calls = []  # audit trail: (model, in_tok, out_tok, usd)

    def record(self, model, in_tokens, out_tokens):
        p = PRICES[model]
        usd = (in_tokens / 1e6) * p["in"] + (out_tokens / 1e6) * p["out"]
        self.spent_usd += usd
        self.calls.append((model, in_tokens, out_tokens, round(usd, 6)))
        return usd

    def remaining(self):
        return self.budget_usd - self.spent_usd

    def allow_step(self, est_cost_usd):
        # The loop calls this before each model call. A step that would
        # break the budget does not run; the caller degrades instead
        # (shorter prompt, cheaper model, or clean stop).
        return self.remaining() >= est_cost_usd

# --- demo: budget a 10-step ReAct run ---------------------------------------
ledger = CostLedger(budget_usd=0.50)
for step in range(10):
    # 4k input tokens (history-heavy) + 300 output tokens, flagship model.
    if not ledger.allow_step(0.02):
        print("step %d: budget stop" % step)
        break
    ledger.record("flagship", 4000, 300)
print("spent: $%.4f over %d calls" % (ledger.spent_usd, len(ledger.calls)))
# 10 x (4000/1e6 x $3 + 300/1e6 x $15) = 10 x $0.0165 = $0.165

Ten history-heavy flagship steps cost about $0.17. The same ten steps on the small model cost about $0.005. That 30x difference is what routing uses.

Model routing: the right model per step

Not every step needs the flagship. Production teams use a practical split:

  • Small model: parsing tool outputs, formatting, classification, query rewriting, summarization for compaction. High volume, low judgment.
  • Mid model: standard ReAct steps, plan execution, retrieval ranking.
  • Flagship model: planning, replanning after failure, final-answer synthesis on hard tasks, the critic's verdict on high-stakes work.

How to read this diagram

  1. The input arrives at the router.
  2. The router classifies it by step type. It does not classify it by content.
  3. Each class has its own model. The small model is for parsing. The flagship model is for planning.
  4. The chosen model handles the step. The router never does the work itself.

The router is a small policy. It is not a model. It routes by step type. It has an escalation rule. If the small model fails two times on a step class, that class escalates to the mid model for the rest of the run. Static routing is predictable.

Static routing is auditable. Learned routing is a research project. A model that picks models is learned routing. Start static routing.

# ---------------------------------------------------------------------------
# Static step router with escalation.
# WHAT: maps step types to model classes; repeated failures escalate the
# step class to a stronger model. WHY: captures most of the savings of
# smart routing with none of the unpredictability. WHAT BREAKS: routing
# the critic or the planner to the small model to save money. The steps
# where judgment concentrates are exactly where cheap models fail
# silently. Never route planning or final verdicts down.
# ---------------------------------------------------------------------------
class StepRouter:
    ORDER = ["small", "mid", "flagship"]

    def __init__(self):
        # Default assignment by step type. Tune from trajectory data.
        self.route = {
            "parse": "small",
            "format": "small",
            "rewrite_query": "small",
            "compact": "small",
            "act": "mid",
            "retrieve_rank": "mid",
            "plan": "flagship",
            "replan": "flagship",
            "critic": "flagship",
            "final": "flagship",
        }
        self.failures = {}  # step_type -> consecutive failure count

    def model_for(self, step_type):
        return self.route.get(step_type, "mid")

    def note_failure(self, step_type):
        self.failures[step_type] = self.failures.get(step_type, 0) + 1
        # Two consecutive failures escalate one tier, once per run.
        if self.failures[step_type] == 2:
            cur = self.route.get(step_type, "mid")
            nxt = self.ORDER[min(self.ORDER.index(cur) + 1,
                                 len(self.ORDER) - 1)]
            self.route[step_type] = nxt

    def note_success(self, step_type):
        self.failures[step_type] = 0

r = StepRouter()
print(r.model_for("act"), r.model_for("plan"))  # mid flagship
r.note_failure("act"); r.note_failure("act")
print(r.model_for("act"))  # flagship: escalated after 2 failures

Cascade design: try cheap, escalate on failure

How to read this diagram

  1. Top: the cheap model handles about 80 percent of steps at $0.10 per 1M tokens.
  2. If confidence is low, escalate to the mid model. It handles about 15 percent.
  3. If the step still fails, escalate to the strong model for the last 5 percent.
  4. Log every escalation. The log is your cost signal.

The parts

  • Cheap tier. What it is: the smallest model that can try. Why it exists: most steps are easy and cheap steps keep the bill low. If it fails: you paid little and learned the step is hard.
  • Mid tier. What it is: the fallback model. Why it exists: it catches what the cheap tier cannot. If it fails: the strong tier is still there.
  • Strong tier. What it is: the best model, used rarely. Why it exists: some steps truly need it. If overused: the budget dies.
  • Confidence threshold. What it is: the score that triggers escalation. Why it exists: it makes the cascade automatic. If it is wrong: easy steps escalate or hard steps never do.

A cascade runs the whole task on the cheap stack first. It only escalates the failures to the expensive stack. It works when the cheap stack solves a large share of tasks. The small stack solves 70 percent of tasks at $0.05. The flagship stack solves 95 percent of the remaining tasks at $0.50. The blended cost is 0.05 + 0.3 x 0.50 = $0.20 per task started.

The cost for flagship-only is $0.50. The cascade is cheaper if the cheap tier's solve rate times the price gap beats the escalation cost. The eval harness (Supplement 9A) measures the solve rates. Use these solve rates to make this decision. Do not guess the solve rates.

How to read this diagram

  1. The cheap model answers first. It is fast and has a low cost.
  2. A confidence check scores the answer.
  3. High confidence answers. Low confidence answers escalate to the bigger model.

Grading every cheap attempt costs grader calls, so the cascade pays off when grading is cheaper than the flagship attempt it saves.

Watch out: the common misunderstanding

"Cost control means using the cheapest model." It means spending where the return is. The planner and the critic earn the flagship. A bad plan wastes ten cheap steps. A bad verdict accepts wrong work. The savings are in the high-volume low-judgment steps. These steps are parsing, formatting, rewriting, and compacting.

Cut costs there first. A team that routes everything to the small model gets a cheap agent that fails. A team that routes by judgment gets a cheap agent that works.

  • Budget per task from task value. Enforce the budget inside the loop. Do not enforce it on the invoice.
  • Route by judgment. Use small models for parsing and formatting. Use the flagship model for planning and verdicts. Escalate on repeated failure.
  • Cascades win when the cheap tier solves most tasks. Cascades win when the grader is trustworthy. Measure. Do not guess.
  • Ship the cost table monthly. It is the deliverable.

Chapter 7: Debugging agents

Budgets hold. Protocols connect. Retries fire. Something still breaks. The trajectory is the crime scene. This chapter shows how to read one run well.

This helps you fix causes, not incidents.

Trajectory analysis: reading one run well

How to read this diagram

  1. Steps 1 to 3 are green: good steps.
  2. Step 4 is red: the first wrong step. The agent passed bad tool arguments here.
  3. Steps 5 to 7 are amber: wasted recovery. The agent burns budget without fixing step 4.
  4. Step 8 is red: the loud failure. The cause is step 4, not step 8.
  5. Fix step 4. That is the lesson of trajectory analysis.

The parts

  • Good step. What it is: a step that moved the task forward. Why it matters: it tells you what already works. If ignored: you rewrite working code.
  • First wrong step. What it is: the earliest step that broke the plan. Why it matters: it is the true cause. If missed: you patch symptoms forever.
  • Wasted recovery. What it is: retries that never address the cause. Why it matters: it is pure budget burn. If ignored: costs grow with no learning.
  • Loud failure. What it is: the visible crash at the end. Why it matters: it is only the symptom. If fixed alone: the next run fails the same way.

A trajectory is a list of steps. Each step has the same parts. You get the model input (prompt). You get the model output (thought + action). You get the tool that the system calls with its arguments. You get the tool's observation.

You get the timing. The structured read asks five questions in order:

How to read this diagram

  1. Each step has the same parts. It has a prompt in. It has a thought plus an action. It has a tool call. It has an observation. It has timing.
  2. Step 4 is where the run stopped being recoverable. Step 8 is only the symptom.
  3. The five questions in order are: Where did it first go wrong? Was the plan, action, or observation at fault? Was it recoverable? What signal was missing? What changes in the next run?
  1. Where did it first go wrong? This is not where it failed. This is where the run stopped being recoverable. The bad assumption at step 4 caused the failure at step 18.
  2. Was the plan, the action, or the observation at fault? A wrong plan needs planning work. A right plan with a wrong tool call needs tool design (Chapter 2). A right call with a misleading observation needs better tool output or retrieval (Chapters 2, 3).
  3. Did the agent notice? The observation contained the error. The agent ignored it. The failure is in error-message design or in the model's reading. It is not in the world.
  4. Did it recover, and how? Successful recoveries are the raw material for retry policies (Chapter 4). Failed recoveries that looped are stuck-loop signatures.
  5. What would a human have done differently at the first-wrong step? The answer is usually the fix. This can be a different tool. This can be a clarification question. This can be a plan revision.

The recorder below gives every trajectory the same shape, so the analysis code (and the human) always knows where to look.

import json
import time

# ---------------------------------------------------------------------------
# Trajectory recorder.
# WHAT: appends one structured record per step: inputs, outputs, tool,
# observation, timing, and cost. WHY: debugging without a standard
# record is archaeology. Every analysis in this chapter assumes this
# shape. WHAT BREAKS: recording the tool result but not the arguments
# makes the record useless for replay. Record both, always.
# ---------------------------------------------------------------------------
class TrajectoryRecorder:
    def __init__(self, task_id):
        self.task_id = task_id
        self.steps = []
        self.start = time.time()

    def record(self, thought, action, action_args, observation,
               model="mid", in_tokens=0, out_tokens=0):
        self.steps.append({
            "n": len(self.steps),
            "thought": thought,
            "action": action,            # tool name or "finish"/"error"
            "action_args": action_args,  # exact args: replay needs these
            "observation": observation,
            "model": model,
            "in_tokens": in_tokens,
            "out_tokens": out_tokens,
            "t": round(time.time() - self.start, 3),
        })

    def save(self, path):
        with open(path, "w") as f:
            json.dump({"task_id": self.task_id, "steps": self.steps}, f,
                      indent=1)

    def outline(self):
        # One line per step: the fastest way to read a run.
        return "\n".join(
            "#%d [%s] %s(%s) -> %s" % (
                s["n"], s["model"], s["action"],
                json.dumps(s["action_args"])[:60],
                str(s["observation"])[:70])
            for s in self.steps)

The outline() method is the workhorse. It shows one line per step. It shows the whole run on a screen. Most debugging sessions start here. They do not start in the full log.

Failure clustering: from incidents to causes

One failed run is an incident. Fifty failed runs are data. Clustering groups failures by signature. Each group gets one fix. The signatures that work are simple and structural. They are not semantic:

Re-running shows which clusters became smaller and which clusters moved.

How to read this diagram

  1. Fifty failed runs enter the system as recorded trajectories.
  2. First, normalize the data. If you do not normalize the data, "o12 not found" and "o13 not found" become different clusters. The pattern hides.
  3. Cluster by structure. Do not cluster by semantics. Cluster by the failing tool and error class. Cluster by the stuck-loop shape. Cluster by the step of the first failure. Cluster by the trajectory shape.
  4. Each cluster gets only one fix. A large cluster is one root cause with a size.
  5. Re-run the system. This closes the loop. Fixed clusters become smaller. The remaining clusters show what to fix next.
  • Group by failing tool and error class. Group by the tool name and the first line of the error. This finds the Chapter 2 problems. One tool with a confusing error message shows as a large cluster.
  • Group by stuck-loop pattern. Group runs where the same action repeats 3 or more times. This finds the tasks where the agent cannot continue. This includes a missing tool, a wrong plan, or an unanswerable task.
  • Group by step of first failure. This is a histogram of where runs stop. If deaths cluster at step 1-2, this means prompt or task-understanding problems. If deaths spread evenly, this means per-step reliability problems (Chapter 4). If deaths cluster late, this means context or budget exhaustion (Chapter 3/6).
  • Group by trajectory shape. This includes the action sequence length, the distinct tools used, and the error count. Outlier shapes often have the same cause.

from collections import Counter, defaultdict

# ---------------------------------------------------------------------------
# Failure clustering over recorded trajectories.
# WHAT: groups failed runs by structural signatures. WHY: turns "many
# failures" into "three causes with sizes", which is a fix list.
# WHAT BREAKS: clustering on raw error text (with ids and timestamps)
# fragments real clusters. Normalize first: the _norm() step below is
# the most important line in this file.
# ---------------------------------------------------------------------------
def _norm(text):
    # Normalize away ids, numbers, timestamps so the same failure
    # classifies the same. Without this, "o12 not found" and "o13 not
    # found" become different clusters and the real pattern hides.
    import re
    t = str(text).lower()
    t = re.sub(r"o\d+", "oID", t)        # order ids
    t = re.sub(r"\d+(\.\d+)?", "N", t)   # numbers
    t = re.sub(r"\s+", " ", t)
    return t[:80]

def cluster_failures(trajectories):
    """trajectories: list of step-lists (from TrajectoryRecorder.steps).
    Returns {signature: [task_ids]} for the top signatures."""
    groups = defaultdict(list)
    for traj in trajectories:
        tid = traj[0].get("task_id", "?") if traj else "?"
        # signature 1: first error's (tool, normalized error)
        sig = "no-error"
        for s in traj:
            obs = str(s.get("observation", ""))
            if obs.startswith("ERROR"):
                sig = "tool=%s err=%s" % (s["action"], _norm(obs))
                break
        # signature 2: stuck loop?
        actions = [s["action"] for s in traj]
        stuck = any(actions[i] == actions[i+1] == actions[i+2]
                    for i in range(len(actions) - 2))
        if stuck:
            sig += " +STUCK"
        groups[sig].append(tid)
    # largest clusters first: fix the fat ones
    return dict(sorted(groups.items(), key=lambda kv: -len(kv[1])))

def first_failure_step_hist(trajectories):
    """Histogram of where runs first error. Read the shape, not the bars:
    early cluster = understanding problem; flat = reliability problem;
    late cluster = context/budget problem."""
    hist = Counter()
    for traj in trajectories:
        for s in traj:
            if str(s.get("observation", "")).startswith("ERROR"):
                hist[s["n"]] += 1
                break
    return hist

def fake_traj(tid, fail_tool, err, stuck=False):
    steps = [{"task_id": tid, "n": 0, "action": "plan", "action_args": {},
              "observation": "ok", "model": "flagship"}]
    steps.append({"task_id": tid, "n": 1, "action": fail_tool,
                  "action_args": {"order_id": "o%d" % (100 + hash(tid) % 50)},
                  "observation": "ERROR: " + err, "model": "mid"})
    if stuck:  # same failing action three times
        for n in (2, 3):
            steps.append({"task_id": tid, "n": n, "action": fail_tool,
                          "action_args": {}, "observation": "ERROR: " + err,
                          "model": "mid"})
    return steps

runs = ([fake_traj("t%d" % i, "get_order", "order oID not found", stuck=True)
         for i in range(4)]
        + [fake_traj("t%d" % (10 + i), "refund", "amount must be cents, got dollars")
           for i in range(2)])
for sig, tids in cluster_failures(runs).items():
    print("%d runs: %s" % (len(tids), sig))

The debugging session, as a procedure

  1. Pull the last N failed trajectories from the recorder store. N=50 is a good start.
  2. Run cluster_failures. Read the top 3 clusters. Each cluster is a hypothesis with a size.
  3. For each cluster, read one full trajectory. Use the five questions. Confirm the hypothesis or make it more exact.
  4. Check the first-failure histogram. Confirm that the cluster story matches the shape.
  5. Fix the biggest cluster first. Make one fix. Then re-run the eval set (Supplement 9A). Confirm that the cluster becomes smaller.
  6. Log the fix with its cluster signature. Next month, the same signature means regression. It does not mean a new bug.

Watch out: the common misunderstanding

"The model is the problem." This is true sometimes. But in many trajectories, the model did something reasonable. This is because of what it saw. The tool lied. The error message misled. The observation was cut at the important line.

The plan was never written. Debugging that blames the model ends with prompt changes. These changes move failures around. Debugging that reads the trajectory ends with tool fixes, schema fixes, and budget fixes. These fixes remove failure classes.

If you write "the model should have known," stop. Ask what in the trajectory would have let it know. The answer is usually a missing tool, a bad error message, or a dropped fact. All three are engineering.

Key takeaways
