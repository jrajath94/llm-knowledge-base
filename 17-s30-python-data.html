Core ideas, worked end to end

Concept 1: Vectorization and broadcasting

1. What it is, in plain words. Vectorization means expressing an operation over a whole array at once instead of looping in Python. Broadcasting is the set of shape rules NumPy uses to stretch smaller arrays so they line up with larger ones. A view is a new array object that shares memory with the original; a copy owns its own memory. A stride is the number of bytes you move in memory to step one element along an axis.

2. Why it exists. A Python loop over a million elements does a million rounds of interpreter overhead: type checks, dispatch, allocation. NumPy pushes the loop into compiled C, which runs close to the speed of the memory bus. Without vectorization, the pairwise distance task in the lab (FAANG classic) would take minutes instead of milliseconds, and no interview answer that slow passes.

3. How it works, step by step. Step one: data sits in one contiguous block of memory, one element after the next. Step two: NumPy records the shape and the strides, so it knows how to walk the block as rows and columns. Step three: a vectorized call like a + b runs a single tight C loop over that block. Step four: when shapes differ, broadcasting compares them right to left; any axis of size 1 (or a missing axis) stretches to match. The stretch is virtual: strides of zero reuse the same memory, so no copy happens.

4. Concrete numbers. Summing 10 million floats: a Python loop takes on the order of 2 seconds; np.sum takes on the order of 10 milliseconds. That is a 200x gap, and the gap grows with array size because the interpreter cost is per element while the C loop is limited by memory bandwidth. Memory: a float64 array of 10 million elements occupies 80 MB contiguously; a Python list of the same values occupies roughly 280 MB scattered across the heap, which also destroys cache locality.

5. The common misunderstanding. Beginners think broadcasting matches shapes from the left. It aligns from the right. A vector of shape (3,) added to a matrix of shape (3, 4) stretches across the columns, not down the rows, and NumPy will not warn you. The second misunderstanding is views: slicing an array returns a view, so writing into the slice mutates the original. That is a feature for speed and a trap for correctness.

Key takeaways

  • Vectorize the inner loop away; NumPy runs it in compiled C over contiguous memory.
  • Broadcasting aligns shapes from the right; a size-1 axis stretches virtually through strides, with no copy.
  • Slices are views, not copies; mutating a slice mutates the original.
  • Assert shapes before every non-trivial operation; most NumPy bugs are silent shape bugs.

Concept 2: Joins, groupby, and leakage-safe time features

1. What it is, in plain words. A DataFrame is a labeled table: named columns, an index, and typed data. A join (merge) combines two tables on shared key columns. A groupby splits rows into groups by key, aggregates each group, and combines the results. Feature engineering is the construction of model inputs from raw columns. Leakage is when a feature contains information that would not be available at prediction time.

2. Why it exists. Models consume tables, not event streams. Somebody has to turn raw logs into one row per prediction moment with the right features, and that somebody is pandas code. If the join is wrong, rows duplicate or drop and every downstream number is fiction. If a time feature leaks, the model learns to read the future and scores beautifully offline, then fails on live data where the future has not happened yet.

3. How it works, step by step. Step one: filter and clean the event table. Step two: build user-level aggregates with groupby (counts, sums per user). Step three: merge the feature table onto the label table on the key, choosing the join type deliberately: left join keeps every label row, inner join drops unmatched rows. Step four: for time-based features, sort by user and timestamp, compute the cumulative aggregate, then shift by one so each row sees only strictly earlier events. Step five: validate row counts before and after every merge.

4. Concrete numbers. Take a users table with 100,000 rows and a purchases table where one prolific user has 3 duplicate rows on the join key. A merge on that key turns that one user into 3 rows; if the average user has 1.2 matches, the merged table has about 120,000 rows instead of 100,000, and every revenue sum is inflated. The lab has you detect this with a row-count check and fix it by deduplicating one side first.

5. The common misunderstanding. Beginners trust the merge and never check the row count. The second misunderstanding is that .apply with a lambda is fine for row-wise logic. It is not: apply calls Python once per row, while a vectorized boolean comparison runs in C. The lab times both so you feel the gap. The third is cumsum without shift: it looks right, the numbers even look better, and that is exactly why it is dangerous.

How to read this diagram

  1. Left table: two rows share the join key k = 7. Right table: two more rows share the same key.
  2. A merge on k pairs every left row with every right row, a Cartesian product on that key.
  3. The result has 2 times 2 = 4 rows, and each side is now duplicated. Aggregates like sums and means are silently wrong.
  4. The fix, stated at the bottom: assert key uniqueness on at least one side before merging, and check row counts before and after every merge.

How to read this diagram

  1. The timeline shows one user with four events; the label row is the purchase at t3.
  2. The green box shows the safe pattern: cumsum then shift by 1, so the feature at t3 counts only purchases strictly before t3 (zero of them).
  3. The red box shows the leak: without the shift, the feature at t3 sees the purchase at t3 itself and reports 1.
  4. The dashed arrow marks the future event at t4 flowing backward into the leaky feature. In production, t4 has not happened yet, so the model is cheating.
  5. Rule: every time-based feature must be computed as-of the label timestamp, never after.

7. Interview relevance. Many-to-many join diagnosis and the cumsum-plus-shift pattern are signature FAANG interview traps. The interviewer gives you an event log and asks for features; the correct answer includes the shift, stated unprompted.

Key takeaways

  • Check row counts before and after every merge; duplicates on the join key multiply rows silently.
  • groupby plus transform keeps row count; groupby plus agg collapses to one row per group. Choose deliberately.
  • Time features must be as-of the label timestamp: sort, cumsum, then shift by 1.
  • Prefer vectorized column operations over .apply; the per-row Python call overhead dominates.

Concept 3: Exploratory data analysis as structured suspicion

1. What it is, in plain words. Exploratory data analysis (EDA) is the disciplined first pass over a dataset before modeling: checking what each column means, what is missing, what the distributions look like, how the target behaves across slices of the data, and which features could leak the answer. The grain of a table is what one row represents (one user, one event, one day). A slice is a subgroup of rows, for example one country or one signup cohort.

2. Why it exists. Data is never what the schema promises. Missing values hide as -1 or the string "unknown". Duplicates inflate counts. The label is imbalanced 99 to 1 and accuracy becomes a lie. One slice behaves oppositely to the aggregate, which is Simpson's paradox, and a model trained on the aggregate learns the wrong lesson. EDA exists to surface these facts while they are still cheap to fix.

3. How it works, step by step. Step one: sanity checks, ten minutes. Confirm the grain, the schema, the row count, and that keys are unique. Step two: missingness and duplicates. Count them per column, and look for encoded missingness (-1, empty string, "unknown"). Step three: distributions. Summarize numerics (mean, median, percentiles), plot the two highest-signal distributions, and decide whether outliers are errors or signal (fraud and whales are signal; do not blindly delete). Step four: the target. Check label balance, then compute the target rate per slice. Step five: leakage hunt. For each feature, ask: would I know this value at prediction time? Anything computed after the label moment is suspect.

4. Concrete numbers. A fraud dataset with 1% positives: a model that predicts "not fraud" for every row scores 99% accuracy and catches zero fraud. The EDA task on label imbalance makes you compute the base rate first, so you never report accuracy alone on such data again. A slice analysis might show 85% accuracy overall but 52% on the newest signup cohort, which is the number that decides whether the model ships.

5. The common misunderstanding. Beginners treat EDA as plotting for its own sake and produce twenty histograms nobody reads. The lab enforces the opposite: two high-signal distributions, chosen because they change a decision. The second misunderstanding is deleting outliers on sight. Outliers are sometimes the entire business case. The third is assuming "no missing values" from a null check when the missingness is encoded as a magic number.

7. Interview relevance. "Walk me through how you would start with this dataset" is one of the most common ML interview openers. The expected answer is this exact sequence: grain and schema, missingness, distributions, target and slices, leakage. Candidates who jump to model choice first are telling the interviewer they skip diagnosis.

Key takeaways

  • Confirm grain, schema, and key uniqueness before anything else; ten minutes here saves ten hours later.
  • Look for encoded missingness (-1, "unknown", empty strings), not just nulls.
  • Compute the label base rate and slice metrics before choosing any model or metric.
  • Interrogate every feature for leakage: would this value exist at prediction time?

# Pairwise distance (FAANG classic)
def pairwise_distance(X):
    # ||x-y||^2 = ||x||^2 + ||y||^2 - 2 x·y
    sq = np.sum(X * X, axis=1, keepdims=True)
    dist2 = sq + sq.T - 2 * (X @ X.T)
    dist2 = np.maximum(dist2, 0.0)
    np.fill_diagonal(dist2, 0.0)
    return np.sqrt(dist2)

Q1. Which of these shape pairs broadcast together without error? A: (3,) with (4, 5). B: (4, 1) with (4, 5). C: (2, 5) with (4, 5). D: (5,) with (4, 5).

Answer: B and D. Broadcasting aligns shapes from the right; each axis pair must match or include a 1.

  • A, wrong: (3,) aligns right against (4, 5): the 3 meets the 5 and neither is 1, so it fails.
  • B, right: (4, 1) against (4, 5): 4 matches 4, and the size-1 axis stretches to 5.
  • C, wrong: (2, 5) against (4, 5): 5 matches 5 but 2 vs 4 fails.
  • D, right: (5,) against (4, 5): right-aligned, 5 matches 5, and the missing axis stretches to 4.

Q2. a = np.arange(6).reshape(2, 3); b = a[:, :2]; b[:] = 0. What is a now, and what general rule does this demonstrate?

Answer: the first two columns of a become 0: [[0, 0, 2], [0, 0, 5]]. Basic slicing returns a view that shares memory with the original, so writing through b mutates a. The rule: if you need independence, call .copy() explicitly.

Q3. Your training table has one row per user and you merge a purchases table on user_id. Afterwards the table has more rows than users. Name the cause, the check that catches it, and the fix.

Answer: duplicate keys on the right side caused a many-to-many explosion: each user row paired with every matching purchase row. The check: compare row counts before and after the merge, and assert key uniqueness on at least one side (df["user_id"].is_unique). The fix: aggregate or deduplicate the right side to one row per key before merging.

Q4. Why does computing a cumulative purchase count per user require a shift by 1 before using it as a training feature?

Answer: without the shift, the cumulative count at row t includes the event at row t itself. If the label is derived from that same row (for example, the row is the purchase), the feature encodes the answer: leakage. Shifting by 1 makes each row see only strictly earlier events, which matches what is knowable at prediction time.
